# 设计取舍记录

本文记录 RayAgent 几项影响面较大的选择：当时要解决什么问题、选了什么、放弃了什么、代价是什么。记录的是选择本身，不是推荐做法；场景变化时结论可以推翻。

每条给出可核对的依据。课程章节只写编号，目录在文末。

## 自研执行循环，不引入现成 Agent 框架

**问题：** 需要一套能规划、能调工具、能被观察和打断的执行循环。

**选择：** 自己实现 Plan + ReAct，模型调用、工具分发、事件发布、状态保存全部在本仓库内。

**放弃：** 直接采用成熟框架的编排与工具抽象，省掉一部分实现工作。

**理由：** 项目的目标是研究 Harness 本身。框架会把上下文装配、循环退出、失败处理这些最值得研究的判断封装成配置项，读代码读不到取舍。自研的版本可以逐行追踪一次任务里信息与控制的交接。

**代价：** 流式、并行工具调用、上下文预算、检查点这些框架通常已经提供的能力，这里都需要自己补，目前都还没有。协议接入或局部修复不应顺带替换主循环。

**依据：** [调研：工作区与 Harness 演进](research/workspace-harness-research.md)（2026-09-09）评估后建议维持二开而非重建。

## 双层循环，而不是单循环加计划工具

**问题：** 多步骤任务需要一个"还剩什么工作"的表示。

**选择：** 外层由程序按步骤状态调度，内层由模型在步骤内自由决策，两层只在步骤边界交接。

**放弃：** 单层 Agent Loop，把"更新计划"做成一个普通工具由模型自己调用。

**理由：** 步骤边界给了程序一个确定的介入点：可以在这里更新计划、清理上下文、发布进度、判断是否继续。单循环方案里没有这样的锚点，进度完全由模型的叙述决定。

**代价：** 每轮多一次规划调用；计划与实际执行会不一致——执行器能看到原始目标，常在一步内把后续工作也做完，导致计划塌缩。另外计划更新只在存在未结束步骤时才合并，不能当作任意时刻追加工作的入口。

**依据：** 课程第 07 章给出了两种方案的完整对照。

## 模型调用不走流式

**问题：** 模型响应可能长达数十秒，期间页面没有内容。

**选择：** 使用一次性块响应，任务级事件通过 SSE 推送。

**放弃：** 流式接收 token 并增量拼装 `tool_calls`。

**理由：** 非流式的响应解析是一次完整的 JSON，工具调用的边界清晰；流式需要维护未完成状态、区分连接断开与协议结束、处理增量 `tool_calls` 分片，复杂度集中在最容易出错的位置。当时优先保证执行链正确。

**代价：** 首字延迟等于整次响应耗时；页面在模型生成期间只能显示上一次事件。2026-09-14 的一次端到端观察里，一个写入 12 字节文件的任务首次输出延迟约 14 秒。这是[调研：Harness 能力评估](research/harness-capability-review-2026-09-14.md)列出的 P1 问题之一。

## 沙箱按会话准备，不按任务创建

**问题：** 工具动作需要一个文件、进程、浏览器都可用的环境。

**选择：** 创建任务时按会话标识查找或创建容器，任务结束不销毁。

**放弃：** 每个任务一个一次性环境，结束即回收。

**理由：** 同一会话内的多轮任务能看到彼此的工作文件，符合"继续上次的工作"这一使用预期；反复创建容器的启动开销也高。

**代价：** 任务结束不等于资源释放，环境靠 TTL 或显式销毁回收；容器隔离是按会话而不是按任务，也不构成租户隔离。另外准备链路是统一的，不使用浏览器的纯文本任务也会启动浏览器。

## MCP 与 A2A 接进同一个工具层

**问题：** 外部工具和远程 Agent 都需要参与本地任务。

**选择：** 两者都实现为工具，接进现有的工具契约与分发路径，主执行流程不变。

**放弃：** 为远程 Agent 设计独立的协作流程，例如把远程 Task 的状态提升为本地计划步骤。

**理由：** 保持一个执行链，模型只需要理解"调用工具"这一种交互；协议差异收敛在适配层内部。

**代价：** A2A 的 Task 语义被压扁成一次工具调用的返回值——远程的 `input_required`、`auth_required` 无法接到本地的等待续接机制上，只能按失败返回；远程状态变化也不会逐条投影为本地进度事件。远程产物不会自动成为本地可下载附件。

**依据：** 课程第 14、15 章对比了两种协议的契约差异。

## 等待用户时退出重建，而不是挂起协程

**问题：** Agent 提问后需要等待用户回复，可能等很久。

**选择：** 保存等待状态并结束当前运行，回复到来时重新组装运行器继续。

**放弃：** 让协程阻塞在等待上，回复到来时唤醒。

**理由：** 挂起会长期占用进程内资源，而且一旦进程重启，调用栈上的状态全部丢失。退出重建让等待期间不依赖任何进程内状态。

**代价：** "继续"必须能完全从已保存的状态重建，只存在于调用栈里的信息会丢失；回复被包装成一条没有配对调用的工具结果接回上下文。

**依据：** 课程第 08 章。

## 取消不引入独立终态

**问题：** 用户请求停止后，会话需要一个终态。

**选择：** 取消执行协程，写入与正常结束相同的完成状态和终态事件。

**放弃：** 增加一个独立的取消状态，并向下传播到沙箱进程和外部调用。

**理由：** 实现简单，页面不需要额外分支。

**代价：** 这是本文中代价最明显的一条。状态字段无法区分"跑完了"和"被叫停了"；取消不会终止沙箱里的 OS 进程，不会回滚已写入的文件，也不保证远程任务同步结束。判断一次任务是否真的完成，不能只看状态字段。

**依据：** 代码核对确认会话状态枚举中没有取消态，停止路径不调用 Shell 终止也不销毁沙箱；课程第 08 章按故障窗口展开了这一点。
