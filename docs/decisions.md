# 设计取舍记录

本文记录 RayAgent 几项影响面较大的选择：当时要解决什么问题、选了什么、放弃了什么、代价是什么。记录的是选择本身，不是推荐做法；场景变化时结论可以推翻。

每条给出可核对的依据。课程章节只写编号，目录在文末。

## 自研执行循环，不引入现成 Agent 框架

**问题：** 需要一套能规划、能调工具、能被观察和打断的执行循环。

**选择：** 自己实现执行循环（旧版为 Plan + ReAct 双循环，W1 起为单循环加计划工具），模型调用、工具分发、事件发布、状态保存全部在本仓库内。

**放弃：** 直接采用成熟框架的编排与工具抽象，省掉一部分实现工作。

**理由：** 项目的目标是研究 Harness 本身。框架会把上下文装配、循环退出、失败处理这些最值得研究的判断封装成配置项，读代码读不到取舍。自研的版本可以逐行追踪一次任务里信息与控制的交接。

**代价：** 并行工具调用与检查点这些框架通常已经提供的能力，这里都需要自己补，目前都还没有（W1 支持一次回复多个调用，但仍串行执行；W2 已按单次请求检查上下文容量）。模型响应自 W6 起默认流式组装，见下节。协议接入或局部修复不应顺带替换主循环。

**依据：** [旧方案背景与调研来源](background/README.md#历史资料合并与证据来源)记录了 2026-09-09 的评估：维持二开而非重建。后续演进范围见[二次开发总计划](plan/README.md)，下列选择仍描述当前实现。

## 单循环加计划工具，而不是双层循环

**问题：** 多步骤任务需要一个"还剩什么工作"的表示。

**选择（W1 起）：** 一个 Agent 循环、一份记忆。计划清单是模型调用的普通工具 `update_plan`，程序只校验格式、保存并展示，不按清单调度；没有工具调用的回复就是最终答复。

**放弃：** 旧版的双层循环——外层由程序按步骤状态调度，内层由模型在步骤内自由决策，两层只在步骤边界交接。

**旧选择的理由：** 步骤边界给了程序一个确定的介入点：可以在这里更新计划、清理上下文、发布进度、判断是否继续。单循环方案里没有这样的锚点，进度完全由模型的叙述决定。

**放弃的原因：** 这个锚点的代价在 W0 基线里很具体：每轮多一次规划调用，规划器与执行器各持一份上下文；执行器必须输出步骤 JSON，解析失败即终止，假完成守卫与附件声明都依附在这个结构上；执行器能看到原始目标，常在一步内做完后续工作，计划随之塌缩；计划更新只在存在未结束步骤时合并。同一批 E1–E6 任务上，单循环的模型调用从 55 次降到 20 次、prompt tokens 从约 28.5 万降到约 9.3 万，检查结论相同（W1 评测在 Git 提交 `2e68aa3` 的 `w1-2026-09-28-9faa304`）。

**代价：** 进度只能由模型维护，清单与实际执行可能不一致，程序没有替代的完成判定；步骤边界上的上下文清理改为在每次新用户消息时进行，一次运行内不清理，直到 W2 引入容量检查与压缩。

**依据：** [W1 子计划](plan/w1-agent-loop.md)与评测报告；课程第 07 章给出了两种方案的完整对照（课程正文仍以双循环为准）。

## 模型响应先流式组装，再按完整结果执行

**问题：** 模型响应可能长达数十秒，期间页面没有内容。

**选择（W6 起）：** 默认 `stream=True`，并请求 `stream_options.include_usage`。适配层按 `choices[0].delta` 组装出与整包响应相同的 message、`finish_reason` 与 usage，文本增量另经通知推给当前连接。工具调用仍等组装完成、校验通过后才执行。`llm_config.streaming` 为 false 时保留整包路径。

**原先不走流式的理由（执行链仍遵守的部分）：** 整包响应是一次完整的 JSON，工具调用的边界清晰。流式要维护未完成状态、区分连接断开与协议结束、按 index 拼接 `tool_calls` 分片，复杂度集中在最容易出错的位置。因此循环只消费组装后的完整结果：没有 `finish_reason` 时按可重试错误处理，不执行任何调用，半截文本不进入模型历史。推理分片写入最终消息的 `reasoning_content`，不推给页面，也不当作首字。

**代价：** 文本增量不落库。刷新、断线或通知丢失后，页面只能看到已经保存的完整内容。非流式路径的首字延迟仍为空，等于整次响应耗时。供应商不返回 usage 时，生成速度只能按字符估算。2026-09-14 文件任务的记录及时间口径更正见[背景中的运行观察](background/README.md#能力评估的真实任务记录)；原报告“约 14 秒”的数字与括注时刻矛盾，不作为有效延迟基准。

**依据：** [W6 子计划](plan/w6-streaming.md)。会话页在生成期间按增量显示临时文本，状态条标出字符估算速度；轮次结束后开发者视图按用量与首字延迟显示速度，并在有推理 token 时从分子扣除。

## 沙箱按会话准备，不按任务创建

**问题：** 工具动作需要一个文件、进程、浏览器都可用的环境。

**选择：** 独立对话按会话标识查找或创建容器；项目工作文件由平台持久化，项目运行终态后停止容器并确认旧写入者静止。

**放弃：** 每个任务一个一次性环境，结束即回收。

**理由：** 同一会话内的多轮任务能看到彼此的工作文件，符合"继续上次的工作"这一使用预期；反复创建容器的启动开销也高。

**代价：** 独立对话环境靠 TTL 或显式销毁回收；项目跨运行不保证浏览器和终端状态延续。容器不构成租户隔离；统一准备链路仍会为纯文本任务启动浏览器。

## MCP 与 A2A 接进同一个工具层

**问题：** 外部工具和远程 Agent 都需要参与本地任务。

**选择：** 两者都实现为工具，接进现有的工具契约与分发路径，主执行流程不变。

**放弃：** 为远程 Agent 设计独立的协作流程，例如把远程 Task 的状态提升为本地计划步骤。

**理由：** 保持一个执行链，模型只需要理解"调用工具"这一种交互；协议差异收敛在适配层内部。

**代价：** A2A 的 Task 语义被压扁成一次工具调用的返回值——远程的 `input_required`、`auth_required` 无法接到本地的等待续接机制上，只能按失败返回；远程状态变化也不会逐条投影为本地进度事件。远程产物不会自动成为本地可下载附件。

**依据：** 课程第 14、15 章对比了两种协议的契约差异。

## 等待用户时退出重建，而不是挂起协程

**问题：** Agent 提问后需要等待用户回复，可能等很久。

**选择：** 保存等待状态并结束当前运行，回复到来时重新组装运行器继续。

**放弃：** 让协程阻塞在等待上，回复到来时唤醒。

**理由：** 挂起会长期占用进程内资源，而且一旦进程重启，调用栈上的状态全部丢失。退出重建让等待期间不依赖任何进程内状态。

**代价：** "继续"必须能完全从已保存的状态重建，只存在于调用栈里的信息会丢失。W1 起，回复作为提问调用的配对结果接回上下文，同批次未执行的调用在续接时补为"未执行"。W7.2 起，工具策略的 ask 也走同一套退出重建；API 重启不续接审批，见下条。

**依据：** 课程第 08 章。

## 停止写入取消终态，并终止本次运行的 Shell 会话

**问题：** 用户请求停止后，需要能与正常结束区分的终态，并且沙箱里已经启动的命令不应继续跑。

**选择（W3 起，W7.2 区分两种等待）：** 运行置为 `cancelled`（原因 `user_stop`），与完成、失败、中断分开。同一事务写入终态事件后取消执行协程，再逐个终止本次运行登记过的 Shell 会话；结果记入 `cleanup` 事件，失败不改终态。API 重启时，启动扫描把仍为 `running` 的运行，以及正在等待审批的运行，置为 `interrupted`（`api_restart`）。等待提问的 `waiting` 保持，回复后继续同一个运行。等待审批被中断时同时写 `approval(expired)`，挂起的调用补为未执行，不在重启后续接。不回滚已写入的文件；项目环境另由终态收尾停止。

**放弃：** 取消与正常结束共用 `completed`，并且不向沙箱进程传播。

**旧选择的理由：** 实现简单，页面不需要额外分支。

**放弃的原因：** 状态字段无法回答“是跑完了还是被叫停了”；只取消协程也停不掉已经在沙箱里运行的命令。W0 与 W1 的 E4 都停在 `completed`，停止后标记仍在增长。

**代价：** 文件仍不回滚，独立对话沙箱仍按会话复用，远程 A2A 只沿用已有的取消尝试且不保证成功。Shell 会话 ID 只登记在当前进程，崩溃或停止请求落到别的进程时，启动扫描或下一次消息只会把运行标成 `interrupted`，不会去终止当时的进程。多实例下的执行所有权仍未定义。判断目标是否达成，仍然不能只看终态。

**依据：** [W3 子计划](plan/w3-run-events.md)与 Git 提交 `2e68aa3` 中的 W3 评测 `w3-2026-09-28-8511bdf`（E4 为 `cancelled` / `user_stop`，停止后标记不再增长）；课程第 08 章仍按旧选择展开。

## 托管项目文件与透明记忆

**选择：** 项目按 id 管理平台文件副本，沙箱挂命名卷子路径；上传下载、运行前快照和整项目恢复提供文件保护。项目说明、笔记与有来源的对话摘要在新运行冻结并注入，笔记可编辑且按版本审计。

**放弃：** Git 工作台、宿主机目录登记、本地回写和隐式跨会话记忆。

**理由：** 项目用于保存复杂任务的材料、背景与结果；默认部署不要求用户配置目录、Git 身份或远端凭据。文件所有权与旧写入者收尾必须由平台管理。

**代价：** 上传是副本，用户需下载结果；快照仅保护项目文件，不是完整历史，也不回滚笔记与会话。运行前超限可降级跳过保护。项目没有删除入口，只有归档与快照清理；工作区内 Agent 写入没有硬配额，不能将上传限制当作运行写入限额。
