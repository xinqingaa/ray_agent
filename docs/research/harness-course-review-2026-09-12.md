# Harness 工程课程评审

评审日期：2026-09-12。代码与课程基线：RayAgent `6422e9f`，本次修订前工作区干净；教学参照为本机 learn-codex `fed06fa`。本文是此次审查的分析快照；课程正文已于 2026-09 冻结，后续不再维护制作进度文件。

## 结论与范围

RayAgent 适合作为 Harness 机制与工程设计教程的实践载体。16 章已经覆盖模型交互、工具、循环、上下文、规划、任务控制、状态、事件、执行环境、产物、协议与评估，暂不需要为了追求完整而增加大量章节或替换主循环。

主要差距是：若读者学完要能判断“这个 Harness 在什么条件下可靠、改动是否有效”，教材还需要把运行边界、失败实验和对照评估讲得更具体。下文记录的是 2026-09-12 审查时的发现；课程已于随后完成并冻结，其中若干建议已落实于正文。

本次读取根 README、PLAN、AGENTS、架构与工作区调研，课程目录与创作约定，第 01–07 章相关正文以及后续骨架；静态追踪规划、步骤执行、基础循环、任务注册与 token 用量路径。外部资料实际获取范围见末节。没有重跑 Compose、真实模型、协议测试或故障注入；既有验收记录是引用，不是本次重新验证。

## 按优先级排列的发现

### P1：把步骤职责和行动权限混在一起，会误导控制设计

原第 07 章比较小节写“执行器被关在当前步骤里”“外层不容易跳步、丢步”，同章却已经记录第一步完成读取、后续待办被移除的真实案例。执行器输入包含原始目标和步骤描述；[步骤执行](../../ray_agent/api/app/domain/services/agents/react.py)没有据此建立独立的每步工具权限。[计划更新](../../ray_agent/api/app/domain/services/agents/planner.py)保留已结束前缀，再替换剩余列表，也不是检查全部用户要求都得到满足的验收器。

读者若把步骤标题当成强制边界，可能在需要审批或严格顺序的业务中仅依赖提示词。应分别解释调度边界、工具授权和目标验证。本次已修正第 07 章这些绝对化表达，并保留“双循环与同循环计划工具”的原有比较主题。

原文“Codex 的循环和进度都由 Agent 决定”也过强。官方 App Server 提供计划事件、取消、运行中追加输入与审批；计划展示本身不能证明产品的全部内部调度结构。现改为比较计划是否直接参与步骤调度，并明确程序仍负责运行边界。

### P1：安全主题已有归属，但尚未形成可推演的信任边界

[第 08 章](../../lessons/08-task-execution-and-control.md)已有授权与暂停，[第 11 章](../../lessons/11-sandbox-and-execution-environment.md)已有路径、网络和隔离，[第 05 章](../../lessons/05-context-and-memory.md)也已提醒网页资料不能升级为指令。缺口不是没有提到安全，而是这些内容还没有组合成一条具体判断链。

建议用“网页要求读取无关文件并发送到外部地址”的教学案例，逐段解释不可信内容怎样进入 Context、谁决定授权范围、路径和网络限制在哪里执行、被拒绝时返回什么、审批结果如何绑定具体动作。人工同意不能自动替代环境限制，模型认为可以也不能替代授权。用临时文件和本地接收端即可研究机制，无需真实敏感数据。

教学验收应让读者能指出每一道检查的实施位置和绕过条件，并说明 RayAgent 当前实际实现了哪些。多用户部署还需明确身份、会话、文件和执行环境的归属；目前不能从“每项任务有沙箱”直接推出完整租户隔离。

### P1：有结果验证意识，但还缺少可复现的改动评估方法

[第 16 章](../../lessons/16-reliability-and-verification.md)已经提出任务样本、重复运行、失败分类；[PLAN 的完成标准](../../PLAN.md#阶段-3lessons-与系统学习)也要求用证据评价执行。现在的骨架没有具体说明怎样固定输入和环境、定义评分、比较两个版本、排除评分器错误，读者仍可能只能重复跑演示。

建议先建立少量有明确目标的案例：文件内容交付、依据记录生成报告、工具失败后纠正、取消长操作、上下文清理后继续。每个案例说明初始文件、允许的行动、预算、可检查产物与失败条件；对版本比较保留模型标识、提示与工具版本、参数、初始环境及每次运行结果。用程序检查可判定的产物，开放内容才使用明确评分规则与人工校准。

不要把固定工具顺序当成全部任务的正确答案。第 06 章三步缩为一步就是很好的反例：只要满足授权与结果条件，另一条有效轨迹也可能正确。机制实验可以固定模型响应以核对程序分支；任务评估则应允许合理路径变化。

产品已有 [UsageEvent](../../ray_agent/api/app/domain/models/event.py)、[用量累计](../../ray_agent/api/app/domain/models/token_usage.py)和模型响应 usage 解析。可以从这里观察规划与执行的 token 代价，但用量不是执行预算的强制限制，也不是货币成本；服务端未提供用量不能算作零。尚未验证的真实 token 观察继续保持 `unverified`。

### P2：恢复、取消和并发需要按故障窗口解释保证

[第 09 章](../../lessons/09-state-and-persistence.md)已正确区分历史回放与恢复，并提出“写完文件但尚未读取时中断”。还应把中断位置细化：动作未发出、动作已生效但结果未保存、结果已保存但页面未收到。这三个窗口决定能否重试、是否需要查询结果、是否存在重复副作用。

[RedisStreamTask](../../ray_agent/api/app/infrastructure/external/task/redis_stream_task.py)的注册表和执行实例位于进程内，Redis Stream 的存在不代表有跨进程接管；`cancel()` 发出取消请求，也不等于外部动作已回滚。这些是很适合本项目的教学入口，而不是必须立刻改造成分布式调度器的理由。

第 08、09、16 章应共同交代：取消请求与取消确认、长进程退出与清理、幂等键与业务副作用、同会话重复提交与并发所有权。实际没有提供的保证要明确写出；故障实验需检查持久化状态、实际文件或远程结果、后台进程和客户端事件，不能只看一个终态字段。

### P2：观测与配置的素材还不足以支撑复现和归因

[第 10 章](../../lessons/10-events-and-streaming.md)已承诺核对步骤、工具、产物及耗时关联；第 16 章的“资源消耗按实际可取得记录观察”也需要承接这些已有入口。（课程冻结后，上述缺口已在正文中标注，不再单独维护制作进度。）

建议沿一次任务建立“用户请求 → 计划 → 模型调用 → 工具调用 → 产物”的关联记录，并指出当前哪些 ID 可用、哪些耗时或失败位置缺失。再用同一任务比较一次提示或工具说明变更，记录模型、参数、工具 schema、提示内容版本和沙箱初始条件。这样才能区分模型波动、上下文遗漏、工具失败与系统控制错误。

配置、提示和工具版本可放在第 02、03、10、16 章的既有范围内，不需要另造配置平台。记录原始请求时还应讨论凭据与用户数据的脱敏、访问范围和保留期限。

### P2：上游写作约定存在直接冲突

[lessons/AGENTS.md 的写作约定](../../lessons/AGENTS.md#写作约定)（当时名为「制作约定」）要求“每个章节……不放源码链接或代码片段”，同一句又要求遵循 write-lessons。[write-lessons](../../skills/write-lessons/SKILL.md#use-examples-and-code-deliberately)则允许在实现影响行为时放短代码，并要求精确控制流使用简化 Python/TS。已制作的第 02–04、07 章也确实包含代码。

这会让后续作者无法稳定判断“代码应删掉，还是为了讲清控制流保留”。建议把课程特有约束收窄为“开头先用任务与自然语言建立问题，正文不以源码导览代替机制讲解；短代码与简化模型按 write-lessons 使用”。这是对上游规则的修改建议，本次保留原规则供作者决定，不用一次评审直接重写长期规范。

## 现有章节如何承接

| 章节 | 建议补足的工程问题 | 可交付的学习证据 |
|---|---|---|
| 02、03 | 模型契约、工具描述、配置变化如何影响行为 | 固定输入对照；区分解析失败、工具失败与模型选择错误 |
| 05 | 压缩后哪些事实还在，哪些需要重取；按需加载指令或技能的代价 | 压缩前后相同问题的证据对照；不强制开发记忆系统 |
| 07 | 计划更新与下一步选择的真实关系 | 保留第二步的确定性夹具，以及独立标记的真实模型观察 |
| 08、09 | 取消、等待、恢复、重复提交的边界 | 故障窗口表与状态、资源、副作用的检查结果 |
| 10 | 如何关联一次行动并解释时间与用量 | 一条可追踪记录；清楚列出缺失字段和不能得出的结论 |
| 11、13、14 | 文件、网络、网页和外部工具之间的信任边界 | 越界访问或不可信内容案例，核对拒绝与反馈位置 |
| 12、17 | 产物何时成为可交付版本，跨会话如何复用 | 文件内容与来源核对；中断、交接后产物仍可定位 |
| 15 | 远程协作的任务边界、取消传播和结果可信度 | 远程终态与本地结果对应；区分 A2A 接入和本地多 Agent 调度 |
| 16 | 相同任务下的质量、延迟、用量和失败比较 | 小型任务集、评分规则、重复运行记录与改动前后比较 |

这张表是本次评审的建议快照，不是第二份制作计划。自动化调度、复杂多 Agent 团队、框架迁移、完整记忆平台可以作为未来比较材料；它们不应挤占控制、恢复、安全和评估这些基础内容。复杂机制的价值应来自可观察的任务收益。
