**发现与判断**

1. **部署一致性需要收口。** 全部 204 个 API Python 源文件对比，有 5 个与 HEAD 不同：计划提醒、计划工具描述、搜索工具描述、中英文系统提示。差异均为描述/提示文字，执行循环与计划检查逻辑相同。运行中仍保留“修复后复检一次即可”“改动后另存为新版本”等较硬措辞，搜索时间过滤也仍为旧规则。因此不能把本次端口测试说成最新“提示词减负”版本验收。证据：[源码差异](evidence/project-closeout-review-2026-10-11/deployment.diff)、[核对范围](evidence/project-closeout-review-2026-10-11/api-parity-all.json)。

2. **计划入口可用，过程进度仍不可靠。** 第一次执行先做了 8 次非计划工具调用，约 36.7 秒后才更新计划，直接把前两项补记为完成，此时已经进入浏览器自检。追加改版先做了 9 次非计划工具调用，约 42.7 秒后才 reset 新计划，第一项建立时就已完成。第一次执行的重建请求能看到“计划核对”提醒，说明提醒链路在起作用，但不能保证模型在阶段切换时主动更新。最终两个运行均补齐清单，第二次确实使用新 plan_id，未把旧清单一直当作本次进度。该问题主要影响过程可理解性，不是工具执行失败。当前 UI 在计划尚未归属本次运行时隐藏计划条，会进一步放大前半程缺少计划的感受。建议把“已确认计划开始执行”的归属/展示和及时更新作为一个小范围维护项；不要再依靠堆积更强硬的通用提示词。

3. **内容质量不能由完成状态担保。** HTML、题目解析和最终答复均把 1405–1433 年七次下西洋归于明成祖在位期间；第七次在明宣宗宣德年间，因此相关事实和题目表述需要订正。界面交互通过没有发现这个错误。简单周报还把“完成报表导出”扩写成“开发并交付使用”，超出了原始材料。这些属于生成内容问题，本次未改产品或代模型纠正。面向教学交付，事实核查必须是独立验收项；不能用计划全完成或浏览器自检替代。

4. **效率可继续维护，但不构成重开项目的理由。** 两版小样分别使用 20/16 次模型请求、24/26 次工具调用，首个文件直到自检结束才交付；早交付和批量检查原则并未稳定贯彻。过程中有不少逐项浏览器操作，但约一分钟内均收敛，没有重现此前百轮耗尽预算、文件未交付的故障。本轮没有特意触发预算末段，因此不能宣布历史长任务问题已被真实复测关闭。累计输入 token 含重复历史且大部分命中缓存，不能直接当作账单费用。

5. **记录口径有少量需要澄清的地方。** 运行预算计划开头写“真实模型复测由用户执行，结果见文末”，文末仍写未做真实模型复测、未重建；这份文档本身不足以确认该复测是否发生。近期图片规则与底部统计也明确有“只构建部署、未重跑行为”的边界。本轮仅补到了上述六次运行所覆盖的路径，未补验图片、长上下文或真实审批取消。

**建议的收尾范围**

- 作为教学与实验工程：可以结束成组开发，保留现有能力边界并进入维护；课程升级单独排期。
- 作为本地个人工具：已具备真实使用价值，可持续使用；文件和关键事实仍需用户核对。
- 正式标记当前版本验收完成前：先让部署与选定提交一致，再对“确认计划执行 + 同会话追加改版”做一次小回归，明确计划状态的表现。不需要重跑 W0–W11 全套。
- 若目标变成长期无人值守、多用户公网或高风险自动执行，则鉴权、任务恢复/归属、出站权限、幂等与成果校验属于新的产品阶段，不能纳入本次收尾承诺。
