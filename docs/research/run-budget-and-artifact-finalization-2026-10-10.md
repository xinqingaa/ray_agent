# 任务请求预算与异常结束成果交付分析

核对日期：2026-10-10。代码基线：`01674e84ffa017dbf1f32c9558b3a028b1479cc6`。状态：待审查的调研与方案建议，尚未授权产品实施。

本次明朝 HTML 课件任务在生成文件并完成多轮检查后，因达到 100 次模型请求上限结束，用户没有收到附件。主要问题是执行范围与“小样评估”的要求不匹配，缺少预算感知和及时收尾，异常出口又没有保存并展示已有成果的统一机制。单纯提高请求上限不能解决这些问题。

## 2. 对四个问题的判断

### 2.1 这个任务是否需要 100 次请求

对于“简单 HTML 小样供评估，图片可占位”的范围，100 次明显偏多。预期流程应是确定最小评估范围、生成完整可打开文件、检查关键操作、修复阻碍评估的问题并交付。真实图片和进一步精修不应阻塞首版。

8–20 次请求可作为这类小样的初始工作估计和评测假设，但尚未在同一模型与工具条件下验证，不能作为性能承诺或平台比较结论。实际预算取决于内容范围、环境准备、素材要求和生成质量。

本次有证据支持“已有成果后的收敛与交付失效”。并不能从单个失败案例证明模型能力是唯一原因；也不能把另一个 Agent 的预计请求数当作同条件实测。模型、提示词和 Harness 应分别评估。

### 2.2 是否应放宽请求上限

应保留可配置的保护上限，但不建议先把默认值从 100 普遍提高到 300。当前上限承担失控保护，却没有提前引导收尾。扩大额度可能让同一精修行为继续更久。

建议先补预算感知、阶段交付和异常成果保存，再按任务复杂度提供更高预算。复杂工程与调研可能合理地超过 100 次，简单小样则应尽早交付。请求数是粗粒度保护，后续结合时间、token 或费用以及成果进展，不能仅按次数评价效率。

外部产品的公开限制及其适用范围见第 4 节，不能从公开文档推断所有内部保护策略。

### 2.3 是否应优化内置提示词

应优化，重点是范围取舍、有限验证、降级策略和及时交付，而非不断追加宽泛的“努力完成”要求。当前提示词已经要求交付、计划更新和证据充分后结束，这次仍未落实；只改提示词不能为模型不可用、预算耗尽、停止或进程退出提供可靠兜底。

### 2.4 失败或停止时是否应输出已有工作

应作为产品契约：运行未完成与成果不可用是两个不同结论。已有可用成果应能被保存、下载和说明，同时保留真实失败或停止原因。

尽力兜底不意味着保证每次都有文件。文件尚未生成、已损坏、沙箱已消失或存储不可用时，应报告具体缺口；有可用版本时，不能因后续精修失败而只显示通用错误。

## 3. 当前实现的缺口

### 3.1 范围与验证没有收敛策略

**观察事实：** 小样任务扩展为 16 页图文课件，素材阶段占 36 次工具调用；初次构建后又发生 60 次调用。发现溢出后确有有效修复，因此不能把所有检查认定为无用。

**影响判断：** 执行没有稳定地区分影响使用的问题与可选审美改进。用户需要的是可评估成果，Agent 却不断提高自己的交付标准。计划长期不更新，也不能帮助用户理解当前真实阶段。

**建议：** 明确首版验收条件，关键行为验证后交付；可选改进随成果说明。阶段转换时更新计划，不按每个工具调用机械更新。

### 3.2 请求预算对模型不可见

**源码事实：** 默认 `max_iterations=100`。循环请求前及模型重试前检查计数，达到上限直接产出错误。没有把剩余请求预算作为动态执行信号提供给模型。

**影响判断：** 模型无法准确知道自己还剩多少次请求。普通最终回答也需要请求机会，预算不能只分配给业务工具决策。

**建议：** 引入预算信号与收尾阶段；普通请求、重试、自动摘要请求统一核算。当前摘要调用后才累加尝试数，不能仅在普通请求入口预留预算，就声称全部模型请求严格遵守总上限。

### 3.3 结束一致性反馈只覆盖主动结束

**源码事实：** 模型回复不含工具调用时，普通模式检查明确交付需求、交付失败和已修改计划中的未完成条目，最多追加一次反馈。达到请求上限时直接走错误分支，不经过这道反馈。

**影响：** 模型一直调用工具，就不会触发主动结束检查；异常结束又没有成果收尾。已有检查不能保证本次这种运行会交付。

### 3.4 交付需求识别过窄

**源码事实：** 当前交付必需标记通过“交付或下载”与“文件”等词的组合识别。“做一份简单版 HTML”没有直接命中这条规则。系统提示词仍要求文件任务交付，但程序检查的覆盖不足。

**建议：** 用明确的成果契约与记录支撑交付判断。可改善意图识别，但不能继续仅靠关键词扩充承担通用成果验收。

### 3.5 文件写入与持久化交付分离

**源码事实：** 文件或 Shell 写入不会自动交付。`deliver_files` 才核对文件、上传存储并关联会话；成功交付后会发出带附件的消息。已有交付工具支持部分成功和逐项失败说明。

**影响：** 沙箱里有 HTML 不等于用户能下载。当前异常出口没有统一的已登记成果清单与补存流程。项目文件协调已有独立保护机制，但本次是独立对话，不能把项目文件保护等同于会话成果交付。

### 3.6 停止与重启不能简单追加普通交付

**源码事实：** 用户停止先写入取消终态，再取消执行协程并终止登记的 Shell 进程。账本拒绝终态后的普通迟到事件，现有终态后写入例外用于清理记录。启动扫描将活动运行标为中断，不代表恢复业务执行。

**建议：** 设计明确、幂等的收尾记录及归属规则，不能在通用异常分支随意调用交付工具或全局放开终态事件写入。强制进程退出不能依赖 `finally` 保存成果，必须有运行期间的持久化版本。

## 5. 建议的目标契约

### 5.1 区分运行终态与成果状态

保留 `completed`、`failed`、`cancelled`、`interrupted` 的现有运行含义，不因为保存了文件就将失败改为成功。成果另外记录生成、保存、交付和验证状态。

本次期望的结束信息可以是：

> 本次运行因请求预算耗尽而结束。已保存明朝历史 HTML 样例，可下载。生成记录为 16 页，已检查翻页、时间轴和小测；完整教学内容审核尚未完成。

这段说明只有在保存成功后才能使用。补存失败时应改为“生成记录存在，保存失败”，说明原因并提供仍可用的旧版本，不能展示无效下载入口。

第一阶段不必新增一个笼统的 `partial_success` 运行终态；它会混淆执行结束原因与交付结果。可以先用现有终态加成果清单和结束摘要表达。

### 5.2 为可交付成果建立持久记录

建议记录会话与运行归属、成果名称和类型、源路径、版本或内容哈希、草稿或可交付状态、实际验证记录、持久化存储引用、交付结果及错误。具体 schema 在获授权计划中确定，不将本表视为既定数据库迁移。

成果识别采用指定产物目录与显式登记相结合。文件工具可以提供结构化登记入口；Shell 生成文件需要约定输出目录或登记动作。路径只登记后仍须实际核对存在性、读取范围与文件完整性。助手自然语言、Shell 输出字符串和目录里任意文件都不能自动作为可信成果清单。

不扫描整个沙箱并打包上传；脚本、日志、临时图片、原始素材和用户材料不能默认成为交付成果。复用现有路径与资源归属校验，不为兜底开绕过工具授权的入口。

### 5.3 保存可用版本并及时交付

首次可用版本完成必要检查后，保存到持久化存储并交付；继续精修时保留此前可用版本。保存候选版本与展示给用户可分开，不必每次小改都新增一张附件卡。

保存与交付应有幂等键，结合运行、成果身份及版本判断重复；内容相同的重复收尾不重复上传。新版本失败不能先删除旧记录。可用版本选择基于已保存及实际检查记录，不凭模型声称“最新版最好”。

持久化成本随文件大小和修订次数增加。首批先保存首次可用版和关键修订版，不为每个写入动作生成永久副本；版本保留与现有数据清理规则须一起核对。

## 6. 预算与收尾方案

### 6.1 建议的预算阶段

以下是在总上限仍为 100 时的试验初值，不是已验证最佳配置：

| 阶段 | 建议触发点 | 执行策略 |
|---|---|---|
| 正常执行 | 前段预算 | 完成用户目标，阶段成果及时保存与交付 |
| 提醒收敛 | 约 70 次 | 提供已用与剩余预算、已登记成果，重新判断完成条件 |
| 优先交付 | 约 85 次 | 停止可选扩展，解决阻碍交付的必要问题 |
| 受限收尾 | 最后约 10 次 | 只核对、保存、交付和说明，不增加新功能 |
| 总预算耗尽 | 达到总上限 | 不再发模型请求；程序依据持久记录兜底 |

提醒与预留可以按上限比例计算，同时设置合理的最小收尾空间；低预算任务不能机械扣掉 10 次。收尾预算包含最终回答所需请求、允许的重试或摘要，不能在 100 次之外另开无限额“最后一次”。

预算动态信号应由 Harness 提供，与事件和快照保持一致；不要求模型自己从历史数工具调用，也不要求用户为普通任务填写内部次数。更高预算可作为明确的任务选项，自动延期不属于本次推荐的默认行为。

### 6.2 收尾必须由程序限制

只提醒“请尽快结束”仍允许精修继续。进入收尾后，程序应限制允许的动作：读取登记成果和已有状态、有限交付、计划说明与最终摘要；禁止新素材检索、新依赖安装和新增功能。

不能将整个 Shell 或 `browser_console_exec` 工具集视为安全收尾白名单：它们能执行任意写操作。需要读文件、计算哈希或核对结构时，优先由成果服务执行定向检查。必须改文件才能交付时，应有可控的必要修复路径，否则交付已保存草稿并说明缺口，不把“必要修复”变成新的无限执行阶段。

同类问题多轮不收敛可先发策略提醒，但不要用简单的工具名重复次数直接强制终止：合理的分页、等待和修订也会重复调用。首批依靠预算、成果里程碑和提示词，通用停滞检测待有评测证据再引入。

### 6.3 区分不同终止原因

| 原因 | 模型层处理 | 程序兜底 |
|---|---|---|
| 接近预算上限 | 受限收尾，停止可选工作 | 核对并保存已有成果 |
| 预算已耗尽 | 不再调用模型 | 根据登记和存储事实生成摘要 |
| 模型接口不可用 | 不依赖新摘要请求 | 保留已有成果，说明接口错误 |
| 上下文无法继续 | 不强行携带完整历史再总结 | 用成果记录和验证记录说明进展 |
| 用户停止 | 立即停止业务执行，不新增模型或外部 Agent 调用 | 终止写入者后，有限保存已登记成果，展示已有版本 |
| API 强制退出 | 无法保证执行收尾代码 | 重启后读取检查点与成果记录，按归属尽力恢复 |
| 上传或存储失败 | 可用预算内只补失败项 | 保留旧版，标记具体失败，避免无限重试 |

用户停止接口不应长时间等待文件上传。可先完成取消，再让独立且有界的收尾处理保存，界面显示保存状态；是否需要这一异步状态和期限，在审查时确定。其目标是保留已有文件，不是延续用户要求停止的业务执行。

### 6.4 处理终态、并发和恢复

收尾应有独立身份、运行归属、幂等与有限重试，允许写入专门的成果收尾记录，而不放开所有终态后的业务事件。原终态和原因不可被收尾改写。

保存前确认旧业务写入者已停止，或读取此前固定版本，避免边写边上传。新运行开始后，旧运行收尾只能处理自己的固定版本，不能读取同路径的新文件并冒充旧成果。持久化成果与事件关联应有可恢复的事务边界，上传成功但关联失败不能盲目重复上传。

进程重启恢复采用成果清单与存储检查点，不自动恢复 Shell、浏览器操作或外部副作用。数据库、存储、沙箱同时不可达时无法保证即时交付；应记录可恢复状态，在资源恢复后有限处理并说明边界。

## 7. 提示词修改建议

以下文本是建议内容，尚未写入产品提示词；实施时需核对中英文版本、运行快照以及计划模式的适用范围。

### 7.1 范围与降级

> 用户要求简单版、草稿或评估样例时，优先完成足以支持评估的成果，不自行扩展为完整方案。运行中收到的范围调整应改变后续执行，已有投入不构成继续扩展的理由。可选素材获取困难时，采用用户允许的占位、简化图示或文字说明，不让素材阻塞主要交付。

### 7.2 验证与收敛

> 修复影响使用、主要内容正确性或明确验收条件的问题。成果已经可评估时，停止仅涉及审美偏好的精修，并随成果说明可改进部分。验证应针对关键行为；同类问题持续不收敛时调整方法或交付可用版本，不无限重复修订。跨阶段推进时更新计划。

不建议把“最多两次检查”写成所有任务的全局规则。教学小样、复杂应用和协议修改需要不同验证深度。

### 7.3 阶段交付与预算收尾

> 文件达到可用阶段后及时保存和交付，不必等待所有可选精修结束。收到平台预算收尾信号时，停止新增功能与可选优化，核对并交付已有成果，说明实际验证内容和未完成事项。部分成果可以交付，但不能称为全部完成。

保留“路径不算交付”“工具失败先读结果”等现有规则。通用提示词不写死 100 或固定预留次数，由运行控制提供真实预算。计划模式仍只输出方案，不因这条规则授权文件写入或交付。

## 8. 推荐实施顺序与范围取舍

| 顺序 | 建议工作 | 完成条件 |
|---|---|---|
| 第一批 | 明确成果登记、首次可用版保存与阶段交付；优化范围和收敛提示词 | 后续失败不会让此前可用成果失去下载入口 |
| 第二批 | 预算动态信号、受限收尾、统一异常摘要和程序补存 | 上限、模型错误与用户停止均有真实成果和缺口说明 |
| 第三批 | 重启恢复、终态后收尾幂等、停止与新运行并发验证 | 不重复交付，不串用版本，不继续旧业务执行 |
| 后续调优 | 同条件评测，调整默认值及复杂任务预算 | 用完成率、交付率与成本确定阈值，而非只追求少请求 |

以上是建议组织顺序，不是已授权工作包。第一批也不能宣称具备任意故障下恢复能力；完整终止契约需要后续批次闭合。正式计划应将数据结构、事件、前端、资源所有权及实际验收组成完整范围，不能仅完成提示词就宣布问题解决。

首批不建议做通用任务成功判定器、自动提高预算、复杂停滞评分系统、统一成本预测平台、框架迁移或课程更新。可以复用现有交付服务、部分成功结果、事件账本和项目协调机制，但独立会话成果与项目快照须分别核对。

| 备选做法 | 优点 | 缺点与判断 |
|---|---|---|
| 只提高上限 | 改动小，给复杂任务更多空间 | 精修失控和成果丢失仍存在，不作为本次主方案 |
| 只改提示词 | 易试验，可改善范围选择 | 无法兜底模型故障、强制停止和进程退出，作为配套措施 |
| 每次写文件自动交付 | 容易保留过程版本 | 临时文件误交付、附件噪声和存储成本高，不推荐 |
| 失败后扫描整个沙箱 | 可能找到漏登记文件 | 归属、版本和交付意图不可靠，不推荐 |
| 明确成果登记加阶段保存 | 可追踪、可恢复、适合程序兜底 | 需要跨模块契约与存储治理，推荐 |

## 9. 验证与评测建议

### 9.1 确定性行为验证

用脚本化模型覆盖预算临界点、最终回答预留、重试与摘要计数、收尾阶段禁止扩展，以及模型完全不可用时的程序摘要。测试应验证外部行为和状态一致性，不镜像提示词文本或内部实现。

用真实临时数据库和文件存储验证：成果登记与会话关联、固定版本保存、重复收尾、部分上传失败、上传成功但关联失败、停止与新运行竞争，以及重启后的恢复。沿用服务指南中的独立测试库要求，不能指向业务库。

### 9.2 最小验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 简单 HTML 小样 | 文件可打开，关键操作正常，用户可下载 |
| 已生成成果后耗尽预算 | 保留 `max_iterations` 原因，同时提供已保存成果和缺口说明 |
| 第一次生成后模型接口失败 | 无新模型请求也能展示成果，不声称全部完成 |
| 用户在精修时停止 | 停止业务执行，保留已有版本，不继续搜索或修改 |
| 强制终止 API 后重启 | 读回持久成果，不假装自动恢复全部执行 |
| 新版本损坏或上传失败 | 旧可用版本仍可获取，新版本错误清晰 |
| 收尾重试或重复恢复 | 不重复关联，不把新运行文件交给旧运行 |
| 无成果或源文件不存在 | 说明未生成或无法取回，不给无效链接 |

### 9.3 真实模型评测

先使用相同输入、模型、思考档位、工具配置和干净环境，对小样及复杂任务分别多次运行；记录差异而不凭一次成功宣布优化有效。跨模型比较另设同条件组，不将提示词变化、预算变化和模型变化混为一个原因。

核心指标是首次可用成果时间、首次持久化与交付时间、交付前请求数、最终完成率、异常结束成果可获取比例、累计 token 与缓存，以及关键质量检查结果。先交付一个不可用文件不算达标。

小样约 20 次内交付可以作为待校准目标，不能牺牲正确性来满足次数。必须同时观察首版是否满足评估需要、用户降级要求是否落实，以及失败时是否保住已有工作。

本次没有运行上述测试或真实模型评测；本节定义未来获授权实施的验证范围。

## 10. 审查时需要确定的选择

1. 是否接受运行失败或停止时仍展示阶段成果，并保留原终态与原因。
2. 首次可用版保存后是否立即交付，后续修订采用有限版本更新而不是每次新增附件。
3. 是否先保持默认总上限 100，试验提前提醒和约 10 次收尾预留，再依据评测调参。
4. 成果登记采用指定产物目录与显式登记结合，首批是否覆盖文件工具与 Shell 两种生成路径。
5. 用户停止后是否允许有界的文件保存收尾；它不调用模型、不继续业务动作，界面可显示保存状态。
6. 首批是否将重启恢复纳入完整验收；若分期，必须明确第一期尚不能保证进程崩溃后的补存。

获授权后另建实施计划，记录具体范围、契约和完成条件；不在本调研快照追加实施日志，不将建议写为当前能力。当前产品事实仍以[Harness 工程](../harness.md)、[能力与边界](../capabilities.md)和源码为准。
