# 浏览器截图机制盘点与按需截图建议

> 历史分析快照：正文描述 2026-10-08 调研时的实现与建议，后续优化已落地。当前范围与关键结果见[阶段收尾与维护](../plan/README.md)和[综合验证](../plan/evidence/browser-visual-resources-2026-10-08.md)；以下“未实施”“待批准”保留当时语境。


核对日期：2026-10-08。代码基线：`0ad50a1df56c5087bdf9520f0435a3d510f668f0`。范围：RayAgent 内置浏览器工具、运行器展示补全、文件存储与工作台；不涉及本次协助调研所用工具的截图规则。

当前每次浏览器工具完成后自动截图没有普遍必要。它提供的是给用户看的操作画面，未进入模型的视觉判断链路。建议采用显式、按需截图：普通网页检索和文本操作展示文本结果；视觉检查、明确截图要求和确有视觉诊断需要时截取关键状态。即使打开网页，也不应默认截图。本次只形成调研结论，没有修改产品或建立实施计划。

## 当前触发范围

运行器 `_handle_tool_event` 仅判断事件为 `called`、`denied_by` 为空、工具集名称为 `browser`，不看任务意图、具体函数、页面是否变化、面板是否打开，也不检查结果是否成功。

| 内置工具 | 当前行为 | 按需截图建议 |
| --- | --- | --- |
| `browser_navigate`、`browser_restart` | 每次完成后尝试截图 | 展示当前地址及操作结果；视觉任务在页面达到目标状态后显式截图 |
| `browser_view` | 读取正文与元素后再截图 | 默认展示文本内容与元素，无需图片 |
| `browser_console_view` | 读取日志后截图 | 默认展示日志 |
| `browser_console_exec` | 执行任意 JS 后截图，包括只读表达式 | 默认展示脚本结果；需要核对视觉变化时再截图 |
| `browser_click`、`browser_input`、`browser_press_key`、`browser_select_option` | 每次完成后截图 | 依据操作结果和最新页面状态验证；视觉任务在关键变化后截图 |
| `browser_move_mouse` | 每次移动后截图 | 只有检查 hover 效果、菜单或提示等视觉状态时才截图 |
| `browser_scroll_up`、`browser_scroll_down` | 每次滚动后截图 | 文本浏览不截；检查指定区域或固定元素效果时截 |

共 12 个工具，声明中没有独立的 `browser_screenshot`，也没有要求截图或选择截取范围的参数。底层浏览器协议虽然已有 `screenshot(full_page)`，模型目前不能通过工具声明直接选择调用它。

`called` 不等于动作成功。执行返回失败、执行异常转成失败结果，乃至已解析为浏览器工具后参数校验短路，只要未标注 `denied_by`，也会进入补截图分支。策略禁止、用户拒绝和 Plan 模式禁止会跳过；等待审批尚未完成时不截图。MCP 浏览器工具和通过 Shell 执行的浏览器脚本不属于 `browser` 工具集，不受这条规则统一控制。

## 截图实际供谁使用

数据顺序是：工具执行与结果整形 → JSON 工具结果写入模型记忆 → 产出 `called` → 运行器截图并上传 → 将图片地址填入 `BrowserToolContent` → 保存事件并发布给前端。

模型读取的是 `ToolResult` 序列化文本。`browser_view` 提供 Markdown 正文和可交互元素，导航提供可交互元素；操作、脚本和日志各自返回结果。补截图发生在结果写入记忆之后，图片地址只放在事件展示字段中，没有把图像注入模型请求。因此，当前自动截图不能帮助模型识别排版、看图表、选择视觉坐标或确认 hover 效果，也不能据此声称具备视觉验收能力。

代码注释将这段逻辑解释为让前端交互更友好。结合工作台可以选择历史调用查看图片，推断其设计意图是操作过程预览。现有材料没有证明“每次都截图”比关键状态截图更有效，过程图片也不能替代业务成功条件。

已有证据是[W9–W11 验收原始记录](../plan/evidence/w9-w11-acceptance-2026-10-02.json)中的受控网页任务：目标只是读回验收码，却分别为 `browser_navigate`、`browser_view`、`browser_console_exec(document.body.innerText)` 保存了 3 个不同截图文件引用。这证明只读调用确实产生额外图片；没有比较这些图片的像素，不能宣称三张完全相同。

## 资源开销与观测盲点

每次成功补截图至少涉及浏览器截图与 PNG 编码、CDP 字节传输、API 中的图片缓冲、文件写入或 COS 上传、文件元数据数据库提交、事件中的图片引用。用户查看图片时，还涉及图片下载、解码与界面重绘。工作台关闭只可能减少图片展示开销，不会停止后端生成、上传和保存。

这条链路被 `await` 串行执行，在 `called` 持久化之前。图片生成或上传慢，会延迟用户看到工具完成，也会延迟循环推进到下一个工具或下一次模型请求。补截图异常只记录日志，不把已完成的工具改成失败，但失败之前的等待仍存在；此处没有单独设置截图及上传的总超时，底层自身的超时不等于这条链路的统一预算。

`duration_ms` 在工具管线中已算完，后续截图和存储不计入该值；轮次与收尾的 `tools_ms` 又按该值累加。验收记录中的 434、20、18 ms 因此不能用来估算这 3 张截图的开销。总运行墙钟时间会受影响，但目前没有独立截图耗时统计。本次没有性能实测，不提供节省比例或每张图片的成本数字。

当前图片没有作为视觉输入送给模型，所以这里的直接浪费主要是执行延迟、计算、存储和展示流量，不能直接套用视觉模型的图片 token 费用。

每次上传使用新的 UUID，没有内容去重或采样。文件存储协议只有上传、下载与获取地址；补截图不登记到会话附件列表，删除会话的代码也没有调用截图文件清理。已核对链路未发现截图专用保留期和回收入口。外部 COS 生命周期配置不能由源码判断；历史清理应作为单独事项，不能为减少未来截图顺带删除旧文件。当前清理边界统一记录于[能力与边界](../capabilities.md#浏览器与视觉边界)。

## 为什么截图显得短且缺少信息

自动截图调用没有传 `full_page=True`，底层使用 PNG，按 Playwright 默认语义截取当前视口，不会保存整个可滚动页面。沙箱 Chrome 配置窗口为 1280×1080，并使用最大化参数；实际视口受窗口环境影响，不能把启动尺寸直接写成每张图片的像素尺寸。[Playwright 截图文档](https://playwright.dev/docs/screenshots)区分了视口、整页和元素截图。

工作台使用 `w-full h-auto` 把原图缩放到窄面板宽度。原图中的字和高度一起缩小，会进一步造成“很短、信息很小”的观感；放大预览只能改善显示，不能补上没截到的页面下半部分。这里是源码解释，没有重新测量用户所指图片或本次实际窗口。

截图分支也没有统一等待业务目标出现。`browser_view` 检查页面 `readyState`，并不证明 SPA 数据、图片或点击后的结果已经稳定。其他操作完成后立即补截图，可能只保存了加载中或过渡状态。改成全量长截图会增加体积和阅读负担，仍然无法解决截图时机和用途问题。

## 外部工具采用的取舍

| 官方来源 | 已核对做法 | 对 RayAgent 的意义 |
| --- | --- | --- |
| [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp) | 使用结构化可访问性快照完成交互，截图是独立工具，支持整页与目标元素 | 浏览器自动化可以主要依赖结构化内容，截图不必绑定每次动作 |
| [Chrome DevTools MCP 工具参考](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md) | 文本快照和截图分别提供；快照说明推荐优先使用文本快照 | 日志、脚本结果、页面结构和视觉证据各有用途 |
| [Anthropic Computer use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool) | 图像返回给模型；支持一组操作后截图观察结果，并建议管理截图历史 | 视觉 Agent 确实需要持续观察，但前提是模型能看图；这与 RayAgent 的展示补截图不同 |

以上核对的是 2026-10-08 的官方资料，不是对所有浏览器 Agent 的统计。RayAgent 当前提取的是自研 DOM/Markdown 与元素列表，不能直接称为上述工具的可访问性树；借鉴其取舍不需要迁移浏览器框架。

## 建议采用的截图规则

默认按文本与结构化结果浏览。截图只在以下场景显式生成：用户要求截图或留证；检查视觉布局、样式、响应式、交互反馈；DOM 和日志无法解释的视觉异常；确实需要观察 canvas、图表等像素内容。后两类是必要的补充例外，不必限制成用户必须说出“截图”这个词。

视觉任务也不应每步自动截。先明确要验证的现象，再选关键状态：例如修改后按钮是否遮挡、菜单打开后的层级、窄屏布局、表单提交后的反馈。输入多个字段可以在提交或状态变化后集中核对，无需为每个字段保存一张图。普通打开网页、滚动读文章和读控制台默认零截图。

| 要回答的问题 | 合适证据 |
| --- | --- |
| 页面写了什么、数据是多少 | 文本提取、结构化数据、来源链接 |
| 按钮是否可操作、提交是否成功 | 操作返回值、最新元素状态、结果文本或业务读回 |
| 排版是否合理、元素是否遮挡 | 指定视口或目标区域截图，加具体观察结论 |
| 整体页面布局如何 | 显式整页截图；长页面必要时分段检查 |
| hover、弹层、固定元素是否正常 | 保留相关状态的视口或区域截图，避免用长图代替 |

如果今后让 Agent 判断视觉效果，需要同时解决图像送入模型、模型能力与历史容量管理。只增加一个返回下载 URL 的工具只能完成截图留证，不能保证模型看过图片。用户手动预览与 Agent 视觉输入应明确区分。

## 落地时必须一起处理的契约

直接删除补截图分支会造成展示缺口：当前 SSE 投影的 `content` 来自 `tool_content`，没有直接传出 `function_result`；浏览器展示内容目前只有截图字段。前端虽然有“无图时展示结果”的分支，标准浏览器事件却缺少正文和日志供它使用。因此建议在同一范围内处理以下事项，再安排实施：

1. 浏览器完成事件提供当前 URL、结果摘要或受限文本、成功或失败与错误；不把超长原始正文无界地塞入事件。实时与历史回放保持一致，兼容旧截图事件。
2. 截图成为独立显式能力，允许按视口、整页或目标区域选择，并记录目的、页面 URL、捕获时间与实际尺寸。底层已有 `full_page` 不代表所有区域能力已经实现。
3. 普通调用展示文字和操作状态；有明确截图结果才展示图片。不能用后来的“当前页面截图”冒充某个历史调用的当时画面。
4. 图片失败不覆盖业务结果。需要截图的任务明确反馈失败；工具耗时与截图/存储耗时分别记录。图片保留期、配额与清理归属有明确规则。
5. 提示词按任务和证据需求选择截图，不用中文关键词匹配来硬编码意图。普通工具链不因视觉诊断规则重新恢复全量自动截图。

建议验收至少覆盖：纯文本网页任务零自动截图；明确截图任务产出正确范围的图片；视觉任务检查关键状态并解释观察；浏览器日志与失败可见；旧截图回放可用；慢截图或存储失败不会掩盖已完成动作。性能对比需使用同一网页和同一操作序列，独立统计截图数量、字节与耗时。
