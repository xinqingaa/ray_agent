# RayAgent 架构说明

本文维护系统结构：模块边界、执行与数据流、状态归属和控制参数。按机制定位代码见[代码地图](code-map.md)。

## 系统边界

![RayAgent 架构：任务运行分别写入三处存储，模型、沙箱与外部服务在右侧，沙箱画面单独经 API 转发到页面](assets/architecture-overview.svg)

*旧基线示意，W8 重绘：图中「任务运行」标注的 Plan + ReAct 已由单循环 Agent 替换，组件边界与数据流向不变。*

图中蓝线是请求与调度，绿线是持久化与事件回传，紫线是沙箱操作，红线是外部协议，灰色虚线是沙箱画面的转发通道。箭头指向被调用的一方表示谁发起，结果沿同一条边返回。左侧三处存储各自标注了写入内容，两组扇出分别来自应用协调和任务运行；这些写入不在同一个事务里完成。

| 模块 | 职责 |
|---|---|
| UI | 会话交互、事件消费、计划与工具结果展示、沙箱画面 |
| API | 会话管理、任务执行、模型与外部能力适配 |
| 沙箱 | 隔离的 Shell、文件、浏览器与进程管理环境 |
| Nginx | UI 与 API 的访问入口，转发 SSE 和 WebSocket |
| PostgreSQL | 会话状态、事件历史、Agent 记忆及文件元数据 |
| Redis | 任务输入输出流与事件传递 |
| 文件存储 | 附件、执行文件与截图；通过适配支持本地磁盘或对象存储 |

产品通过 MCP 客户端调用外部工具，通过 A2A 客户端调用远程 Agent。两者接入现有工具层，主执行流程由自研单循环 Agent 驱动。实验目录还包含服务端示例，其角色不能直接套用于产品。

## API 分层

API 的实现位于 `ray_agent/api/app/`：

| 层 | 职责 |
|---|---|
| `interfaces/` | HTTP 路由、请求响应结构、SSE 映射与依赖组装 |
| `application/` | 会话、文件、配置和任务等应用服务的协调 |
| `domain/` | 领域模型、Agent 循环与工具管线、工具，以及仓库和外部能力的抽象 |
| `infrastructure/` | 数据库仓库、模型调用、Docker、浏览器、消息队列、协议客户端和存储的具体实现 |

依赖在 `interfaces/service_dependencies.py` 中组装。数据访问通过仓库与工作单元组织，外部资源通过抽象接口和具体适配实现连接。目录表达了职责划分，分析具体行为仍需沿调用代码确认。

## 一次任务的执行

![任务运行模型：外层选择并更新步骤，内层循环调用工具，两层只在步骤边界交接](assets/task-lifecycle.svg)

*旧基线示意，W8 重绘：图中的外层步骤调度与内层循环已合并为下文的单循环。*

会话请求经应用服务准备沙箱、浏览器与任务，由运行器消费输入并调用 `AgentLoop`。循环只有一层、一份记忆：每次请求模型前先取出运行中补充的用户消息，再带全部工具声明请求一次模型。回复含工具调用时，按返回顺序逐个经工具管线执行，把结果按调用 ID 回填后再次请求模型；回复不含工具调用时，这段文本就是最终答复（Markdown），运行结束。模型可随工具调用附带简短说明，作为进展旁白显示。

计划清单由模型调用 `update_plan` 维护：每次提交完整清单，程序据此发出计划事件供页面展示，不按清单调度，也不校验清单与实际执行是否一致。需要文件成果时，模型调用 `deliver_files` 把沙箱文件上传为会话附件；缺少必要信息时调用提问工具，运行进入等待。

工具管线分执行前、执行、执行后三段，每段是按注册顺序运行的处理函数。执行前检查工具是否存在、解析参数 JSON 并按声明做轻量校验，失败时短路为该调用的失败结果；执行段只调用工具一次，异常转为失败结果、不重试；执行后记录耗时。任何路径都产出一个与调用 ID 配对的结果和一对工具事件，工具失败交给模型决定下一步，不终止任务。

模型请求只对传输类错误（连接、超时、限流、5xx）和空回复重试。输出因长度上限被截断时，本次回复不写入记忆、其中的调用不执行，循环追加一条缩短输出的提示后重试一次；连续两次截断以失败结束。

## 结束路径与控制平面

![任务的四条结束路径：完成、等待、失败与停止，各自的收尾范围不同](assets/task-exits.svg)

*旧基线示意，W8 重绘：图中完成与失败的触发条件仍是双循环版本，当前触发条件以下表为准。*

任务有四种离开运行状态的方式，收尾范围各不相同：

| 路径 | 触发 | 收尾 | 注意 |
|---|---|---|---|
| 完成 | 模型回复不含工具调用 | 写入完成状态与终态事件 | 最终答复是模型的陈述，不等于目标达成 |
| 等待 | 模型调用提问工具 | 发出问题消息，保存等待状态并退出当前运行；同批次提问之后的调用不执行 | 回复到来时重新组装运行器继续，回复作为提问调用的结果，不唤醒原协程 |
| 失败 | 模型请求不可重试或重试耗尽、连续两次输出截断、模型请求数达到 `max_iterations` | 写入失败状态与错误事件（含原因） | 只结束本次运行，同一会话可再发消息 |
| 停止 | 用户请求停止 | 取消执行协程，写入与完成相同的状态和终态事件 | 会话状态枚举中没有取消态 |

上一次运行留下的无结果调用（等待、停止或失败时正在执行或尚未执行的调用）在下一次运行开始时统一补结果：等待时提问调用以用户回复为结果，其余补为“未执行”；停止或失败时，已发出 `calling` 事件的调用补为“执行中断，结果未知”，其余补为“未执行”。因此发给模型的消息序列里不会有缺少结果的调用。

停止不会向下传播。取消调度协程、终止沙箱内的 OS 进程、回收沙箱环境、撤销已写入的文件是四件独立的事，当前只做了第一件。

执行预算分布在各层，除 `max_iterations` 按单次运行累计外都约束**单次调用**，没有跨运行的任务总预算或 token 预算：

| 参数 | 默认值 | 约束范围 |
|---|---|---|
| `max_iterations` | 100 | 单次运行（一条新消息或一次续接）的模型请求数，重试也计入 |
| `max_retries` | 3 | 单次模型请求的最多尝试次数，只对传输类错误和空回复生效；工具调用不重试 |
| 模型请求超时 | 3600 秒 | 单次模型请求（在模型客户端内硬编码） |
| 沙箱 HTTP 超时 | 600 秒 | 单次沙箱请求 |
| Shell 等待进程 | 60 秒 | 单次等待；超时返回错误，不终止进程 |
| MCP 连接／发现／调用超时 | 10／15／120 秒 | 每个服务各自计时，另有 20 秒全局发现预算 |
| A2A 调用／取消超时 | 600／5 秒 | 单次委派；轮询间隔由 1 秒递增至 5 秒 |

`context_window` 只用于展示最近一次请求的占用，不参与裁剪或拒绝。用量事件是记账，不是强制预算。

## 状态与持久化

![状态归属：请求内、进程内与进程外三层寿命，以及哪些是引用、快照和真实副作用](assets/state-ownership.svg)

执行中的信息按寿命分三层，排查问题时应先确定目标信息属于哪一层：

| 寿命 | 包含 | 边界 |
|---|---|---|
| 本次请求内 | Context 装配结果、前端派生的展示状态 | 请求结束即消失，事后不可追溯 |
| 当前进程内 | 执行协程、任务注册表、Flow 局部状态 | 进程重启即丢失，另一个进程看不到 |
| 进程之外 | 会话、Agent 记忆、事件历史、Redis 流消息、工作文件与附件 | 能重新读到，但不等于能继续执行 |

三类进程外数据的性质也不同：**ID 是引用**（数据库里存着 `sandbox_id` 不代表容器还在），**记录是快照**（事件历史能完整回放不代表执行能继续），**只有工作文件是真实副作用**（取消不会回滚已写出的内容）。

| 状态或数据 | 所属位置 |
|---|---|
| 会话、事件历史、Agent 记忆、文件元数据 | 领域会话模型与 PostgreSQL |
| 计划清单 | 计划工具在运行内持有，每次更新发出完整快照的计划事件；续接时从最近的计划事件恢复 |
| 正在执行的任务 | `RedisStreamTask` 维护的进程内 `asyncio.Task` 与注册表 |
| 输入输出消息 | Redis Stream |
| 页面展示状态 | 前端从实时事件和历史详情派生 |

`Session.get_latest_plan()` 返回最近一个计划事件的快照。当前实现不再产生步骤事件，每次计划更新都是完整快照；旧会话历史中的步骤事件仍由前端合并到计划展示里。

Agent 记忆在每次以新用户消息开始运行时做一次局部清理（回复提问属于同一轮，不清理）：`compact()` 把此前浏览器查看与导航两类工具消息的正文替换为占位内容，并删除消息上的推理字段。这是按工具类型的定点裁剪，不按 token 预算触发；一次运行内的工具结果全部保留。工具结果写入记忆先于对应的 `called` 事件发布，在事件之后停止不会丢失已执行调用的结果。

界面显示完成、流程到达终态、后台任务结束和资源释放是不同环节，排查时应分别确认。

## 事件与投影

领域事件经 API 映射为 SSE，前端据此构建时间线与计划展示；历史详情提供已保存的事件。实时流与历史读取共同支撑同一会话视图。

投影过程中会丢信息，因此**页面所见严格小于内部保存**：给前端的工具事件省略了模型收到的原始结果，只保留供预览的内容；文件类工具在 `called` 阶段由运行器再读一次沙箱来填充这份预览。时间戳取整到秒，短间隔无法区分，工具事件另带毫秒级的执行耗时；事件之间也没有贯穿一轮的关联标识，无法据此重建完整调用链。

事件先写入 Redis 输出流，再写入数据库。页面因此能尽快看到进展，代价是存在一个窗口：事件已经展示但尚未落库。数据库事务也不包含工作文件写入、事件发布与文件存储上传。

## 跨模块协作

工具层将模型提出的动作交给具体适配实现：Shell 和文件操作通过 HTTP 访问沙箱服务，浏览器通过 Playwright 以 CDP 连接沙箱内的 Chromium，MCP 与 A2A 通过协议适配连接外部工具和远程 Agent。应用侧负责组装这些能力，协议接入不替代本地任务流程。

沙箱画面走的是另一条路：页面建立 WebSocket 连接到 API，由 API 转发到沙箱的 VNC 端口双向传数据。它不经过工具层，和任务是否在执行无关。

多服务可能提供同名工具，MCP 适配用带哈希的别名路由区分并映射回原始名称。协议返回的结果按字符数与列表项数截断后才进入上下文。需要多轮交互的协议调用当前按失败返回。

领域模型、数据库模型与接口响应分别承担业务、存储和传输职责。文件内容由存储适配管理，元数据与会话关系由应用和数据库管理；沙箱工作文件与用户可下载的交付文件属于不同资源：用户上传的附件由运行器同步进沙箱，交付文件只由 `deliver_files` 从沙箱上传到存储并关联会话，文件工具读写不会同步到存储。

## 沙箱生命周期与限制

创建任务时会准备沙箱和浏览器，因此不使用浏览器工具的对话也依赖这条准备链路。

沙箱按会话标识查找或创建：找到运行中的容器就复用，否则新建。任务结束不销毁沙箱，环境靠显式销毁或存活时间到期回收。API 支持动态创建，也支持按地址连接已有沙箱，两种模式不能混用资源归属假设。

隔离需要分别落实在四个方向上，当前程度不一致：文件系统按容器分离；网络仅在配置了专用网络时才隔离；沙箱服务以 root 身份运行；创建容器时未设置 CPU 与内存配额。工具参数中的工作目录只用于解释相对路径，不构成访问围栏；已知的不一致与未验证范围见[能力与边界](capabilities.md)。
