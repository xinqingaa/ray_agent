# 长任务计划可信度与成果交付优化方案

日期：2026-10-12。代码基线：`6ae08486ff41d351786ccfaf661894bd7f0e4d25`。状态：**实施与有限验收结束；业务正确性和效率保留失败观察**。

本次维护以用户能持续信任计划、理解当前工作、取得完整成果为目标。采用稳定的整体阶段与可调整的执行步骤，按成果版本管理验证，将交付纳入预算收尾，并在最终答复中核对当前任务的累计成果。以下定义本轮契约；实施与运行结果见末尾，当前能力以源码和验收证据为准。

## 一 目标与范围

用户应能回答四个问题：最初要求还剩什么、现在在做什么、为什么需要返工、最终能拿到什么。任务运行成功、计划勾选完成和成果满足要求分别表达。

本轮包含计划数据与工具协议、事件及上下文恢复、计划显示、验证和返工记录、文件交付、预算收尾、最终答复组织及相关验证。保留自研单循环；执行步骤仍由模型决定，程序校验结构、引用、动作条件和交付事实。

本轮不包含框架迁移、独立 Planner、额外通用评审模型、自动证明任意业务正确、课程同步、公开多用户改造或崩溃后自动重放。用户测试生成的后台原型用于分析与回归，不在此方案中授权重做该原型。

优先级按下表执行。四组都纳入本方案，不把修好文案当作整轮完成。

| 优先级 | 工作 | 完成条件 |
|---|---|---|
| P0 | 稳定计划与范围 | 整体阶段不被局部步骤替换；延期不掩盖未完成；计数同层且可解释 |
| P0 | 验证和返工收敛 | 取消固定批次核对往返；复用有效证据；重复修复有原因和结束条件 |
| P0 | 成果与预算收尾 | 分项核对预期成果；收尾能完成已登记成果；已有版本和失败项保留 |
| P1 | 累计交付说明 | 答复与文件、范围和验证一致，能独立阅读，简单问答不受报告规则干扰 |

## 二 事实依据与问题界定

依据为本次用户提供的两个会话、全部持久事件、最后一轮请求重建、交付文件及有限浏览器抽查。[精简证据](evidence/long-task-audit-2026-10-12.json)保存输入、运行统计、关键计划、失败及交付事实，并记录下载文件哈希。业务内容只进入证据和回归样例，不写入通用提示词、工具说明或通用判定规则。

| 观察 | 已确认事实 | 设计含义 |
|---|---|---|
| 多轮计划混层 | 父阶段与四个子步骤平铺；5/7 完成时仍显示第 2/7 步，同一状态约保持 90 秒 | 阶段与步骤需要明确关系，不能共同充当线性进度分母 |
| 计数含混 | 第一轮共三项，其中一项本轮、两项 later；当前计数分母是一 | 不能在完整清单旁显示没有范围说明的 1/1；用户描述的四项变 1/1 尚未完整复现 |
| 固定核对成本 | 多轮原型执行 58 次请求，其中 12 次只调用 review；多轮和单次分别有一次、三次未确认事件 | 核对频率与工作变化脱节，内部状态不适合成为主要用户状态 |
| 交付被预算阻止 | 单次任务 95 次请求；进入收尾后写方案被拒，最后将未落盘项改为 later | 必要成果不能被当作可选扩展拦截；资源不足不能等同授权后续 |
| 总结与实现冲突 | 单次答复中的用户数量、任务规模、留存队列及停留分母与交付实现不一致 | 最终答复需要当前成果依据；程序只能校验部分可观察事实 |
| 排版体验 | 多轮最终正文有合法 Markdown 与正常段落，长段落仍难扫读 | 优化内容组织，避免用修复 Markdown 解析器解释生成内容问题 |
| 压缩范围 | 多轮未压缩；单次压缩一次，原目标和用户原文仍在请求里 | 本次不能断言目标因压缩丢失，但恢复信息需要明确区分来源 |

多轮实际输入为“先交付方案”及“我同意你的方案”，并非原拟三轮测试脚本；两次均为独立会话、同模型与思考档位。本证据不能比较项目模式，也不能给出总体成功率或严格提速结论。

## 三 计划结构与稳定性契约

### 整体阶段与执行步骤

保留一个计划身份，计划内区分整体阶段与当前阶段的执行步骤，最多两层。整体阶段回答“目标由哪些部分构成”，执行步骤回答“当前部分如何完成”。开始执行前确定整体阶段；后续可细化步骤，保持阶段身份和顺序。

建议扩展现有计划，而非引入独立需求表与新的常驻界面。利用计划已有目标字段，保存独立的简短标题、一句任务描述、完整目标、相关用户消息引用、本次范围、预期交付及变更原因。用户原文仍是依据，模型整理的目标是可修订解释，不成为新的用户授权。

建议字段含义如下，名称可在实施中按现有模型调整，含义不得混用。

| 信息 | 契约 |
|---|---|
| 计划身份与目标 | 延续同一任务复用 plan_id；目标关联真实用户消息 seq；无关任务才建立新计划 |
| 阶段 | 稳定 id、标题、生命周期状态、执行安排、范围来源；同一阶段展开步骤时保留 id |
| 步骤 | 稳定 id、所属阶段 id、描述、状态；只从属于一个阶段，不与父阶段共同计数 |
| 本次范围 | 保留必要能力与交付形式，关联本运行实际用户输入，区分用户明确安排与模型执行建议 |
| 预期成果 | 回复正文、文件或二者；独立成果身份、来源、必需性和交付方式 |
| 变更 | 保留身份，说明增删、拆并或重新打开的原因，以及相关用户消息或实际失败证据 |

一次完整更新仍返回完整有效清单，程序检查身份、父子关系、无循环引用、同一时间最多一个当前执行阶段和一个进行中的叶步骤。未展开的阶段不强制生成子步骤，简单任务无需凑阶段或调用计划工具。

### 执行状态与后续安排分开

生命周期拟采用未开始、进行中、已完成、受阻、已取消；本轮或后续属于安排属性，不再让 later 同时承担未开始、范围排除和失败出口。

| 情况 | 拟议表达 | 允许依据 |
|---|---|---|
| 用户明确本轮只做部分 | 剩余阶段为后续，尚未开始 | 原始或补充用户消息 |
| 模型建议先做部分 | 阶段建议；原目标仍需完成 | 模型建议只能说明安排，不能充当缩减授权 |
| 用户取消一项 | 已取消，保留范围变更记录 | 真实用户范围修改 |
| 预算或环境不足 | 本次未完成或受阻，保留原因 | 实际预算或工具失败事实 |
| 用户同意下一轮继续受阻部分 | 更新后续安排，仍未完成 | 后续用户输入 |

程序能验证来源引用存在、属于该会话并在正确顺序，不能自动证明自然语言已授权某种取舍。对明确要求的关键能力或交付方式进行实质缩减时，模型需要说明影响；确需用户选择才提问。正常细化、排序和实现细节继续自主推进。

同一任务不能通过 reset、删除条目或 action=not_needed 消除已记录的必要成果。无关新任务可以新建计划或直接回答，历史未完成项保留在原计划，不阻塞新任务。语义上是否无关仍由模型判断，保留其判断来源，不能宣称程序已自动识别所有目标。

### 合理调整与可追溯性

- 步骤拆分、增加诊断、针对性修复允许进行，说明实际原因，不要求用户逐项确认。
- 整体阶段新增或用户明确取消有变更依据；已有整体阶段不直接删除，合并仍保留原身份和记录。展开步骤不会改变整体阶段数。
- 已完成项重新打开必须有新要求或反证引用；保留先前完成声明及对应证据，显示当前需要修复。
- 完成属于模型声明。可关联验证或交付事实，但工具 success、文件存在和测试通过都不能自动证明全部业务要求完成。没有实际核验时保留未验证范围。

## 四 用户界面与事件投影

主计划条固定使用整体阶段口径：当前阶段名称、已完成阶段数和仍需处理的阶段数。取消项单独表达，资源受阻项继续保留在目标范围内。全阶段完成才显示计划完成；仅当前阶段完成则说明后续阶段。

展开清单只保留简短标题、一句描述、任务项与状态；简单任务平铺，需要分组时轻缩进。完整目标、范围、变更解释、成果与核验记录继续用于执行及恢复，不重复占用清单。成果在交付区查看，范围变化和阻碍在对话中说明。完成数与分母采用同一层。清单只有一个顶层进度，子项不增加独立计数，父节点不与叶节点重复累计。历史查看复用同一投影规则。

| 状态 | 用户主要看到什么 | 内部记录 |
|---|---|---|
| 首次准备 | 正在安排任务或准备执行 | 尚无有效执行清单 |
| 正常执行 | 当前阶段及本次动作 | 计划最近更新与工具活动 |
| 同阶段核验 | 当前阶段下正在核验 | 核验对象、版本和条件 |
| 修复问题 | 正在修复已发现问题，简短原因 | 问题、改动和复验关联 |
| 计划近期未更新 | 继续展示最近有效计划，必要时说明最近更新时间 | 计划时效，不冒充实时动作 |
| 真正受阻 | 未完成的成果、原因、可执行下一步 | 预算、工具或等待事实 |
| 结束 | 当前任务的完成与未完成范围 | 运行终态与交付状态分别保存 |

工具执行动作来源于实际事件，只说明正在读、写或核验什么，不从工具名称自动推断业务阶段完成。界面不能用“进行中”高亮宣称旧步骤就是当前动作；当前阶段和实际活动分别表达。

“进度未确认”“清单尚未核对，请以执行记录为准”退出普通会话的主要状态。协议拒绝、过期声明和计划恢复异常仍保留在开发者视图；确实无法恢复有效清单时，普通界面显示“正在执行，计划暂不可用”，并提供查看过程入口。不要用隐藏真实错误来制造可信。

按事件 seq 更新投影，忽略旧快照覆盖，支持刷新、SSE 断连补齐、提问与审批续接。稳定身份保持展开和选择状态；轻量确认不增加清单版本或造成闪烁。使用现有专业工具界面、语义色、焦点与窄屏规则，详细设计契约实施后替换所属说明。

## 五 核对与重复返工治理

### 取消固定业务批次核对

取消“连续三批业务工具后强制 review、拦截下一批”的常规机制。保留已有计划承接、身份及参数校验。实际范围变化、阶段切换、首次执行已确认计划、准备交付或已有完成声明遭到反证时，核对相关信息。

这些核对优先随正常 update_plan 或业务动作同批完成，不新增每轮核对模型。继续当前步骤无需单独证明“仍在此步骤”。对明显遗漏的一次有界提醒和透明恢复仍保留，禁止形成定时核对循环。

是否进入新阶段主要由模型声明，程序不能仅凭工具类别决定。阶段未切换时，界面仍可依据工具事件显示核验或修复活动，避免为更新当前动作额外调用计划工具。

### 按版本保留验证证据

对复杂或文件任务，在现有计划更新或业务结果处理中登记少量关键验收项，不要求简单问答创建验收表，不新增独立 check 工具往返。每项至少关联验证目标、验收条件、成果版本、实际执行引用、观察结果和未覆盖范围。

验收条件来自用户要求及合理说明的默认值，不能直接把实现当前返回值设为正确答案。模型声明通过与实际执行证据分开；实际工具成功也只证明调用成功。程序校验引用、版本和执行事实，业务断言是否充分仍由检查及独立验收判断。

| 情况 | 处理 |
|---|---|
| 同一版本、同一条件、已有通过证据 | 复用，不反复执行或重新描述 |
| 修改影响被验证行为 | 标记相关证据过期，定向复验 |
| 修改影响多个共用机制 | 复验相关依赖和主链路，解释扩展理由 |
| 环境、输入或外部数据变化 | 依据变化重新验证，记录条件 |
| 无法确定文件是否被 Shell 等修改 | 状态标为待核对，在复用或交付前确认版本，不乐观假定未变化 |
| 当前没有实际证据 | 标为未验证，不用固定或模拟结果代替实际执行 |

版本以实际内容哈希或可验证文件版本为依据。文件工具可登记受影响路径，Shell 写入不能靠命令文本获得完整影响面；在成果登记、关键验证和交付边界批量确认相关文件，避免每轮重新读取全部文件。外部页面或服务无法获得稳定版本时，用观察条件和时间说明有效性，保守处理缓存。

数据计算、来源事实、真实交互和文档实现一致性分别检查。所有检查依赖同一个实现函数只能证明内部一致，不能作为独立业务口径通过。本轮不建设通用事实验收器；将这个边界落实到验收声明和回归用例。

### 给返工明确原因与结束条件

每次必要返工关联稳定的问题身份、影响成果、实际错误或新增要求。同一问题的修复前后版本和复验结果相连，不能靠更换命令或改写问题标题重置记录。

拟议默认：同一关键问题两次针对性修复仍未解决，先标明受阻并判断换方法、继续其他独立工作还是需要用户决定；可选美化在主要成果可用且预算紧张时停止。该上限按问题计，不限制整个任务只能修两次；新证据支持不同解决方法时可继续，但记录理由，不能静默循环。

程序可靠检测的是有明确身份和版本的重复动作。对未声明的语义重复只做观察与一次提醒，不能承诺自动识别所有无效返工；有理由的复检与关键失败修复不得被机械去重。

## 六 成果登记与交付保底

### 分项追踪成果

文件生成或复杂任务规划时，登记用户所需及 Agent 已承诺的成果。登记随 update_plan 完成，直接回答保持轻量路径。用户只要正文时不能擅自增加必需文件；Agent 主动承诺的额外产物须区别来源，最终说明其兑现情况。

成果状态至少区分待生成、已生成、已核验、已交付、生成或交付失败。核验状态允许未验证或部分验证，文件未核验也可在明确说明后交付可用版本；未经用户要求不无限追求完美。

运行正常结束仍可保留 completed，另由交付摘要表达完整、部分或受阻的成果状态。程序根据已登记成果的生成和交付事实判定可观察缺口；能力完成与业务质量保留模型声明和核验范围。存在必需成果缺口时，普通界面和最终答复显示“已交付部分成果”及具体缺口，不能仅凭运行终态显示整个目标完成。

路径不充当稳定成果身份。成果身份关联每版路径、哈希、文件 id、所属计划或运行，以及替代关系。继承同一任务以前的已交付成果，核对实际引用后列入累计成果；不会因一次 deliver_files 成功就宣布所有成果已交付。

附件成功与项目副本成功分别记录。部分失败只补失败项；重试以成果版本和既有交付记录判断，避免把已交付的同一字节重复创建为新附件。实质内容改变才登记新版，保留既有可下载版本和用户原材料。

### 提前形成完整可用版本

将必要的主体成果、基本核验、交付安排在可选扩展前。多文件任务先形成完整初版集合，再统一补关键检查；禁止一直精修其中一个文件而让其他必需成果直到预算末段仍不存在。

不强制刚写一个空壳就交付。初版应能覆盖核心用途，尚未实现或未验证的部分说明清楚。先交付后继续改进时，最终给出版本关系，不在每次小改后发送新附件。

### 受限收尾写入

保留请求预算、提前提醒及收尾阶段，取消“所有写文件都拒绝”的结果。建议新增专用收尾写入能力：仅在普通执行模式，为收尾前已登记的成果补写最终文本版本，成功后沿已有 deliver_files 路径交付。

拟议调用以成果 id 和内容为输入；运行器从登记记录解析目标路径，检查所有权、版本和既有文件保护。收尾阶段禁止为新功能临时注册成果或任意选择路径；每项最多一次成功收尾写入，明确执行失败可在剩余预算内定向重试一次，结果未知时先对账，不自动重复副作用。

此能力沿既有参数校验、工具授权、沙箱访问、项目占用和文件保护链路执行。不能在计划模式写入，不能绕过 ask 或 deny。覆盖旧用户材料需要原有授权；默认保存新版本。总写入量和工具结果沿既有输入输出及文件限制设置上限，超限明确返回原因，不静默截断。

这条通道覆盖最终文本成果，不提供任意 Shell、安装依赖、重新构建或继续开发。二进制成果应在正常执行阶段生成，收尾只交付既有文件；缺失时明确未完成。系统不能因预算只剩少量请求就保证任何尚未生成的复杂成果都能补齐。

拟保留现有 70% 提醒、末段收尾作为首轮对照参数，先改变可执行动作和成果核对，不同时更换阈值来模糊效果。收尾请求余额需要考虑现有重试与压缩计数，不额外赠送隐藏预算。最后一次有意义答复不得因补发一致性反馈而丢失。

## 七 累计总结与上下文恢复

### 根据交付方式组织最终答复

收尾前由运行器从有效计划、范围来源、成果记录、有效证据及缺口构造简短的任务状态，作为动态上下文提供给同一个执行模型。字段说明程序事实、模型声明和未验证部分，不将其全部包装成已完成事实。不额外请求通用总结模型。

只在复杂任务、文件交付、范围受阻或同一任务多轮延续时提供这段信息。简单问答沿原路径直接回答；正文就是成果时保留完整正文，不能用总结替代；文件交付时以成果和可用能力为主。业务任务类型不做宽泛分类，依据已有运行模式、交付约定和执行事实选择行为。

| 输出方式 | 必需内容 |
|---|---|
| 简单直接回答 | 用户问题的答案；不增加计划、检查和成果报告 |
| 回复正文为成果 | 完整正文；必要的假设、范围和实际缺口 |
| 文件为主要成果 | 文件与版本、当前累计可用能力、关键核验、实际未完成项 |
| 明确分阶段交付 | 本次范围、整体目标位置、后续安排的依据 |
| 修改已有成果 | 修改内容、沿用内容、当前新版整体状态，保留旧版关系 |

累计总结围绕同一计划对应的任务，不概括会话里全部无关主题。至少说明相关阶段各自的成果，不只描述最后一轮改动。没有获得授权的延期继续列为本次未完成；用户明确排除的能力作为边界，不能冒充遗漏待办。

### 可读性与真实性

最终答复先写可用结果及关键缺口，再写必要说明。并列功能用短列表或短段落；较长说明使用层级清楚的标题。允许用户需要的表格，移除全局“最终答复不需要表格”和“一律简洁总结”的限制。文件型答复的过程和验证细节进入成果说明或开发者记录，正文型答复遵从用户篇幅要求。

文件、版本、交付数量等可观察事实由程序核对，严重不一致最多一次纠正。统计口径、内容事实和功能质量不能靠通用文本比较自动验收，按关键验收项及独立检查核对。未执行的检查不写成通过；先前版本的通过不能挪到修改后的版本。

### 压缩与续接

压缩摘要区分真实用户要求、模型建议、已确认范围、成果事实、检查声明与剩余工作。排除预算和计划核对等内部消息成为“用户明确约束”；内部消息保留自己的来源和协议作用。

最新有效计划、范围与成果状态从持久事件恢复，并在需要的请求边界注入精简快照，不只依赖摘要记住所有 id 和文件。仅提供当前阶段、主要成果及有效检查索引，按需读取细节，避免每轮重复整份报告。

提问、审批续接沿同一运行恢复收尾额度及一致性反馈次数；新用户消息按已有预算规则处理并更新范围。API 重启继续保留当前中断语义，不借本轮引入执行检查点或自动重放。项目笔记补充背景，不替代相关计划和文件事实；会话与项目使用同一套执行契约。

## 八 实施顺序与模块责任

每批完成后运行实际受影响的检查，再推进下一批。全部工作包完成后统一真实验收；实施中允许修正字段名称和局部设计，范围和验收条件发生实质变化时先更新本方案。

| 批次 | 实施内容 | 依赖与交付 |
|---|---|---|
| A | 固定审查基线与最小回归；定义阶段、步骤、范围和成果协议 | 保留现有失败观察及旧事件；确定新协议样例 |
| B | 计划协议、范围变更、事件读回及阶段界面 | A；稳定两层计数、状态和刷新恢复，取消旧周期 review 拦截 |
| C | 验收项、版本关联、重复检查与返工记录 | B；批量核验、影响面失效、必要修复和停止条件 |
| D | 分项成果、版本交付、受限收尾写入 | A/B，复用 C；多成果完整性与预算末段路径 |
| E | 动态收尾上下文、累计总结、压缩来源与文档同步 | B/C/D；直接问答对照与两类交付均通过 |
| F | 有限真实模型与真实 UI 验收，部署前后身份核对 | A–E；保留失败、按匹配条件比较，完成范围逐项收口 |

领域层维护计划、范围、验证与成果事实及纯校验；循环决定何时注入上下文、继续或收尾；工具管线执行授权和一次动作；应用运行器负责实际文件版本、上传及项目副本；前端只投影事件并保持状态，不自行判断业务完成。持久事件作为恢复依据，配置快照冻结协议版本及预算参数。

定位入口集中在[代码地图](../code-map.md)的 Agent 循环与工具管线、上下文与记忆、文件与交付、事件观测与投影及前端分组。实施后在该地图更新新入口；本方案不另维护代码路径表。

## 九 新协议与部署约束

用户明确不要求兼容旧对话。本轮直接使用阶段、步骤与成果新协议，移除旧 later 状态，不猜测历史父子关系，不保留旧等待处理器，不自动改写或删除旧对话。用户自行移除不符合要求的旧对话；本轮验收只新建会话。

计划和成果复用现有事件 JSON，不新增数据库表。API/UI 配套部署，核对实际内容指纹。部署前确认无活动和等待运行，保留实际容器配置、数据库、附件与项目文件。新事件写入后旧镜像不能解释全部新协议，不声称能够直接回退并继续新会话。

## 十 验收矩阵与停止条件

### 确定性与组件验收

测试使用实际循环、工具管线、事件投影和组件，模型及环境按条件替换。对数据库原子性和项目文件保护，使用独立测试数据库与受控文件环境。以下是完成门槛，不是已通过结果。

| 编号 | 场景 | 必须观察到的行为 |
|---|---|---|
| T01 | 三个整体阶段，当前阶段展开四步 | 整体分母仍为三；父阶段与子步骤不重复计数；界面标签明确 |
| T02 | 当前阶段全部完成、整体尚有工作 | 只声明阶段完成，整体目标仍有剩余；不能显示整体全完成 |
| T03 | 合法增删、拆并、重新打开 | 身份和原因保留；过期或非法引用失败，不产生半份清单 |
| T04 | 预算不足或文件生成失败 | 记录本次未完成及原因，不能通过 later/reset/not_needed 消除 |
| T05 | 同阶段执行十二批工具 | 零次仅为定时核对而产生的 review 请求；正常业务不中断；无未确认闪烁 |
| T06 | 已确认计划执行与范围补充 | 首次业务动作前承接范围；正常细化可继续；重大缩减不伪装成授权 |
| T07 | 同版检查、改版及外部条件变化 | 同条件通过证据复用；变化只失效相关项；未知影响不冒用旧通过 |
| T08 | 同一问题两次修复仍失败 | 记录持续问题，停止机械循环并保留用户目标和下一步 |
| T09 | 两份必需文件只交付一份、截图成功 | 仍保留另一份缺口；一次交付或截图不满足全部成果 |
| T10 | 一项交付失败、同版重试、新版发布 | 只补失败项；同版不重复附件；新版不破坏旧版 |
| T11 | 收尾补写已登记文本成果 | 能写并交付；新功能、新路径、覆盖旧材料及计划模式受原契约约束 |
| T12 | 最后请求、摘要请求、重试及审批续接 | 预算准确；无隐藏额外额度；已有最终答复不因反馈被丢弃 |
| T13 | 正文、文件、混合交付和简单问答 | 正文完整；文件回复累计明确；简单问答不多一轮报告 |
| T14 | 压缩、提问续接、刷新与 SSE 补齐 | 计划及成果状态恢复；用户原话与内部消息区分；旧 seq 不覆盖新状态 |
| T15 | 新协议读回与非法旧状态 | 新字段完整读回；非法状态拒绝，更新原子失败；不迁移旧会话 |
| T16 | 会话与项目、附件与项目副本 | 同一目标规则；文件保护和失败恢复不退化 |

既有注入用户消息测试需按实际契约更新：断言消息在下一次请求前出现、顺序正确、工具不被中断；不再依赖末尾恰好三条消息，同时不能删去有效控制断言来制造通过。

### 有限真实任务验收

首轮建议八次运行，保持模型、思考档位、预算、工具策略及任务材料固定。任务输入冻结后才运行；两个已审查任务是主要对照，新增数据和正文任务用于防止方案偏向界面生成。

| 场景 | 次数 | 实际验收 |
|---|---:|---|
| 一次交付方案与原型 | 1 | 全部预期成果、关键口径与实现一致、必要交互；记录是否因预算缺失 |
| 同目标分轮交付 | 2 | 原方案保留、阶段延续、最终列出累计成果；旧版不破坏 |
| 多文件数据整理 | 1 | 固定输入独立重算、各文件一致、原材料保护 |
| 回复正文交付 | 1 | 完整正文、必要结构；总结不替代正文 |
| 简单直接问答 | 1 | 一次请求直接回答，无计划与报告往返 |
| 项目内多轮修改 | 2 | 文件与背景延续、版本关系和累计成果；不把进程状态延续当作保证 |

压缩未触发就记录未覆盖，压缩和预算边界另由确定性场景及受控实际路径覆盖，不为触发压缩刻意扩大产品任务。首轮有失败时，保留失败，只补测被定向修复影响的场景；所有参与者看到相同结果，不为了凑全通过反复运行。

记录总请求、纯协议请求、有效业务调用、重复检查、返工原因、首次可用版本和首次交付时间、完整交付比例、计划结构变更及缺口。完整交付按事先冻结的必要成果计算；运行 completed 不作为业务通过标准。质量与范围先通过，再评价成本；相同任务条件下比较，不预承诺固定提速百分比。

关键范围被消除、必要成果被阻止、已有文件损坏或新协议不能读回，均阻止发布。健康运行反复显示未核对、固定核对仍造成纯往返、已通过且未变化的检查无理由重跑，均不接受为“模型限制”直接收尾。

本方案完成意味着计划结构与计数稳定、内部核对不制造常规噪声、验证记录可复用、交付有分项依据、最终答复能交代累计成果。模型仍可能遗漏语义要求、提出不足的验收条件或错误判断内容；这些属于明确保留的边界，不用“计划可信”承诺全部任务自动正确。

实施已覆盖协议、循环、工具与界面，配套部署与源码指纹核对通过。核心与协议 386 通过、62 跳过；独立 PG 27 通过；真实模型分批 12 次运行及最终轻量文件、桌面/窄屏检查已记录于[本轮验收](evidence/long-task-closeout-2026-10-12.md)。第一次界面改动过度展示内部信息，按用户反馈收简为标题、描述、任务项和一个顶层进度。完整文件交付不代表业务验收通过：后台原型留存口径和快速重置仍有失败证据；模型未登记的语义重复及条件遗漏未解决。原阶段身份保留，不直接删除整体阶段。
