## 方法与结果

确认零活动 run 后，创建记录中列出的 8 个隔离项目。容器内临时[测试钩子](w11-stage-d-api-exit-hook-2026-10-01.py)只作用于 PID 1 和这 8 个项目 ID；恢复到删除、覆盖、链接重建、属主设置阶段时，先保存一次性故障标记，再调用 `os._exit(73)`。请求使用运行产品的实际 HTTP 恢复入口；没有替换业务路由或修改仓库源代码、镜像、配置及凭据。

四阶段分别使用重试目标和回到恢复前。8 次 HTTP 请求全部在操作过程中中断，8 个标记均为 PID 1，容器 RestartCount 逐次从 0 增至 8，镜像 ID 不变。自动重启后的 API 均健康；恢复操作保留 failed/applying、原目标和恢复前快照，新运行仍返回 409。通过实际 HTTP 完成两种修复各 4 次，路径集合、单文件和 ZIP 字节、链接目标、uid=1000、files 根 inode、保护快照 ID 集合全部核对通过。

后置 Docker die 事件查询首次直接观察到后 4 条退出码 73，未保存完整事件；后续查询已无这四条。期待后置查询返回全部 8 条的证据断言失败，原记录明确保留这一限制，不补造事件。每次实际 PID 1 退出与容器自动重启由已保存的标记、HTTP 中断及逐次 RestartCount 证明；全部 8 次退出码 73 来自钩子源码，只有首次观察的 4 条来自 Docker die 事件。
