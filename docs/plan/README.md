# 桌面客户端与独立工作区升级

本计划组织桌面优先的客户端、本机运行核心、独立工作区、长期记忆、文档知识检索、文件与执行环境，以及 Skill 兼容升级。这里描述待讨论和待实施的设计；现有能力仍以[架构说明](../architecture.md)、[机制说明](../harness.md)及源码为准。

## 授权与实施状态

当前授权为调研、设计讨论和计划文档维护。尚未开始产品实施、数据迁移、客户端打包或 demo 开发，也未运行本项目的 Tauri 原型。

用户已明确无需另建工作区／RAG 样本来证明升级方向；样本验证不作为规划前提。实施后的行为检查仍应覆盖数据隔离、来源、更新删除、恢复与检索结果，不能将方向认可表述为实现已经验证。

## 已确认的需求与约束

- 桌面端为主，必须能够独立运行，不能要求先部署另一个 RayAgent 服务。
- 移动端为辅，是否实施及具体功能范围继续讨论；优先争取同一套前端代码构建桌面与移动客户端。
- Flutter 不再作为本轮客户端路线；客户端比较集中在 Tauri 和 Electron＋React Native。
- 项目升级为长期工作区，不同工作区之间的记忆隔离，同一工作区内的多个会话共享有效背景。
- 工作区需要容纳大量文档，将 RAG 纳入知识能力设计，同时保留独立的记忆与笔记职责。
- 文件操作应减少重复选择、逐批上传和副本搬运，桌面端应围绕本机材料组织工作。
- Skill 需要兼容 `.agents/skills/`、`.codex/skills/` 等常见 Agent 目录，并考虑其他通行目录。
- 文档按职责维护有效方案，不积累逐轮讨论记录、历史阶段台账或已完成计划。

专业角色只是工作区配置的示例，不据此硬编码业务分类、提示词或记忆规则。工作区身份与角色模板分开，相同角色的两个工作区也不共享私有记忆。

## 建议方案与待定范围

当前建议以 Tauri 统一客户端为首选，保留现有 React／TypeScript 界面，将 Next.js 客户端工程调整为 Vite SPA；Rust 负责原生集成，Python 保留 Agent 核心。桌面使用嵌入式业务存储与检索，按需准备本地执行和自动化浏览器；移动端作为连接桌面核心的辅助客户端。

Tauri 的跨端构建与桌面 Python sidecar 有官方及开源依据，但尚未实际验证 RayAgent 的迁移结果。Tauri 定案、Vite、SQLite、LanceDB Embedded、Python 打包方式、本地执行默认权限、移动端连接方式等仍属于建议方案，不能当作用户已逐项批准的技术决定。

## 依赖与讨论顺序

先明确桌面独立运行的交付口径、首批操作系统、工作区身份及数据归属，再确定存储和文件访问契约。客户端、记忆、知识检索和 Skill 可以沿这些共同契约分别细化；执行环境接入同一工作区资源与运行身份。

移动端复用客户端与核心协议，不反向要求桌面核心立即迁入手机。配对、远程访问与缓存应在桌面接口边界确定后设计，不默认引入云端账号或双向数据同步。

现有 Agent 单循环、模型与协议适配、工具管线、事件投影、审批和交付身份是优先保留的基础；数据库专有行为、Docker 准备耦合和浏览器生命周期需要按专题重新适配，不能只更换连接地址或实现类。

## 整体完成条件

- 桌面安装与启动满足约定的独立运行口径，工作区常规使用不依赖手工部署原服务栈。
- 客户端完成已约定平台的真实构建与运行检查，移动端范围如获授权则按其能力边界交付。
- 工作区隔离、记忆共享、文档检索、文件与 Skill 版本关系一致，停止、重启及失败出口有明确结果。
- 现有数据的迁移、备份与回退边界清楚，用户原目录和私有材料不被误删或串用。
- 检查入口归入所属服务指南；有效机制合入正文，重要设计依据合入背景，完成后清理本计划。

## 后续优先讨论的问题

1. 独立运行是否要求全部内置工具无需额外运行时，以及模型联网、首次组件下载和离线能力的边界。
2. 首批桌面平台、CPU 架构及移动端优先级；Tauri 是否正式定案。
3. 工作区与本地目录是一对一还是允许多个材料根；旧 Web／服务端部署是否继续维护。
4. 嵌入式存储、记忆组织、Embedding 和文档解析方案，以及现有数据如何迁移。
5. 本地 Shell 与浏览器权限、可选隔离环境，以及移动端连接桌面的方式。
