# 桌面客户端与工作区升级

本计划把 RayAgent 从需要部署的 Web 服务升级为本机运行的桌面应用：以本地文件夹作为工作区，为每个工作区提供隔离的长期记忆与知识检索，并组织本机核心、文件与执行环境、客户端分发及 Skill 兼容。范围与技术基线已确认，产品尚未实施升级；现有能力仍以[架构说明](../architecture.md)、[机制说明](../harness.md)及源码为准。

## 授权与实施状态

当前授权为调研、设计讨论和计划文档维护。尚未开始产品实施、客户端打包或 demo 开发，也未运行本项目的 Tauri 原型。

用户已明确无需另建工作区／RAG 样本来证明升级方向；样本验证不作为规划前提。实施后的行为检查仍应覆盖数据隔离、来源、更新删除、恢复与检索结果，不能将方向认可表述为实现已经验证。

## 产品定位与形态

RayAgent 是面向长期工作的桌面 Agent。用户为一件事打开一个本地文件夹，在其中分多次对话推进；Agent 读取文件夹中的材料，把成果写回文件夹，并在这个工作区内积累记忆。产品不以编码为中心，写文件、运行脚本是可用的工具能力；心理咨询、产品设计、学习一个领域、制作演示或小型网页，都是内容不同的工作区，而不是不同的产品模式。

与云端 Project 类产品相比，材料在本机文件夹原位而不是上传副本，成果直接落回文件夹，业务数据与索引保存在本机，对话模型由用户配置。

- **首页**：工作区列表与独立对话入口。
- **工作区**：一个本地文件夹，加上工作方式、记忆、会话与检索索引；不同工作区之间互不可见。对象模型见[工作区与记忆](workspaces-and-memory.md)。
- **对话**：工作区里的一次具体推进，沿用现有单循环、计划、审批与工具。
- **独立对话**：不属于任何工作区，不写入记忆，不查询工作区索引。

## 产品闭环

用户打开文件夹并说明这里的工作方式。每次对话开始时，Agent 带上工作方式、常驻记忆和与本次问题相关的材料；对话中读写文件夹、执行工具；结束后成果留在文件夹并进入索引，可复用的结论经提炼进入记忆；用户通过“本次参考”和记忆提示纠正。下一次对话无需重新交代背景，另一个工作区看不到这些内容。

闭环成立以这两点同时可观察为准，不以某项组件已经接入为准。

## 已确认的需求与约束

- 桌面端为主，必须能够独立运行，不能要求先部署另一个 RayAgent 服务。
- 首个交付只覆盖 macOS Apple Silicon，以内部包在 Mac 上形成完整闭环；Developer ID 签名与公证、自动更新、Windows x64 适配和移动端都放在后续阶段。移动端为辅，按 Android、iOS 顺序交付，共用同一套前端代码。
- 客户端采用 Tauri；Flutter 和 Electron＋React Native 不作为并行实施路线。
- 移除独立 Web 客户端和原服务部署交付，不提供本机浏览器访问入口；不迁移旧部署数据。
- 一个工作区绑定一个本地文件夹，Agent 直接读写原位文件，不再上传副本或进入容器沙箱。
- 工作区之间记忆与知识隔离，同一工作区的多个会话共享有效背景。
- 工作区需要容纳大量文档，纳入全文与语义检索；工作方式、记忆与文件各有归属，不设笔记与独立说明页。
- Skill 需要兼容 `.agents/skills/`、`.codex/skills/` 等常见 Agent 目录，并考虑其他通行目录。
- 文档按职责维护有效方案，不积累逐轮讨论记录、历史阶段台账或已完成计划。

专业角色只是工作方式的内容，不据此硬编码业务分类、提示词或记忆规则。使用相同工作方式的两个工作区也不共享记忆。

## 技术基线

按 Tauri 统一客户端、React／TypeScript＋Vite SPA、Python 核心实施。Rust 只承担平台集成；业务使用 SQLite，知识索引使用 SQLite FTS5 与 LanceDB Embedded。文件直接访问工作区文件夹，Shell 和自动化浏览器按需准备。移动端采用连接桌面核心的辅助客户端，不在手机复制 Python 运行栈。

以上技术基线及[决策清单](decisions.md)中的产品范围已由用户确认，各专题按此落地，不再保留待选的工程分支。计划确认不等于已实施或验证；本轮不改产品实现。

独立运行的交付口径为：无需另行部署 RayAgent、PostgreSQL、Redis、Nginx 或 Docker；安装包提供 Python 核心与基础工具运行时，浏览器、Embedding 和 OCR 作为受管组件按需下载，离线组件包随 Mac 正式发布提供。模型推理使用配置的外部 API，不默认内置完整对话大模型。

## 里程碑与依赖

首个交付只覆盖 macOS：先打通桌面底座，随后交付工作区闭环（文件夹工作区、工作方式与记忆、本机执行），再扩大材料规模（全文与语义检索、Skill 多来源），最后以 Mac 内部包完成闭环交付。Mac 正式发布（签名、公证与自动更新）、Windows 适配和移动端都是后续阶段，不阻塞首个交付。阶段与依赖见[实施与交付](implementation.md#阶段划分)。

每项能力在所属工作包内接入上下文装配与工具，不集中到最后汇合，避免记忆要等检索、OCR 和 Skill 全部完成后才能被运行使用。

现有 Agent 单循环、模型与协议适配、工具管线、事件投影、审批和交付身份是优先保留的基础；数据库专有行为、Docker 准备耦合、托管副本、浏览器生命周期以及说明与笔记需要按专题替换，不能只更换连接地址或实现类。

移动端复用客户端与核心协议，不反向要求桌面核心迁入手机。配对、远程访问与缓存在桌面接口边界确定后实现，不默认引入云端账号或双向数据同步。

## 首个交付的完成条件

- Mac 内部包在未装开发环境的 Apple Silicon 机器上满足独立运行口径，工作区常规使用不依赖手工部署原服务栈。
- 新会话无需重新交代背景即可使用同一工作区的工作方式、记忆与材料；其他工作区和独立对话读不到这些内容。
- 文件夹、记忆、检索与 Skill 的版本关系一致，停止、重启及失败出口有明确结果；用户文件不被误删或串用。
- 内部包升级保留工作区数据，旧二进制不打开新 schema。
- 独立 Web 产品与原服务部署路径从实现、构建、检查和说明中移除，不提供本机浏览器访问入口；保留共享界面、本机通信与成果预览。
- 检查入口归入所属服务指南，已实施机制合入正文，重要设计依据合入背景。

后续阶段各自的完成条件见[实施与交付](implementation.md#后续阶段)：Mac 正式发布要求签名公证包在干净 Mac 上直接打开并可更新；Windows 要求重复首个交付的全部检查；移动端依次完成 Android、iOS 真机交付。

## 范围与计划维护

首个交付不包含 Developer ID 签名与公证、自动更新、Windows 和移动端。整个计划不建设多人协作、云端双向同步、多设备共享同一工作区、一个工作区绑定多个文件夹、手机本地 Agent、任意崩溃点自动续跑、任意格式理解或所有 Agent 专有扩展兼容。保留扩展端口，不为这些能力提前引入分布式调度和账号系统。

跨模块约束只在共享契约维护，详细规则归所属专题。工作包只组织尚未实施的工作，开始后更新实际状态，不追加日期日志。实施后的默认数值归参数页，命令归服务指南，有效机制归正文。首个交付完成后删除计划中已落地的重复设计，只保留后续阶段；全部阶段完成后清理本计划。
