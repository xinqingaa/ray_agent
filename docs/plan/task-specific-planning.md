# 执行计划的任务语义与内容设计

执行计划需要让用户看见 Agent 如何解决当前问题。对于内容制作任务，主题推导、内容取舍和论证设计属于实际工作，应与制作、验证和交付一起进入计划；只有文件操作与交互检查的清单不足以表达这条执行路径。

用户已明确选择“执行计划体现主题推导和内容设计，同时保留制作与验证步骤”，并于 2026-10-14 授权按修订方案实施。实施中进一步要求重点评估清单简练性、停止重复大任务。当前通用规则改写与定向检查已完成，已保存真实执行样本，最终采用只生成计划的轻量检查。不将演示稿中的操作指南当作 Agent 已实际执行的任务，也不默认增加独立内容大纲面板。

## 问题定位

### 任务拆解集中在制作形式

两份清单都把核心内容设计收进“制作文件”或“确定大纲”的宽泛动作，却具体展开了浏览器检查。这使用户能看到 HTML 如何完成，难以看到主题怎样被讲清、重要问题如何取舍，以及内容核对发生在哪一步。

RAG 任务尤其需要承接用户已表达的理解，计划却没有呈现“核对现有理解”“串联两条链路”“设计贯穿示例”等工作。知识库任务要求的是一份讲解搭建方法的演示稿，合理的执行条目应是“设计信息组织与采集检索的讲解”，不能写成“已搭建用户个人知识库”。

### 规划时机缺少明确要求

知识库计划的首次登记发生在制作完成之后，无法支持事前理解或执行中观察。进度机制没有对首次复杂任务建立计划的时机进行强制判定：没有计划时 `PlanProgress.reason` 返回空，承接、范围和续接提醒都以已有计划为前提，`missing()` 未被调用；已确认计划承接和范围变化的检查也不等于首次任务规划。

该会话的首次计划还有一个可观察的直接触发：seq 31 的浏览器核验调用携带 verification，因成果尚未登记而失败（“verification 引用不存在的成果 id”），随后 seq 35 才首次调用 `update_plan`，同时登记成果并把“编写”标为已完成。计划在这里首先是成果与核验登记的前置条件，所以更像补登记账目，而不是事前规划。这是单样本观察；RAG 会话在写文件前就已建立计划，说明并非所有任务都会如此。系统提示“尽早形成整套可用初版”也可能把模型推向先写文件，需要和计划时机一并措辞，避免两条规则互相拉扯。

建议先改进模型指令中的时机要求，不直接以调用数量、写文件工具名或业务关键词阻断执行。它们不能可靠区分简单操作和需要规划的任务。成果与核验登记不应成为计划内容的唯一来源，也不能为了让计划看起来事前建立而补造。

### 通用规则主要约束结构和简洁

现有系统提示及工具说明要求简短动作标题、独立动作、两层结构、稳定身份和及时更新，但没有清楚定义“独立动作”应如何承接当前目标的具体问题与判断。简短本身合理，缺口在于简短条目仍可十分空泛。

直接对应的现有措辞有三处：“条目写简短动作标题……不把规格、来源和执行说明堆在清单里”“已知关键子步骤首次列出，其余在进入阶段时补充”，以及上节的“尽早形成整套可用初版”。前两句以格式简洁为唯一方向，没有说明内容判断也要进入清单；同样的句子在中文系统提示、英文系统提示和 `update_plan` 工具描述中各写了一遍，修改必须同步。

计划工具校验身份、层级、状态、范围来源和成果登记，不判定内容语义是否充分。步骤提醒针对进行中阶段缺少子项或当前步骤，既不会展开已完成的制作阶段，也不会识别“确定大纲”是否掩盖多个重要内容决策。这是程序职责的边界，不能把结构合法当作规划质量合格。

### 展示不是主题缺失的主要原因

原始计划事件本身就没有主题设计条目，当前前端按阶段和所属子步骤展示，不能从未记录的数据恢复这些工作。用户粘贴中的重复编号与列表排版可作为独立界面问题核对，但本次没有复现页面排版，不能判定其具体来源。扩大面板或增加字段不能直接解决语义空泛。

以上结构与时机判断来自事件和源码；“规则偏重制作形式，可能促成模型选择通用清单”属于原因推断，仍需真实任务对照验证。

### 清单简练性评估

首次实施确实增加了主题工作的可见性，但把“保留任务对象、问题或结果”理解成了罗列整个内容目录与规格。知识库首份初始清单为 6 行、227 字，单条最长 55 字；RAG 首份为 6 行、263 字，单条最长 78 字。另一次 RAG 从 5 个阶段展开到 15 行，出现父阶段与子步骤重复说明、标题兼任内容大纲的问题。标题具体并不等于标题需要详细。

短标题检查中，RAG 单条最长缩至 15 字，但仍有 16 行，表明总长度还受到拆分粒度影响。最终规则同时约束语义、表达与粒度：条目用动作与具体对象或结果组成短标题，不附内容列表或解释；完整大纲、规格和核验条件留在目标、范围或正文；按阶段成果合并相关动作，不逐项登记内容、组件和检查手段，不复述父阶段。首次列全部阶段与首阶段关键步骤，其余进入时展开，计划模式采用相同口径。最后的粒度修改只做静态与定向检查，不再追加模型采样。不规定固定条目数或字数上限，也不将主题工作重新吞进“制作文件”。

| 过长表达中的主要问题 | 更适合清单的标题示例 |
|---|---|
| 一项内容定稿列出全部页面主题与框架 | 设计知识库内容主线 |
| 链路梳理列出全部组件与策略名称 | 梳理索引与查询链路 |
| 分镜设计列出所有图形类型和示例 | 设计 RAG 图形分镜 |
| 检查条目同时记录数量、操作方式、视口及预期断言 | 核验交互与离线使用 |

这些示例用于评估当前样本，通用规则只约束工作标题及细节归属，不包含上述主题名称。

## 设计方向

维持现有单循环、两层 stage/step、计划事件和成果契约，优先通过通用规划规则改善语义与时机，再用真实任务判断是否需要额外机制。

通用系统提示及工具说明采用以下原则，不加入知识库、RAG 或其他个案的术语和模板：

- 从用户目标中识别需要解决的具体问题、关键判断和预期成果，再组织执行阶段。条目应说明推进目标的实际工作，不只描述操作工具或交付形式。
- 对确实需要计划的任务，在主要工作展开前登记已知执行路径；可与首批业务动作同轮调用，不增加纯核对往返。已发生的动作如实记录，不补造事前规划或未执行步骤。
- 简洁工作标题保留足以辨识当前任务的对象或结果，大纲、规格与核验条件进入目标、范围或正文。按阶段成果合并相关动作，独立关键工作才展开；首次保留全部阶段和首阶段关键步骤，其余进入时展开。细节不逐项登记，父子标题不重复；不按页面、工具调用或固定数量机械拆分，也不把关键判断压成笼统动作。
- 内容推导、方案选择与关键判断属于执行工作。计划同时覆盖这些工作及制作、核验、交付；具体是否分为独立阶段由任务决定，不强制每项任务套用相同阶段。
- 区分 Agent 正在执行的工作与产物讲解、建议或模拟的步骤。计划的完成状态只描述实际执行范围，不把产物中的建议当作现实成果。
- 主题要求与交付约束都应有相应工作承接。核验依据来自要求、原材料或适用证据；格式和交互检查不能替代内容核对。

这些原则需要合并进既有段落，避免再追加一套冗长、重复的流程。直接回答和单次明确操作继续可以不建计划，不默认增加 Planner、第二模型评审、自动换模型、强制提问或业务关键词门禁。

## 两个任务的预期示例

以下是针对样本的执行计划示例，用于明确期望差异；不进入通用系统提示或工具说明，不要求真实模型逐字输出，也不表示原会话执行过这些步骤。

### 个人知识库演示稿

| 阶段 | 可独立推进的工作 |
|---|---|
| 设计知识库搭建的讲解路径 | 明确演示稿要解决的使用问题与适用假设；组织工具选择、信息结构、采集加工、查找复用和维护的先后关系，并分配到 6 页 |
| 完善各页实例与讲稿 | 设计文件夹、标签或关联的具体使用例子；将采集到复用过程写成可操作说明；编写维护与启动步骤及逐页备注 |
| 制作离线 HTML 演示稿 | 实现页面与目录导航；接入按钮、方向键及随页更新的备注 |
| 核对内容并验证交付 | 核对搭建路径、例子和备注的一致性；实测翻页、跳转、备注与离线约束，并检查真实视口；交付文件和使用说明 |

第一阶段不能因用户只给主题就自动暂停提问，可以采用合理的入门受众假设。用户另有工具或使用背景时再据此调整。计划不会承诺为用户安装软件或建立实际知识库。

### RAG 讲解演示稿

| 阶段 | 可独立推进的工作 |
|---|---|
| 核对现有理解并确定讲解重点 | 区分用户理解中已有的环节、需要补充或澄清的关系；据此组织图形化的讲解顺序 |
| 串联索引与查询的完整过程 | 设计文档进入索引的过程；连接查询、召回、融合、重排与答案生成，并说明各环节的输入输出及条件 |
| 设计贯穿示例与图形动画 | 用一组文档和问题串联候选变化；核对示例计算；让图形和动画呈现数据流转而非装饰效果 |
| 制作并核验 HTML 幻灯片 | 实现演示交互；核对概念关系、示例与图示一致性，保留可选策略的适用条件；验证演示效果并交付 |

此处是教学内容工作的拆解，未授权搭建一个真实 RAG 系统。条目只给出计划层面应呈现的工作，技术内容是否正确需在产物中单独核验。

## 验收条件

结构测试只能证明契约未破坏，不能证明模型真的会生成合适计划。语义改进必须通过实际任务轨迹判断。

| 场景 | 关键检查 |
|---|---|
| 两个原始任务 | 主要内容制作前已有适当计划；能辨识主题问题、内容设计与关键核对；制作、交互验证和交付要求仍被保留 |
| 其他内容或材料分析任务 | 计划承接该任务的具体问题和判断，不套用样本的主题词或相同阶段；结论核对不被格式检查替代 |
| 软件修改或数据处理任务 | 条目反映诊断、实现或处理目标；没有强制增加不适用的内容设计阶段 |
| 简单问答与单次明确操作 | 直接完成，不为追求计划丰富增加清单、提问或额外核对 |
| 运行中变更与续接 | 保留稳定身份和有效成果，按新要求更新相关条目；不补造已完成工作，仍遵守来源与完成状态契约 |

实际验证范围遵从用户停止重复大任务的要求，采用已有执行轨迹和最终轻量规划，不能声称完成原建议的全部重复采样与跨模型对照。条目数量、字数、关键词不单独作为质量通过标准；同时判断主题辨识、独立工作、重复表达与阅读负担。记录请求数、计划调用数、完成耗时、交付缺口与计划参数输出量；输出增幅已促成标题规则收紧，不通过删除必要工作或设置固定条目数解决。

当前机制已合入 Harness、服务指南和代码地图；实际条件、最终轻量规划与保留限制维护在[计划与成果验收](evidence/plans-and-delivery.md#任务语义与清单简练性)，能力边界维护在能力文档。首次改写的大任务证据不冒充最终措辞的完整执行验收，停止样本不计成功或稳定失败。
