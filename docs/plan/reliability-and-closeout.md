# 计划可靠性、验证质量与收尾方案

日期：2026-10-11。分析基线：`53873fd8f71840a17bc475a842ea5628321c7dca`，结合[真实服务收尾评估](../research/project-closeout-review-2026-10-11.md)。状态：**已按用户批准范围实施、部署并完成有限验收；效率观察项保留**。第 1–7 节保留批准时的分析和范围，当前结果见第 8 节与验收记录；不重开 W0–W11，不包含框架迁移或课程同步。

## 1. 判断与优先级

| 问题 | 判断 | 推荐处理 | 完成口径 |
|---|---|---|---|
| 部署与源码不同 | 明确的发布一致性问题，不是模型能力问题 | 对齐选定版本，补构建身份及读回核对 | 能明确回答“实际运行的是哪份代码与提示词” |
| 计划进度滞后 | 确认执行没有结构化承接，过程仅靠提示与有限提醒 | 显式计划承接、当前运行的计划判断、有界核对及真实降级展示 | 不丢计划归属，不长期静默展示未经更新的阶段 |
| 生成内容错误 | 模型知识/推理影响上限；材料保真、验证工具和证据表达仍有改进空间 | 简洁事实依据规则、真实验证条件、独立验收 | 降低可避免错误，不能承诺自动证明任意答案正确 |
| 执行效率 | 有空间，主要是无效试错、零散验证与交付时机 | 修正工具说明，集中验证，关键检查后交付 | 正确性不退化，减少无意义往返；不预承诺提速百分比 |
| 文档与证据同步 | 有明确矛盾和陈旧表述 | 核对当前事实、区分实施/部署/测试状态 | 当前说明一致，历史证据仍保留原条件 |

推荐先完成部署基线、计划机制和文档收口，再完成验证工具与内容/效率调整，最后做一次有限真实回归。两批都保留自研单循环，不增加独立 Planner、全任务评审模型或通用成果验收平台。

## 2. 事实、根因与不能承诺的部分

### 2.1 部署差异

本次方案评估再次只读核对了先前发现的五个 API 文件，仍与工作树不同：中英文系统提示、计划提醒、计划工具说明和搜索工具说明。旧提示仍有“修复后复检一次即可”等措辞。当前健康检查不识别这种差异；镜像构建也没有明确携带产品源码指纹。

因此，先前真实测试不是最新提示词的完整验收。仅凭这次差异不能推断部署失败的具体操作原因，也不能推断更新到最新提示词就会解决计划问题。

### 2.2 计划问题

当前“按计划执行”只发送普通消息文本，没有携带被确认的计划身份。新运行会读取会话最新计划，但前端只显示归属本次运行的计划事件；模型未更新前，已确认清单会退出计划条。

当前提醒按有效工具批次计数：五批才提醒，每运行最多两次。清单更新和阶段完成仍由模型判断。这次两个执行分别在 8、9 次非计划工具调用之后才更新/建立计划，耗时约 36.7、42.7 秒；后者在新计划建立时已把制作项标成完成。

可以由程序保证的是归属、状态协议、核对机会和展示诚实性。无法只凭“调用了文件/浏览器工具”确定业务阶段，更不能由工具 success 自动认定步骤完成。将阈值从五改成三只是缩短间隔，不是完整修复。

### 2.3 质量与效率的关联

史实错误属于生成内容错误，浏览器交互成功不能纠正它。周报把“完成导出”扩写成“已交付使用”，则还涉及未遵守材料边界。

另外发现一个工具条件缺口：旧轨迹通过修改 body 宽度，甚至直接把 grid 改成单列来模拟手机布局，没有真正设置浏览器视口。这样的结果不能证明 CSS 媒体查询在手机宽度下会生效。此前评估用独立浏览器的真实 390px 视口补验后产物通过；这不能倒推出 Agent 自己的验证方法充分。

两版 HTML 使用 20、16 次模型请求，24、26 次工具调用，并非所有调用都冗余：卡片、答错/答对、重做和键盘检查有实际价值。但已知不支持的 file:// 试错、可合并的 DOM 读取、验证时手改 CSS，以及先清理服务再交付，都有改善空间。

## 3. 第一批：部署、计划与文档收口

### 3.1 明确发布身份，核对实际运行

建议为 API 和 UI 构建产物各保存一份小型构建清单，包含 Git 提交（可获取时）、是否有工作树改动、相关构建输入的内容指纹和构建时间。Git SHA 只用于定位，内容指纹用于区分同一提交之上的不同工作树。

- API 指纹覆盖应用源码、运行脚本及容器依赖来源；UI 覆盖源码、public、锁文件和构建配置。指纹算法按固定的相对路径顺序计算，明确纳入范围。
- 排除凭据、环境文件、运行中可变配置、缓存与本次文档证据；不把配置值或密钥写入清单。
- 清单随实际构建生成并进入最终镜像，不能只在部署时填一个可与镜像内容脱离的环境变量。UI 编译后没有原始源码，应读回构建清单，不拿编译文件与 TS 源码直接比对。
- 提供一个轻量核对入口，读取 API/UI 运行产物清单，与预期构建指纹比较；失配直接说明哪一端、哪个范围不一致。无需新增普通用户页面。
- 运行配置快照记录 API 构建身份；仍以已保存的实际系统提示和工具 schema 为该次模型请求的依据。旧运行缺身份时标为未知，不补写成当前版本。

部署时先保留运行中的实际配置，避免容器重建把页面中保存的模型配置替换为仓库默认值；等待活动执行和待审批运行妥善结束，不强停用户任务。更新后按服务指南处理网关上游刷新，核对健康、构建身份和一个新运行实际使用的提示词。已有等待回复运行继续遵守其冻结快照，不为对齐版本改写历史。

### 3.2 显式承接被确认的计划

建议在现有 chat 请求增加可选的执行计划信息，字段名称在实施时定稿。至少携带来源运行、计划 ID、计划事件序号和请求标识。

1. 页面按钮提交结构化引用，不能只靠“按计划执行”这句话识别。
2. 后端在受理事务中验证：计划属于当前会话；来源计划运行已完成；引用是当前可执行版本；有未完成项；当前没有活动运行。过期引用返回冲突并刷新清单，不静默执行另一个版本。
3. 新运行创建时，在同一事务内固定这份计划并发布归属新运行的计划事件，保留原 plan_id、步骤 ID 和来源。原计划事件不改写。
4. 页面立即显示已承接的清单；尚未选定执行项时显示“准备执行”，不自动把第一项标为进行中或完成。模型首批业务工具前选择当前项，可以把计划更新和业务工具放在同一次回复中。
5. 双击、网络响应丢失后的相同请求读回同一个受理结果，不再创建一次执行或向运行中注入重复“执行”消息。请求标识需要持久化并在会话受理锁/事务中核对，不能只依靠按钮 disabled。

用户手动输入“继续”或“按计划执行”仍按普通自然语言处理；没有结构化引用时，不用关键词自动确认某份旧计划。

### 3.3 区分当前任务判断、步骤更新与进度核对

复用计划工具，增加轻量的“核对当前步骤”和“本次无需计划”语义，而不是要求每次都重写整张清单。具体字段/API 形状可在实施时确定，以下行为必须固定：

| 场景 | 推荐行为 |
|---|---|
| 简单直接回答 | 直接结束，不强制调用计划工具，不增加规划请求 |
| 普通对话中的短工具任务 | 沿用按需计划，不因一个读文件或计算动作强制写清单 |
| 明确确认的计划开始执行 | 使用已承接清单，在首批业务动作前指定当前步骤 |
| 已完成计划之后的新一轮工具工作 | 第一轮上下文明确旧计划已关闭；首个写操作前要求模型选择“建立本次计划”或“本次是简单修改”；选择可与动作同批完成 |
| 当前步骤仍在进行 | 轻量确认“仍在此步骤”，不虚增完成数、不重写所有标题 |
| 转入下一阶段 | 更新旧项、新项状态并保留步骤 ID；程序只校验合法性，不推断真实性 |
| 运行中用户补充或改变范围 | 标记需要重新核对范围，保留原计划，模型据新要求决定延续或调整；不能自动清空已完成项 |

普通对话未建计划且持续执行多个批次时，也触发一次“是否需要计划”的核对；允许明确回答无需计划。不能用任务关键词或工具名硬判复杂度，也不把某个 write_file 等同于“开发阶段完成”。

### 3.4 让核对有边界，不再只追加两句提醒

建议已有计划每连续 **三批有效业务工具**未更新/确认时进入核对点；这是待验证初值，不是最优阈值承诺。纯轮询、失败、拒绝和计划工具本身不推进间隔。

- 在下一次模型请求前给出简短的本次计划、当前步骤及“更新或确认仍在此步骤”的动态上下文。核对信息进入已有上下文事件，保持系统提示的稳定前缀。
- 正常路径允许模型先核对、再在同一回复中执行已知参数的业务调用，减少额外模型往返。
- 明确计划首次执行、旧计划已结束后的新写操作、以及到期核对点，若模型仍跳过必要声明，则最多进行一次程序纠正：该批业务调用不执行，逐调用返回明确的未执行结果，再请求其核对。不能暂存后自动重放旧调用，也不能产生悬空 tool_call。
- 若纠正后模型仍不遵循，转为可观察降级：允许任务按原工具权限继续，计划区明确“进度未确认”，保留真实工具活动，不再将旧步骤暗示为当前阶段。记录核对失败供验收，不能用最终产物成功把这项判为通过。每个用户输入范围最多一次这种额外纠正，避免反复拦截造成新的效率问题；模型恢复主动更新后可以恢复可信展示。
- 审批或提问续接从本运行事件恢复计数与降级状态，不重新获得无限纠正次数。新增合成核对不能算作用户新输入，也不能重置运行预算。停止仍立即进入现有取消路径。
- 轻量确认保存“已核对”的事实，UI 不增加一行重复清单，也不把未变化步骤显示成新版本或刚完成。

这里选择有界纠正和明确降级，是为了避免“模型不更新计划就永远不让工作继续”的新限制。硬保证是：已确认计划不丢失、需要核对时有可回放记录、无法核对时不误导。步骤语义是否准确仍依赖模型与任务证据；如果要求每个动作必须经一个确定性阶段调度器批准，那是另一种执行架构，不属于本方案。

### 3.5 文档同步

实施完成后将事实分别合入产品、能力边界、UI/API 指南；计划归属和请求受理路径改变时再更新架构及设计取舍。代码定位和检查入口集中维护在[代码地图](../code-map.md)。当前已确认需要收口的例子：

- 运行预算计划开头称“真实模型复测结果见文末”，末尾仍记未复测。保留当时实际检查；若没有可追溯运行记录，明确“尚无可核对的真实复测记录”，不能替用户断言已执行或未执行。
- 设计取舍仍写“项目没有删除入口”，与当前永久删除实现及产品说明不符，应替换为当前事实。
- 维护入口的历史产品基线应明确是该阶段验收基线，不能让旧提交看起来代表最新部署。
- 计划展示和提醒次数的旧描述在机制改变后替换；图片、统计等未被本轮实际覆盖的边界继续保留，不因为相邻功能通过就改成全部通过。

保留原始评估和历史验收为分析快照，不回填成新版本通过，不迁移旧会话数据，不顺带改课程。阶段结论和关键证据索引继续只在维护入口汇总。

## 4. 第二批：改善质量与有效执行效率

### 4.1 事实依据与材料保真

替换、整理现有相关提示，不叠加一套冗长验收规则。推荐增加两条简洁原则，中英文一致：

> 整理、改写或汇总用户材料时，保留原有事实、范围和确定程度，不把未提供的完成状态、效果或因果当作事实补入。为表达需要作出的假设，应与材料事实区分。

> 验证按任务的主要风险选择：数据核对计算与口径，内容核对影响结论的关键事实，界面核对真实交互条件。可以查证且需要来源时，核对用户材料或可靠原文；不能以格式、页面可用或模型自检代替事实依据。

用户明确不联网时继续遵守；优先检查已有材料和内部一致性，只在影响结论的具体不确定处说明限制，不给所有句子机械加免责声明，也不一律提问。对郑和案例，不能硬编码一个历史答案进系统提示；需要验证的是模型会利用给定年代材料、区分“开始于”和“全部发生于”、发现证据不足时不扩大断言。

默认不增加第二个模型审阅每条回复，不自动切换更贵模型。同一模型重复自检可能重复原来的错误。真正的改进依据是独立样本中的错误是否减少，而不是“自检工具调用成功”。

### 4.2 补充真实浏览器视口能力

建议增加一个小型浏览器工具或现有工具的明确扩展，设置指定 tab 的实际 viewport，支持恢复原值，并返回实际 innerWidth/innerHeight、页面尺寸和可选观察。名称尚未确定，不能写为现有能力。

- 尺寸参数在工具层校验并设置合理上限，作用范围是明确标签页；不通过修改业务 CSS 达到尺寸效果。
- 通过既有工具管线、策略与日志；视口变更会触发 resize 处理，因此不自动列为计划模式只读工具。
- 与现有浏览器写操作同批按顺序执行，失败不继续后续依赖动作。
- 记录修改前视口及本运行所有权，结束、停止或失败时只恢复本运行修改且仍持有的标签页；等待续接按既有浏览器生命周期保留记录，不能重建运行器后丢失恢复依据。
- 用真实 Chromium 核对媒体查询是否切换、尺寸是否真实、复原和异常退出。视口模拟仍不等于真实手机、触屏或软键盘验收。

对自己生成的页面，鼓励用少量批量断言检查关键行为并返回检查摘要；断言应基于用户要求或独立预期值，而不是从当前 DOM 读出值再把它当作正确答案。外部业务网站仍优先使用已有元素引用和标准动作，不把任意 JS 执行作为所有网页的默认路径。

### 4.3 减少无效试错，调整交付时机

- 浏览器导航工具说明明确支持 HTTP(S)/about:blank、不支持 file://，并说明本地成果可通过沙箱内静态服务验证。首批不放宽 URL 协议，不另建通用预览服务。
- 验证参数已知、相互独立时合批；后一步需要前一步结果时保留分轮。目标是减少模型往返，不是无条件减少有价值的检查。
- 对自建页面集中核对卡片、答题、重置、视口与溢出；只返回足以判断通过/失败的结果，失败再定向展开，避免多轮打印重复结构。
- 将“写好立即交付”明确为“主体完整且关键检查通过后交付”。清理临时服务和可选美化可以随后完成；不能为了早交付跳过数据/内容/交互的主要检查，也不为每次小改产生一个永久附件。
- 临时进程按本次创建的进程/会话归属清理，避免宽泛 pkill 匹配到当前 Shell 导致后续检查未运行。这次追加版本在交付后另起了一次 Shell 补查，说明清理方式值得一并调整，但不需要重做进程管理系统。

此次已有“截图可能满足普通文件交付检查”的局限继续保留为明确边界。它不是这六次任务失败的原因；若要彻底改成按成果类型和版本验收，需要先设计成果契约，不并入这次轻量效率修改。通用成果登记、自动补存、崩溃恢复和成本硬预算仍属后续独立范围。

## 5. 实施顺序与影响范围

| 顺序 | 范围 | 主要影响 | 退出条件 |
|---|---|---|---|
| A | 构建身份与部署核对 | 构建配置、部署检查、运行快照 | 运行内容可与选定输入核对，保留原配置 |
| B | 计划承接与有界核对 | 受理协调、循环/计划工具、事件、前端投影 | 确定性契约测试通过，无重复执行或虚假进度 |
| C | 验证工具及简洁原则 | 浏览器协议/适配、工具策略、提示词 | 真实视口验证通过，主要质量检查不缩水 |
| D | 部署、有限真实验收、文档收口 | 当前事实文档、关键证据 | 新行为实际可见，问题和未验证范围如实保留 |

第一批为 A+B 及相应文档，第二批为 C，最终 D 合并做一次有限验收。初始部署核对可以只读进行；需要更新服务时再按部署流程执行。若只完成第一批，只能宣称部署与计划问题的覆盖范围，不能把第二批记为已修复。

不增加依赖或数据库表作为默认前提：优先复用现有运行快照和事件 JSON，但新增事件字段、请求标识持久化、并发受理与恢复仍必须验证；若约束需要数据库唯一性保护，应在实施前明确迁移，不用进程内缓存假装持久幂等。

## 6. 验收：先确定性检查，再少量真实任务

### 6.1 确定性契约

使用既有脚本化模型、实际循环及组件检查，重点验证行为，而不是只断言提示词含某句话：

- 计划受理：旧引用、其他会话引用和并发提交不能执行；相同请求的受理读回不创建重复任务；计划绑定事件先于首个业务工具且刷新后仍存在。
- 计划核对：到期后可更新或确认仍在当前项；简单修改可声明无需计划；未声明时单次纠正不执行该批业务工具，所有调用结果配对完整；再次不遵循时只降级展示，不无限拦截。
- 续接与控制：等待、审批、压缩恢复计数；真实新输入触发范围核对，合成核对不重置预算；停止后没有新的业务执行。
- 前端：准备执行、进行中、无需计划、进度未确认和终态不混淆；确认仍在原步骤不新增清单噪声；下一任务不会沿用上次完成数。
- 构建核对：相关源码改变使指纹改变；仅文档或排除的配置变化不伪装成产品改动；旧产物和未知身份能被识别。API/UI 最终产物分别核对。
- 浏览器：真实 viewport 和媒体查询、指定标签页、复原、失败及停止路径。断言不得靠修改被测页面 CSS 才通过。

涉及事务与幂等的用例只使用独立测试库；新增视口检查使用受控 Chromium。相关服务指南是执行命令入口，不为了本次验收再复制一套运行手册。

### 6.2 真实模型检查与停止规则

不在方案阶段调用真实模型。本轮实施后的建议预算为 **七次运行**，保持模型、思考档位、工具配置与样例材料固定；无失败或新的异常，不额外重复。

| 场景 | 运行数 | 主要观察 |
|---|---:|---|
| 简单文案、简单单文件动作 | 2 | 无不必要清单、追问和额外规划模型往返；文案不扩写完成状态 |
| 计划 → 点击执行 → 同会话追加改版 | 3 | 计划立即归属本次运行；制作前有本次计划判断；阶段核对及时；两版可下载且旧版保留 |
| 带明确年代/范围材料的事实整理 | 1 | 能利用材料纠正跨时期概括，不虚构来源或突破禁网要求 |
| 含重复/缺失/退款的表格交付 | 1 | 独立重算、源文件保留、实际下载和预览正确 |

HTML 内容仍独立核对关键史实，浏览器交互用真实宽/窄视口；不因为“已完成”或模型声称验证通过就判成功。上述七次是定向抽查，不证明通用错误率下降；如果失败，保留原结果并只补测受修复影响的样例，不为了凑通过反复试跑。

记录首个计划归属、首次有效核对、首次交付、请求数、失败工具及模型实际耗时。计划机制新增的必要开销单独说明；历史 20/16 次请求只是观察参照，因部署提示词和冷暖条件不同，不用于宣称严格性能提升。正确性、状态可信和交付先通过，再判断请求是否收敛；不设“必须快 30%”或“一律十轮内”的指标。

默认不复测全部项目恢复、永久删除、MCP/A2A、真实 TTL 或 200k 长任务；预算末段用确定性用例验证，不更改真实服务上限去追求故障。保留这些边界，避免把有限维护扩成一轮全面产品认证。

## 7. 收尾后的定位

本方案完成后，目标是一个版本可辨认、计划过程更可信、验证更有效的本地 Agent 工程。它能减少软件机制造成的不确定性，也能帮助模型用好已有能力，但不等于获得更强模型的全部知识与推理能力。

收尾应以实际证据逐项确认。若计划仍频繁降级、原始事实继续被扩写，或效率改善来自减少关键检查，应如实保留未通过项，不以“所有任务都 completed”关闭问题。
