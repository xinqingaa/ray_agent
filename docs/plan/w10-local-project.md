# W10：可靠受理与发送恢复

所属：[总计划](README.md)。本文件保留现行设计与验收，进度只记总计划。旧方案通过Git历史追溯。

## 设计契约

**R2 chat 与审批受理不等待沙箱（高优先级）。**

返工前 chat 在会话锁内调用 _create_task，同步创建容器；HTTP 超时后的受理结果可能不清楚。改为先持久化消息和运行并返回 ChatAccepted，再在后台创建/启动；不单纯延长前端 30 秒期限。

后台启动必须有清晰所有权：

- 受理时登记 run_id 对应的启动记录/输入通道，第二条消息能注入同一 run；不能被当前“无 runner 则 runner_lost”分支误判并创建新 run。审批续接同理。
- 耗时创建不持会话锁；停止及时落 cancelled 并取消启动记录。to_thread 的 Docker 创建不保证随协程取消结束，返回后检查 run 仍活动，否则清理迟到容器，不 invoke、不写入。
- 后台成功后在锁内重验 run_id/状态与项目归属，防止旧任务覆盖新任务的 sandbox_id/task_id；失败写可识别的环境准备错误及终态。创建/销毁、引用更新与异常清理归基础设施/应用层，不塞进路由。
- API 重启沿用 W7 启动扫描，遗留 running 被中断，不建持久调度框架。用 fresh UoW，不能让后台协程共享请求中的事务对象。
- 保持 run 状态小集合；界面以真实“准备执行环境”activity 表达启动，不显示为已经在模型思考。定义事件来源，并同步 W3/W4 契约。
- 项目启动还受 [W11 文件操作准入](w11-project-workspace.md#文件操作互斥与失败收敛)约束：受理事务先检查并登记 run/待落盘附件关联，后台按旧写入者核对→项目附件发布→运行前快照→启动沙箱→沙箱附件同步→invoke 的次序协调，不能在快照前启动保留容器。终态后的项目环境收尾是独立文件占用，不改变 run 终态；W10 的迟到创建与 W11 的 settling 必须按 run_id/operation_id 核对，收尾未完成不允许新启动。独立对话不改沙箱寿命，waiting 续接不重做快照。

测试用事件闸门模拟慢创建，不真的睡 60 秒：及时受理、第二消息不另开 run、停止可响应、停止后创建返回不启动、失败能终态、审批续接、同一会话不重复建任务。W11 再补跨会话的项目互斥。

**R3 首次发送与超时不丢草稿、不重复执行（高优先级）。**

首页与会话页共同处理文字、附件 id、Plan、项目和已建 session id。初始发送失败回填并停在同一 session，清掉 URL 的 init；刷新不自动再发。普通发送也保留失败草稿。补回的截图显示 Nginx 502 HTML 被原样显示；非 JSON 网关错误应映射成简短的失败原因和重试入口，原响应只用于诊断，不作为正文文案。

30 秒超时/网络断连不是“未受理”的证明：先读取详情的用户消息 seq 与活动 run；已受理则继续订阅，不重新发，明确失败才允许手动重发。用现有 accepted seq/事件核对一次待提交内容，不扩展全局 request-id 平台；重复文本有歧义时提示核对历史，不自动猜测重试。文字不继续长期放 URL，首版用本标签的临时草稿传递并完成后清理。

创建失败、绑定失败、chat 未受理、已受理但响应丢失分别覆盖。W11 创建绑定原子性仍不能保证后续 chat 成功，不能两包互相把恢复责任推走。

**附件与受理协作：** 草稿保留原 attachment_id、已建 session_id、项目归属和模式，不重新上传已成功附件。读回消息时同时核对附件 id 与 accepted seq/run，不仅比对文字；重复内容无法唯一归因时保持“受理待核对”，给历史入口，不自动重发。项目附件暂存、规范化路径分配、`(project_id, attachment_id)` 副本关联和失败清理由 W11 负责，W10 在受理事务协调其提交并返回明确附件错误；未受理时草稿保持可重试，已受理后环境同步失败则显示该 run 失败而非再次发送。文件发布后 DB 提交明确失败与结果未知分别测试；结果未知时先读回，不删除可能已被接受的文件。只对同一上传 id 复用项目副本，不承诺不同 id 或普通 chat 的全局去重。

首次创建绑定失败、chat 409、附件预检/落盘失败、DB 回滚、响应丢失、后台沙箱同步失败都保留可核对的提交状态。首页刷新后的待提交草稿不自动执行；恢复时先定位既有 session 与消息结果。W11 的上传批次/恢复/收尾阻止原因原样映射为可读文案与处理入口，不将项目操作占用显示为 Agent 正在思考。

**R4 默认部署边界。**

默认 Nginx 发布到 127.0.0.1，显式配置才能对外绑定；当前面向受信任单人操作者，无鉴权。不宣称已做局域网隔离实测。

**返工验收与 docs。**

- 当前只验 R2、R3 和 R4 的默认 loopback/无鉴权边界；R1、R4 其余、R5 的旧路径/Git 验收均废弃，不要求补仓库/diff 截图。相关后端检查与 UI 类型/lint/build/观察通过，命令仍维护在所属服务指南。
- 真实 Docker与浏览器冷启动发送→受理→准备环境→终态；慢创建/停止/迟到创建/重建/响应丢失/错误读回均有证据。项目场景加上传批次/恢复/收尾占用时的 409、附件落盘后 DB 回滚或未知结果、同附件 id 重试不重复副本、已受理后沙箱同步失败不重发；独立对话回归不退步。
- 原报告只保留为当次记录；重验浏览器首发、失败与核对后手动重试，截图记录完成或明确失败态，不把 API 成功当浏览器流程成功。项目共享写入与恢复故障按 W11 验收，最终评测与版本记录见总计划及W11验收。
- 实现后同步能力边界、架构（启动/资源路径确实变化时）、代码地图、运行指南、UI DESIGN；计划阶段只修改计划与审计记录。

项目实体、托管文件快照、文件操作占用、归档、跨会话项目锁与旧写入者收尾由 W11 负责；压缩耗时与 contextWindow 口径由 W9 负责。旧不做清单的逐项取舍转到总计划，不能继续用旧排除项阻止有价值的工作。

首发创建需要有限创建标识与读回，未知结果保持同对象；项目占用拒绝不遗留空会话；受理核对包含附件、模式与 seq/run。本轮验证完成前不记为已具备。

## 独立对话按需准备沙箱（2026-10-08，已批准）

依据既有纯回答运行的 6048 ms 沙箱准备与 684 ms 模型耗时，下一步延后资源准备。范围与依赖见[总计划](README.md#浏览器与执行效率复核及下一步2026-10-08)。资源代理用于独立对话；初始与追加附件仍在入模前触发准备和同步。项目任务沿用原准备路径，不改变 W11 占用、旧写入者、附件发布和快照顺序。

### 设计

- 受理、运行事实源和模型快照仍先建立；无资源需求时可直接进入模型循环。既要延后应用层的容器创建/重连，也要延后运行器的 ensure，不能只删除 ensure 却仍提前 create。
- 由应用协调层管理唯一的资源准备入口，通过领域协议向工具提供按需资源；首次文件、Shell、浏览器、web_fetch、交付或大结果落盘才准备沙箱。搜索/MCP/A2A 若返回大结果，也必须能在整形写文件前触发准备。不新增模型调用来分类任务，不自动删工具。
- 同一 run 多个资源请求共用一次准备；策略和计划模式检查先于资源副作用，拒绝调用不创建沙箱。新附件注入必须先按既有同步规则准备资源，完成后才交给模型，不只检查首条消息。
- 等待/审批恢复沿 W7 页面所有权契约保留已有资源；无沙箱的运行停止不触发创建。创建中停止、迟到创建及准备失败继续由原 run 所有权收敛，不把失败的已受理请求自动重发。已有沙箱失效后明确返回资源状态，不能假定历史输出文件仍在。
- 准备环境事件只在实际开始准备时产生；纯回答不闪现虚假的环境准备状态，准备中暂停工具执行并展示真实状态。事件与持久化仍用现有链路，联动 W3/W4，不另建状态系统。

### 验收

1. 无附件纯回答不调用沙箱 create/get/ensure；首次资源工具与大结果整形各能触发一次准备，同批多调用不重复创建。
2. 参数/策略拒绝不准备资源；准备失败结束为明确失败，停止与迟到创建不会执行工具或污染后续 run；用事件闸门代替长 sleep。
3. 运行中注入附件、等待恢复、已有沙箱失效可明确恢复或报错；针对项目路径跑已有保护检查，确认快照/占用没有被延后。
4. 在记录代码与镜像版本、冷暖条件的本地部署上，纯回答、网页取数、表单各一次。纯回答“零沙箱创建”是确定性门槛；其余两项结果正确、资源只准备一次。报告总时间及准备/模型/工具分段，不承诺固定秒数。

完成状态与证据统一见总计划；实现后同步架构、能力边界、代码地图和服务指南。
