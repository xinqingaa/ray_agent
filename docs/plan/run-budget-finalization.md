# 运行预算收尾与执行链路首批优化

状态：2026-10-10 获授权并完成实现，真实模型复测由用户执行，结果见文末。代码基线 `01674e84ffa017dbf1f32c9558b3a028b1479cc6`。问题背景、成果契约与长期方案见[任务请求预算与异常结束成果交付分析](../research/run-budget-and-artifact-finalization-2026-10-10.md)；本计划只取其中能直接避免同类失败、改动集中在循环与工具层的部分。

## 问题

明朝 HTML 小样运行（会话 `443bd82c`，运行 `c0219520`）以 `failed/max_iterations` 结束，文件已在沙箱生成却没有交付。按事件逐轮核对，请求主要消耗在以下环节：

| 环节 | 观察 | 主要责任 |
|---|---|---|
| 素材准备 | 第 1–36 轮检索、下载、压缩 16 张图；“简单版”与“图片可占位”没有缩小范围 | 提示词 |
| 长命令 | 5 次 `shell_execute` → `shell_wait_process` → `shell_read_output` 三连，等待只返回退出码，输出要再读一轮；约多 10 轮 | 工具 |
| 首版之后 | 第 40 轮已构建完成，此后 60 轮在“构建 → 打开 → 脚本检查”中逐像素调整（如图片高度 262→238→214 px），每轮 3 次请求 | 提示词与预算信号 |
| 批量调用 | 100 轮共 101 次工具调用，已知参数的连续步骤也逐轮发出 | 提示词 |
| 计划与交付 | 计划只在第 1 轮写过一次；从未调用 `deliver_files` | 提示词与收尾机制 |
| 结束 | 达到上限直接失败，不进入结束一致性检查，模型从不知道剩余预算 | 循环 |

另有两处源码事实影响预算设计：

- 请求计数在每次 `invoke` 和 `resume_approval` 开始时清零。审批续接属于同一运行，所以一次运行的实际请求可以超过上限。
- 交付状态是单一标记，`browser_screenshot(deliver=true)` 也会把它置为完成。识别出“需要交付文件”时，交付一张截图就能通过结束检查；这一点依赖成果契约，留给后续批次处理。

## 关于是否保留请求上限

保留，但重新界定它的作用。决定何时结束本来就由模型负责：没有工具调用的回复即为最终答复，上限只在模型持续不收敛时生效。本次的问题不是上限太低挡住了复杂任务，而是模型到达上限时既没有预警，也没有收尾的机会。

上限从最近一条用户消息起算，不约束整个任务：失败后用户再发一条消息，会在同一份上下文上开启一次新运行，并获得新的预算。复杂任务因此可以分段推进，每段结束时交付并说明进展。首批保持默认值 100，等有了收尾机制和同条件评测数据，再决定是否提高默认值或按任务提供更高预算。

## 范围

### 1. 运行级预算与收尾

- **计数口径**：从最近一条用户消息起累计。新消息、运行中补充的消息和提问回复都会重新计算，这时用户在场并给出了新输入；审批续接沿用审批前的计数，由运行器按本运行事件里最近一条用户消息之后的逐轮尝试与压缩请求还原。普通请求、重试和压缩摘要请求统一计入。
- **阶段**：上限为 N。N ≥ 10 时，已用 ⌊0.7N⌋ 次后提醒一次，最后 max(2, ⌈0.1N⌉) 次进入收尾；N < 10 时不分阶段，只保留到达上限即失败。阶段只依据已用请求数判断，不预测剩余工作量。审批续接从记忆恢复已注入的阶段，跨过新阈值时补发对应提示。
- **信号形式**：阶段切换时向记忆追加一条 user 消息，经 `ContextEvent` 记录，请求重建可以回放。系统提示词保持不变，避免破坏缓存前缀；本次运行 98% 的输入命中缓存。每个阶段只注入一次。
- **提醒文本**：“[运行预算] 本次运行已使用 {used}/{limit} 次模型请求。请判断主要成果是否已经可用：已可用就先交付，剩余预算只用于必要修复，不要开始新的可选扩展。”
- **收尾文本**：“[运行预算] 剩余 {left} 次模型请求，已进入收尾：只能读取文件、交付文件和更新计划，其他工具会被拒绝。请交付已有成果并给出最终答复，说明已验证的内容和未完成的部分。”文本不附候选文件清单：文件工具写入的多是脚本和中间文件，成果往往由 Shell 生成，列出来反而误导，成果清单留给成果登记。
- **收尾限制**：新增执行前检查，复用计划模式的允许清单写法，注册在计划模式检查之后、策略检查之前。只放行 `read_file`、`search_in_file`、`find_files`、`deliver_files` 和 `update_plan`；被拒绝的调用返回说明，不执行、不进入审批。不含工具调用的最终回复始终允许。
- **到达上限**：仍以 `failed/max_iterations` 结束，原因不变；错误文案注明“回复‘继续’可在当前上下文接着执行”。
- **计划模式**：同样注入提示并启用收尾检查；计划模式检查在前，收尾文本不提交付。被拒调用标记为 `denied_by=budget`，前端显示“请求预算即将用完，收尾阶段不执行”。

### 2. Shell 等待返回输出

`shell_wait_process` 在进程结束后，由 API 侧调用 `read_shell_output`，把输出合并进结果；超时时返回失败，并附上已有输出和“进程仍在运行”。结果沿用现有整形逻辑截断。工具描述改为“结束时直接返回输出”。不改沙箱接口，也不需要重建镜像。

### 3. 内置提示词

中文和英文版本同步修改；`build_system_prompt(None)` 与原文逐字一致的约束保持不变。在 `<agent_loop>` 中修改或新增以下各条（英文版语义对应）：

- 批量（替换第二条）：“一次回复可以包含多个工具调用，按顺序执行；参数已经确定的连续步骤（如修改、构建、打开页面、检查）放在同一次回复中，后一个调用需要依据前一个结果时才放到下一次回复。”
- 范围（新增）：“用户要求简单版、样例或想先评估效果时，做足以评估的最小版本：控制篇幅与素材；可选素材难以获取或用户允许占位时直接占位，不自行扩展为完整方案。运行中用户调整范围时，按新范围继续。”
- 计划（替换原计划条）：“复杂任务先用 update_plan 写出简短的计划清单；每完成一个阶段就更新状态，同一时间最多一项 in_progress；简单任务不必写计划。”
- 交付时机（并入原交付条）：“文件第一次达到可打开、主体内容完整的状态后就先交付，再按需改进；改进后交付新版本并说明改动。”
- 验证收敛（新增）：“验证针对影响使用的关键问题，一次脚本批量检查优于逐页截图，修复后复检一次即可；只涉及观感的微调随成果说明，不在交付前反复打磨。”
- 预算（新增）：“收到‘[运行预算]’提示时按提示收敛；交付部分成果时说明完成与未完成的部分，不称为全部完成。”

在 `<shell_rules>` 中新增：“命令运行超过数秒时 shell_execute 会先返回 running；用 shell_wait_process 等待，进程结束时它直接返回输出，无需再读取。”

不写死 100 或任何固定次数，不加“最多检查两次”之类的全局规则。

## 不在首批

成果登记与版本、到达上限或模型故障时由程序补存、用户停止后保存、重启恢复、交付需求识别与截图交付的区分、提高默认上限、浏览器打开 `file://`、停滞检测。它们依赖研究文档第 5–6 节的成果契约，另行规划。首批不能保证模型在收尾阶段仍不交付时用户能拿到文件；这种情况下用户能看到失败原因和缺口说明，并可以回复“继续”。

## 完成条件与验证

用脚本化模型（`tests/support/loop_harness.py` 与 `ScriptedLLM`）和内存替身做确定性验证：

- N = 10 时，用满 7 次后的第 8 次请求末尾出现提醒，用满 8 次后的第 9 次请求末尾出现收尾提示；各次请求的系统消息完全相同。
- 收尾阶段不在白名单内的调用被拒绝且不执行；同批的 `deliver_files` 成功交付，最终回复使运行以 `completed` 结束；持续调用工具到上限时原因仍为 `max_iterations`，错误文案提示回复“继续”。
- 运行中补充的消息使计数清零；审批续接沿用续接前的计数，补发跨过阈值的收尾提示，按事件重建的请求与实际请求一致。
- `shell_wait_process` 的成功、超时和会话不存在三种结果，用替身沙箱验证返回内容。
- 现有提示词一致性测试和全部核心测试通过，前端类型检查通过。

真实模型复测：用相同的两条用户输入、`deepseek-flash` 与 `high` 档位、相同工具配置，在干净会话中运行 3 次，记录首个可用文件的轮次、首次交付的轮次、总请求数和是否交付。目标是 3 次都交付了可打开的 HTML；这只是本场景的观察，不作为性能结论。另将上限临时调为约 30，观察提醒、收尾与回复“继续”的实际表现。
