# 本机核心与存储

本专题按 Python sidecar、SQLite 与本机持久消息协调制定待授权设计，尚未开始实现。产品范围见[决策清单](decisions.md)，共同身份与事务规则见[共享契约](shared-contracts.md)。

## 目标与现状

桌面应用不依赖另行部署 RayAgent 服务器。安装包及应用管理的组件提供核心所需运行时，由应用启动、观察与回收，不要求用户手工运行现有 Compose 服务栈。按 D3，桌面版从空数据开始，不读取或迁移原部署数据。

当前业务依赖 PostgreSQL、Redis 和文件存储，API 装配连接 Docker 沙箱，文件存储可选腾讯云 COS；数据库包含 JSONB、PostgreSQL 专有 SQL、索引与 advisory 锁。输入流和变更通知依赖 Redis，实际执行协程由 API 进程持有。现有边界见[状态与持久化](../architecture.md#状态与持久化)，实现见[代码地图](../code-map.md#状态与持久化)。

## 职责划分

- **Python 核心**：保留单循环、模型与协议适配、工具管线、计划、审批、运行记录与应用服务；暴露 HTTP／SSE，不重写成第二套 Rust Agent。
- **Tauri 宿主**：启动随包发布的核心，确认就绪与实例身份，处理版本不兼容、崩溃、退出和托盘生命周期，只回收本应用拥有的进程。
- **业务存储**：SQLite 保存工作区、会话、运行、事件、配置、工作方式、记忆与持久操作；核心是业务写入入口，前端不直写数据库。
- **检索存储**：嵌入式索引由[知识检索专题](knowledge-and-retrieval.md)负责，原始材料与权威业务数据不由向量索引代替。
- **输入与通知**：本机输入协调与事件通知替换 Redis；受理、去重、持久状态与重连补读以数据库记录为准，通知不是唯一依据。
- **执行资源**：文件、Shell 与浏览器按[执行环境契约](files-and-execution.md)准备，不要求任何会话先启动容器。

以 PyInstaller 产物随安装包发布 Python 核心，各系统与架构分别构建；首个交付只构建 macOS Apple Silicon。原生依赖、子进程模块、模型 SDK、解析库和浏览器组件必须实际核对，不能由“Python 可打包”推导本项目依赖已兼容；M0 宿主探针先用现有依赖集暴露这类问题。

## SQLite 与进程模型

采用 SQLAlchemy＋aiosqlite，应用数据根中的业务库启用 WAL、外键与明确的 busy 处理。一个数据根仅由一个核心持有操作系统级实例锁；第二个窗口连接既有实例，不另开业务写核心。

写协调器独占一条写连接，业务写事务经它串行进入；读取使用独立的只读连接池，在 WAL 下与写入并发。解析、OCR 与 Embedding worker 不持有业务库连接，只返回结果清单，由核心发布。事务中不等待模型、子进程或文件复制。数据库异常只在业务事务尚未产生外部副作用时有界重试；CAS 失败返回最新版本，不自动重放用户变更。

按目标对象模型设计新的 SQLite schema，不逐表搬运 PostgreSQL 结构与迁移历史，但保留已验证的领域语义：每会话事件序号、`(session_id, seq)` 唯一、活动运行唯一、CAS 版本与幂等身份。常查的身份、版本、状态、范围与来源是带索引的普通列，其余结构化内容使用 JSON 文本列；使用 SQLite 方言 upsert 与唯一约束。schema 版本沿用 Alembic 管理：P1 建立新的 SQLite 基线，不保留 PostgreSQL 迁移历史，表结构变更使用 Alembic 的批量模式；后续工作包新增的表各自以升级脚本加入。仓库实现移除 PostgreSQL 专有 SQL、advisory 锁与 asyncpg 异常判断；`FOR UPDATE` 与 advisory 锁承担的职责改由实例锁、写事务和持久租约承担，不能仅用一个 Python 互斥锁替代所有数据库约束。

每会话 `next_event_seq` 在写事务中分配并与事件同提交；活动运行唯一性用 SQLite 支持的条件索引与事务复核保证。时间统一以 UTC 表达。schema 自 P1 起带版本，桌面版本之间的演进沿升级脚本执行并在升级前生成一致副本；首个交付的内部包升级同样保留数据，见[备份与应用升级](implementation.md#备份与应用升级)。

## 持久输入、通知与任务

新增 `accepted_requests` 保存请求摘要和受理结果，`run_inputs` 保存消息、目标运行、消费状态与来源事件。受理在同一事务写入消息、运行和输入；后台唤醒失败不丢输入。输入应用与上下文事件同提交，发送结果未知按请求身份查回，重复请求不生成第二份用户消息。

每次核心启动扫描输入与运行：仍可续接的提问沿原运行重建；崩溃遗留执行标为中断，未消费输入保持已受理可见并提供明确的重新发起入口，不静默自动启动新的业务执行。旧审批同时失效。进程内通知与订阅只作唤醒，按事件序号补查覆盖漏通知窗口。

`background_jobs` 保存类型、工作区、对象版本、幂等键、状态、实例所有者、取消状态、进度和错误；类型至少覆盖解析、索引发布、记忆提炼、会话摘要、组件安装与清理。读取与派生任务可重建，文件恢复与外部副作用任务必须先核对已完成部分。重试改变代次，旧回调按对象版本与所有者被拒绝。

队列按交互任务、当前工作区读取与后台索引区分调度，后台任务可暂停和取消；不让大文档处理独占核心事件循环。取消返回的是任务状态，已经开始的文件发布另行核对，不把取消请求等同于副作用未发生。

## 通信与生命周期

本机 API 默认只接受本机访问，并建立应用实例级的访问边界；移动远程入口单独配对和授权，不因启用桌面客户端自动暴露到局域网。

桌面 UI 使用本机核心，辅助移动客户端使用桌面提供的同一业务协议。协议包含运行、事件序号、资源身份及能力范围，保留流式重连与审批去重；手机不直接访问桌面数据库或本地路径。

关闭窗口、留在托盘、真正退出与操作系统休眠分别定义。核心异常后从持久记录核对运行与外部资源，不自动重放结果未知的工具调用。现有提问续接、审批失效和重启中断语义保留或明确替换，不承诺任意位置自动续跑。

## 核心启动与终止

宿主先取得实例发现信息，再经私有管道传入数据根、实例身份和令牌。核心以操作系统分配的回环端口启动并从受控通道返回握手，不把令牌放在进程命令行。握手核对协议／构建与 schema，完成必要的 schema 升级与重启扫描后才声明可受理。P2 接入宿主之前，开发时直接启动核心并用启动参数指定数据根；正式包只接受宿主经私有通道传入的数据根。

启动失败保留可读诊断与重试，不循环拉起多个核心。核心异常时界面停止新写入并保留草稿，重启后先读回已受理身份；宿主只管理自己启动且身份一致的核心和执行 supervisor，不按旧 PID 误杀其他进程。具体进程树边界由[执行专题](files-and-execution.md#进程与执行资源)落实。

凭据端口连接系统凭据存储；Python 核心按引用获取秘密，客户端只接收掩码与可用状态。首个交付由设置页把模型端点的地址与密钥写入配置与 macOS 钥匙串，替代现有的环境变量来源；模型目录与端点映射沿用代码，不在首个交付开放任意新增厂商或模型。外部 CLI 的环境采用受控继承，不把所有模型连接密钥或其他工作区的凭据注入子进程。日志与备份不记录实际凭据。

正式退出先关闭准入、停止任务并确认写入者，再刷写和关闭数据库；异常终止按启动扫描处理。安装更新期间禁止两个版本同时打开同一可写数据根。数据根搬移必须停写并核对，不能以运行中复制单个 `.db` 代替备份。

## 数据保护

- 业务库、内容对象、Skill 快照、检索索引、组件与临时文件在应用数据目录分别管理；工作区文件夹是用户数据，只被绑定，不纳入应用数据根。
- 清空业务数据、删除工作区与卸载应用都不删除工作区文件夹。
- 备份覆盖业务库与其引用的内容对象；检索索引可重建，不是恢复必需字节。备份与恢复流程见[实施工作包](implementation.md#备份与应用升级)。
- 本地化不扩大执行恢复承诺，也不取消跨数据库、磁盘与外部副作用的一致性边界。文件写入、撤销与删除规则见[文件专题](files-and-execution.md)。

## 责任与依赖

应用层负责启动协调、受理与清理；领域层继续维护运行规则与端口；基础设施层提供 SQLite 仓库、本机队列、通知和平台资源适配；原生外壳负责进程宿主和安装更新。

先确定[工作区身份与数据范围](workspaces-and-memory.md)，再约定文件、索引、Skill 与持久记录的位置。原 PostgreSQL／Redis 部署不再维护，桌面运行时不保留这两套依赖，也不实现双存储适配。

## 交付与检查

P1 交付 SQLite 仓库与工作单元、写协调与读连接、输入与通知、后台任务和启动扫描，应用配置迁入业务库，会话工作目录替代沙箱固定路径；核心启动不再初始化 Redis、Docker 与 COS，PostgreSQL、Redis 与 COS 的实现和依赖随之删除。P2 集成本机宿主与钥匙串，并在最后移除 Next 服务与原部署编排。替换范围见[实施工作包](implementation.md#现有实现的替换与移除)。

SQLite 集成检查覆盖双请求竞争、唯一索引、输入提交与消费之间崩溃、事件提交后通知失败、旧代次回调、提问与审批重启及数据库忙碌。文件操作另用真实 IO 检查；测试通过前不把 PostgreSQL 的原有正确性结论直接搬给 SQLite。

技术依据见 [SQLite WAL](https://www.sqlite.org/wal.html)、[外键等 PRAGMA](https://www.sqlite.org/pragma.html)及[备份接口](https://www.sqlite.org/backup.html)。WAL 仍可能返回忙碌错误，不能据此省去事务与恢复设计。

## 完成条件

- 已约定桌面平台无需手工部署 PostgreSQL、Redis、Nginx 或 Docker 即可进行常规工作区操作。
- 并发受理、等待、审批、停止、核心重启与 SSE 补读沿明确语义工作，未知副作用不会被自动重放。
- 内部包升级保留工作区数据并在升级前生成一致副本，旧二进制不打开新 schema；完整备份与恢复随 P10 交付，恢复失败不覆盖当前数据，也不删除工作区文件夹。
- 内部包安装、升级及退出收尾有服务指南入口，实际支持范围明确。
