# skill 安装与运行的设计取舍

skill 的方法加载与产品安装解决不同问题。模型需要相关方法，产品需要保证来源、完整材料、版本和资源归属可解释。详细机制见[skill 说明](../skills.md)。

## 为什么按需正文之外还需要完整包

目录先提供名称和描述，需要时再加载正文，避免所有方法常驻系统提示。这一分层思路可参考 [learn-codex 的 s07_skills](https://github.com/xinqingaa/learn-codex/tree/main/s07_skills)，但加载示例不能覆盖产品中的安装事务、权限和恢复边界。

只保存 Markdown 会丢失参考资料、脚本与素材，因此安装保留完整包；校验和登记不执行脚本或自动安装依赖。包完整可读与本次任务可用仍是不同判断。

## 为什么全局库与运行材料分开

本机 CLI、沙箱目录与 RayAgent 全局库各有归属。将命令安装当作产品安装，会绕开数据库目录与运行引用，因此设置和聊天共用安装服务。

设置需要更新和删除，等待中的任务需要原材料。不可变版本和持久引用分开这两个寿命；沙箱使用运行专属副本，不能反向覆盖全局包。文件发布与数据库登记分别确认，通过幂等核对和无引用回收处理失败，而不承诺跨资源原子安装。

## 为什么显式选择与自动加载共用身份

自动加载依赖模型判断相关性，显式选择则需要在业务决策前生效。两者共用版本解析、完整性与预算检查，正文以内部资料块保存，避免重复注入、结果截断或被当作用户原始要求。

压缩保留活动正文，新运行将旧资料转为历史引用，等待恢复固定版本。这些约束保护来源与执行条件，不赋予额外工具权限，也不证明模型一定遵循。

## 为什么获取后直接阅读仍需显式安装

用户取得材料后需要查看正文、脚本和相对资源，独立预览动作只会增加导航。共用包阅读器承接导入和已安装内容，安装前修订生成新的校验材料，正式安装或更新仍显式发布版本。

阅读不会执行主动内容，删除也不撤销已运行脚本的副作用。资源版本、文件切换和异步请求分别核对身份，才能避免混读或将刷新失败误报为安装失败。

## 为什么加载成功不能证明效果提升

包安全、事务和交互检查证明工程链路；方法是否相关、依赖是否满足和成果是否正确需要不同证据。相同条件下的独立预期与任务比较，才能评价 skill 对质量、纠正成本、耗时和用量的影响。检查方法见 [API 指南](../../ray_agent/api/README.md#skill-安装与运行检查)。
