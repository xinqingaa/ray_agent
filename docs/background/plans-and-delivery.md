# 长任务计划与成果交付的演进

计划全勾选、运行 completed、文件已上传，分别只能证明部分事实。RayAgent 的几轮优化从“怎样显示进度”走向“怎样保留目标、解释检查和取得成果”，中间的关键是识别不同失败，避免用一个结束标记掩盖全部问题。完整契约见 [计划可信度、核验与成果收尾方案](../plan/long-task-trust-and-delivery.md)。

## 最初的计划工具解决了展示与交接

单循环后，计划工具让目标和进度成为可持久化、可投影的记录，不再由外层 Planner 选择下一步。后来计划模式与确认按钮允许用户先看方案再执行，计划历史可以只读查看。它们解决了可见性，却没有保证执行开始时承接的是用户确认的那一份清单。

优化先处理具体版本承接：确认按钮提交结构化引用，受理事务验证并绑定新运行，业务动作前选择当前阶段，刷新仍可读回。用户直接发送文字仍按普通消息处理，程序不能从“继续”自动推断某份旧方案已被确认。

但仅要求模型经常更新清单，又引入了额外协议工作。观察中计划只覆盖当前局部步骤，做完后显示全部完成，整体目标却仍有缺口；按标题判断身份又会把改名误认为删除与新增。

## 内容质量与过程成功先暴露了分歧

有限任务复审发现，HTML 可以打开、交互可以通过，但内容仍可能把跨时期事件概括为同一时期；整理周报也可能把材料中的“完成导出”扩写成“已交付使用”。这类错误不能由页面截图、格式正确或 completed 消除。另有通过修改 CSS 冒充手机布局的验证，说明检查方法本身也需要证据。

对应优化先整理中英文通用原则：改写材料保持原有事实、范围和确定程度，假设与原文区分；验证针对影响结论的风险，数据检查口径，内容检查关键事实，界面使用真实交互条件。用户禁止联网时检查已有材料与内部一致性，不把具体历史答案写入通用提示，也不增加逐条回复的第二模型审查。后来成果版本与核验记录在此基础上补充程序可观察事实，仍不替代这些内容判断。

## 真实长任务把问题拆开了

审查了两个实际会话的持久事件、末轮请求重建与交付文件。多轮输入是先交付方案、再同意方案，与原拟三轮脚本不同，不能当作严格对照实验。

| 实际观察 | 可以得出的判断 | 不应推出的结论 |
|---|---|---|
| 父阶段和四个子步骤平铺，5/7 完成仍显示第 2/7 步 | 整体阶段与当前步骤混用了进度分母 | 增加更多步骤就能改善整体可信度 |
| 原型 58 次请求中 12 次仅核对计划 | 固定频率与实际工作变化脱节，制造纯协议往返 | 所有检查都冗余，应一律删掉验证 |
| 单次任务 95 次请求，末段必要方案写入被拒 | 收尾限制没有区分必要成果与继续扩展 | 只提高请求上限就能保证交付 |
| 最终说明中的统计口径与实现不同 | 累计说明需要实际成果依据，内容需要独立核验 | 工具执行成功即可证明业务正确 |
| 多轮没有压缩，单次压缩一次且原目标仍在请求里 | 这次没有证据把全部失败归因于压缩丢目标 | 压缩永远可靠、无需结构化恢复 |
| Markdown 合法且段落正常，但长段难扫读 | 内容组织需要改善 | 必须修复 Markdown 解析器才能解决 |

由此形成三个相连的方案：稳定目标和阶段，按版本保留核验，按项管理成果并为预算收尾提供有限通道。界面简化只是其中一部分。

## 为什么稳定整体阶段，而不建立第二个调度器

采用一个计划身份，区分整体阶段和所属执行步骤。阶段回答目标由哪些部分构成，步骤回答当前部分怎样完成；局部细化保留整体身份，不改变顶层计数。生命周期和执行安排分别表达，资源不足保留受阻，用户取消保留来源及原因。

这是记录契约的增强，不是重新引入 Planner。程序可以验证身份、归属、真实消息引用和完整更新，不能判断每个自然语言阶段是否覆盖需求。用户原文仍是依据，模型整理的目标不能代替授权。

固定批次核对被取消，必要核对集中在计划承接、范围变化和结束缺口，优先随正常业务动作一起完成。模型继续自主决定阶段切换，界面用实际工具活动补充“正在做什么”，不强迫每个动作都产生一个新清单。

## 计划语义为何不能只靠结构校验

个人知识库演示稿和 RAG 讲解稿曾暴露另一类问题：清单主要描述写文件、浏览器检查和交付，主题推导与关键判断没有充分呈现；其中一次在制作完成后才登记计划。这不能证明产物没有主题内容，却削弱了计划的事前解释和执行中观察价值。

改进先要求主要工作前登记路径，让条目承接具体问题与成果。初次改写又使标题装入内容目录和规格，清单变长；随后短标题缩短了表达，仍出现拆分过细。因此最终同时约束语义、标题和阶段粒度，按阶段成果合并相关动作，其余阶段进入时展开。

两种案例只用于形成规则，不是要实施真实知识库或 RAG 系统。最终粒度调整未再次模型采样，结构合法也不能证明规划质量。有效设计已并入 [计划与成果方案](../plan/long-task-trust-and-delivery.md#规划语义时机与清单粒度)。

## 为什么检查必须关联版本与条件

同一模型重复说“已检查”可能继续采用错误口径。即使命令正常退出，也可能只说明程序没崩溃。方案因此将核验身份、条件、成果版本和实际调用联系起来，显式通过断言才形成通过记录；同版同条件可以复用，改版则核对有效性。

重复未获得通过证据时，需要解释新条件或更换方法；合理修复后的复验保留。程序可以约束记录和实际调用，不能发现所有未登记的语义重复，也不能证明模型选择的断言充分。因此历史验收用独立重算和真实交互检查，避免让生成实现验证自身。

## 预算收尾经历了两次方案收敛

一份 HTML 小样第 1–36 轮处理 16 张图片，第 40 轮已有可构建首版，之后仍反复精修，最终用尽 100 次请求且从未交付。五组 Shell 执行、等待、读取三连也增加往返。第一批优化保留上限，增加 70% 提醒和末段收尾，等待结束直接返回输出。

这解决了“到最后才知道用尽”的问题，但末段拒绝所有写入又使尚未落盘的必要文本成果无法补齐。后续改为收尾前登记预期成果，仅允许为已登记文本成果补写，已有路径另存系统预留版本，避免破坏旧材料。二进制生成、依赖安装与新功能继续在正常阶段完成。

曾考虑异常结束时自动补存、候选文件扫描和通用恢复；这些需要识别真正成果、路径所有权、幂等发布及未知结果对账。脚本和中间文件不能直接当成果，停止也不能成为未经判断的自动发布。因此最终范围只提供受限通道和明确缺口，没有实现通用崩溃自动交付。预算继续是请求次数约束，不是费用硬上限。

## 完整交付之后仍需要业务判断

后续分批真实任务观察到必要文件完整交付、同版复用、改版保留和累计说明。一次原型复测用 38 次请求完成交付，但独立核对仍发现留存统计口径与快速重置竞态；完整交付和业务通过必须分开记录。此前 97 次与后来的 38 次涉及不同产物及中间修复，不构成受控性能比较。

界面首次展示过多内部范围、成果和核验信息，按用户反馈收敛为标题、描述、任务项及一个顶层进度。执行所需结构继续持久化，成果在交付区查看，范围改变与真实阻碍在对话中说明。删掉技术噪声不应删掉内部恢复依据。

销售工作簿任务则提供另一类证据：冻结三份输入，用 Decimal 独立重算并逐条对照，核对缺失单列、去重、原文件保护与下载字节。不同类型任务用于检查通用规则是否偏向某个原型，不能用一个样例建立所有业务的验证器。

被替换的状态名称与定时核对阈值不再维护为协议。
