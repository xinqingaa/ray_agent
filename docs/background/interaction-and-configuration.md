# 用户交互与模型接入的设计取舍

材料管理、成果阅读、技术观察和部署连接各有使用目的。入口归属和状态来源明确，用户才能判断正在查看什么、修改何时生效，以及关闭后返回哪里。交互契约见 [UI 设计说明](../../ray_agent/ui/DESIGN.md)，模型机制见 [Harness](../harness.md#模型选择与请求分工)。

## 为什么管理、阅读与技术观察分开

同一内容在侧栏、设置和工作台重复管理，会使入口名称、默认内容和返回路径不一致。工作区页与文件夹面板承担稳定材料管理，对话侧承担当前工作与阅读，设置处理名称与生命周期。

原始事件、请求和运行快照供技术观察，普通阅读不需要这些字段。开发者开关只控制展示，不能改变权限或执行事实。

## 为什么界面消费统一事实投影

组件各自根据工具或步骤推断状态，会在重试、重连与多轮任务中产生矛盾。提交负责受理，订阅负责按序号补齐，视图投影统一组织运行、轮次与调用。

容量也需要共同来源。实际 usage、请求前估算和压缩后估算各有含义，不能拼接不同窗口或把估算增大称为释放空间。

## 为什么草稿与迟到响应需要作用域

关闭弹框、切换页面和保存请求可能同时发生。没有对象身份与离开保护，旧响应就可能覆盖新对象，上传结果可能进入另一份草稿。独立首页、各工作区首页与具体会话各有一份草稿，创建会话的请求标识随作用域保存，互不覆盖。

因此保存失败保留内容，版本冲突提供最新状态，切换与关闭处理未保存内容。辅助视图保留返回路径与焦点；当前背景和冻结运行输入也分别展示，避免把编辑误认为已经改变执行条件。

## 为什么预览与输入是共用能力

文件卡、工作台和工作区文件夹里的文件都需要阅读材料，共用查看器避免为阅读启动任务或沙箱。不同格式按实际解析能力展示，下载保持原字节，HTML 隔离预览不等同于完整浏览器沙箱。

独立首页、工作区首页与会话共用输入，使草稿、图片、粘贴和聚焦保持一致。图片是否进入像素输入由后台按能力与容量组织，用户无需选择协议模式，但模型必须获得真实原因，上传成功不能冒充看过图片。

## 为什么模型能力由核心唯一持有

模型能力包括窗口、输出上限、工具、图片、思考档位与单价。如果界面、核心与上游各存一份，三者很快不一致：界面允许的组合被核心拒绝，核心接受的模型界面找不到，上游报告又与两边都不同。界面维护能力白名单时，每接入一个模型都要改前端；用代理域名之类的地址特征推断能力也不可靠，同一地址下的模型能力可能不同。

备选有三种：界面维护目录，会与核心漂移；完全依赖上游报告，多数兼容接口只返回模型 ID，报告的能力字段也未必可信；核心持有目录，上游只做补充。当前选择是最后一种。目录由核心持有并经接口读取，保存、归类与重复检查都由核心完成，界面只展示与编辑。上游报告不覆盖目录模型，因为目录模型已有经过验证的参数与编码规则。这样界面看到的能力、保存的结果与运行时实际发送的请求来自同一处。

代价是新模型要在目录登记后才有精确能力，目录未读取时界面无法显示能力与单价，保存结果以核心为准。这些代价可接受，因为能力错位的后果是运行时才出现的请求失败，比界面少显示一项更难察觉。

目录只说明能力的声明，不证明实际上游一定支持，需要按[模型通信检查](../../ray_agent/api/README.md#responses-模型通信)验证。

## 上游只返回模型名称时的兜底

很多兼容服务的模型列表只有 ID，少数还报告窗口或能力列表。字段缺失时若拒绝保存，用户就无法接入新模型；若凭空取一个值并当作确认，又会在运行时以错误参数失败。因此每个字段独立判断来源：可信的报告直接采用，没有报告时使用保守值，并在界面标「能力未确认」，让用户知道这是默认而不是事实。

- 窗口与输出取保守值，并让输出不超过窗口的一半，宁可截得短，也不让请求超过真实窗口。
- 工具默认开启。常见的兼容接口接受工具定义，若不接受，代价是一次明确的失败，检测可以发现并让用户关闭；反过来默认关闭会让可用模型在界面里显得不支持工具。文件中缺省的 `tools` 仍视为关闭，因为旧配置已依赖这一行为，改动会悄悄改变已有模型的能力。
- 图片默认关闭，且当前不做图片探测。误开启会把图片发给不支持视觉的模型，后果比漏开更严重；而一次图片请求的失败原因很难与其他错误区分，探测结论不可靠。
- 字段与条目互相隔离：一个坏字段只让该字段回到默认值，一个坏条目只跳过该条目，不让一份列表因局部错误整体失效。

这些是取舍，不是已验证的上游事实。模型列表与能力声明的具体规则见[模型连接如何生效](../model-usage.md#模型连接如何生效)。

## 为什么工具检测只以上游拒绝请求体为不支持

检测要回答的是“上游是否接受工具定义”。一次失败可能来自密钥、模型名、地址、限流、网络或服务端故障。如果把任何失败都判为不支持，正常可用的模型会被误关工具，而用户很难察觉。

只有 400 与 422 说明上游读过请求体后拒绝了其中的字段，这是唯一与工具定义直接相关的拒绝信号。401 与 403 指向密钥或权限，404 指向模型或地址，429 与 5xx 是暂时状态，其他 4xx 没有足够信息。这些情况都作为“无法判断”返回，附带对应的修正建议，能力标记保持不变。

检测只发一次最小请求，接受即视为支持，它不证明工具调用的质量。不支持的结论也只给出建议，由用户确认关闭，因为一次结果可能受上游偶发状态影响，不应自动改写配置。

## 为什么右键统一由应用接管

WebView 的原生右键菜单包含重新加载、检查元素等浏览器项，与应用的操作无关，语言也不统一。应用的文本区域、列表行与消息各有不同的编辑需求，原生菜单无法给出正确的编辑项。

备选是只在部分区域阻止原生菜单，但遗漏的区域会再次弹出原生菜单，用户无法预期。当前选择是在捕获阶段取消所有右键默认行为，只在有明确对象或可编辑选区的地方给出应用菜单，其余区域什么也不做。菜单项全部由应用定义，同一对象的右键与「更多」下拉共用一份列表，动作与文案不会分叉。

代价是放弃拼写建议、服务等系统项。编辑菜单由应用补齐剪切、复制、粘贴与全选，粘贴只接收纯文本，与桌面宿主的剪贴板能力一致。交互规则见 [UI 设计说明](../../ray_agent/ui/DESIGN.md#右键与菜单)。
