# 执行循环与上下文的设计取舍

持续执行需要同时组织决策、反馈与有限输入。循环数量、消息保存和容量治理解决不同问题，不能互相替代。详细机制见 [Harness 决策层](../harness.md#决策层)与[上下文治理](../harness.md#上下文与记忆治理)。

## 为什么用一份记忆和一个决策循环

外层 Planner 与内层执行器各自维护记忆时，需要通过步骤描述和总结交接。内层可能顺带完成其他工作，外层却仍按原步骤重新判断，增加重复决策与上下文转换。

单循环让同一模型直接读取工具反馈并决定下一动作，计划用于记录目标与进度，程序负责调用解析、授权、等待和退出。它减少交接，却不能自动保证目标理解、需求覆盖或成果正确。

保留 Python、PostgreSQL、Playwright/CDP 与既有 Web 分层，也是为了将改动集中在执行契约。语言或框架迁移本身不能解决调用配对、未知结果和文件交付，增加日志也不能自动带来执行恢复。

## 为什么冻结背景仍要核对有效性

冻结解决运行中背景漂移的问题：后台新增记忆或新版工作方式不应改变正在执行的任务。撤回、删除与退出记忆参与则改变来源是否还能使用，不能等同于普通内容更新。只在等待续接时校验，会漏掉同一执行协程的后续轮次和传输重试；只查摘要记录是否存在，也无法识别来源会话已退出参与。因此运行保留原选择，每次请求前只剔除已失效依据，并保存提示词修订，兼顾有效性和历史请求重建。退出参与采用持久访问代次，避免关闭后迅速重新开启使旧冻结引用复活。

记忆更正涉及两个独立版本：候选自身的版本，以及候选要替代的目标版本。只检查前者无法阻止旧候选替代用户后来编辑的目标；确认必须带着目标依据一起核对。旧候选没有这个依据时保持未知，重新审阅后才能确认，不以迁移时的当前值冒充历史依据。

材料截止是查询条件，不是对最新材料事后裁剪的标签。先取当前近期窗口再过滤截止，会让排队期间的新消息挤掉原本应提炼的内容。按截止重建后再做有界选择，才能在延迟和重启之后仍使用同一范围。模型结果发布前的取消检查也必须与业务写入处在同一事务，仅在后台任务最终写状态时检查无法撤回已经落库的条目。

撤销恢复的是状态，不只是正文。类型、确定性、钉住状态和来源关系会改变条目如何被后续任务使用，因而需要保存完整的可恢复状态；历史记录缺少这些信息时，明确拒绝猜测恢复比静默丢失用户设置更可控。现行规则见 [长期记忆的更正与撤回](../harness.md#长期记忆怎样更正与撤回)。

## 为什么持久历史不直接等于模型输入

持久历史回答发生过什么，工作记忆服务于下一次决策，页面投影服务于阅读。让同一消息列表承担全部职责，会将展示裁剪带入模型输入，或为了保留审计材料而持续扩大请求。

因此三者分别组织：事件保留事实，工作记忆允许压缩，展示使用有界投影。请求重建依赖快照和上下文事件，不能将页面摘要当作原始请求。

## 为什么结果整形、容量估算和摘要分开

单条结果过大需要完整保存和按需读回，多轮累计增长需要摘要，固定背景过大则不能靠摘要消除。源头未提取的正文也无法由下游整形恢复。

摘要以完整调用轮次为边界，并保留用户原文与结构化任务状态，减少要求和成果身份只由摘要承载的风险。它仍有信息损失和容量成本；固定输入或保留区超限时，需要明确失败，而不是静默删除约束。

## 为什么效率优化落在工具与资源边界

等待可能来自模型、环境准备、能力发现、观察补读和展示加工。墙钟差额不足以完成归因，单次任务也不能形成统一性能结论。

按需准备资源、复用当次结果和有界独立读取分别减少不同的等待。工作区写入仍先取得租约与备份，浏览器写动作仍顺序执行；这些约束不能为了减少往返而省略。具体取舍见[工具观察](tools-and-interface.md)。

提高请求上限只能推迟耗尽，不能保证必要成果优先完成。预算因此与预期成果和受限收尾共同设计，见[计划与交付](plans-and-delivery.md#为什么预算收尾需要成果身份)。
