# 执行循环与上下文的演进

持续调用工具只是开始。RayAgent 从双循环到单循环的改造，先处理决策交接，再处理模型输入容量，随后才处理无效往返与长任务收敛。这些问题相互影响，但各有独立成因。对应设计及实施依赖见 [循环、上下文与效率方案](../plan/execution-and-context.md)。

## 双循环原本提供了什么

早期实现由外层 Plan + ReAct 创建计划、选择步骤、更新计划与总结，内层执行器请求模型、调用工具并回填结果，两者各有记忆。外层组织步骤，内层处理真实动作与反馈，两者之间需要传递上下文和执行结论。

当时审查将问题分成两类：

| 问题 | 历史表现 | 影响 |
|---|---|---|
| 决策交接 | 内层顺带完成后续工作，外层仍重新判断；两份记忆经步骤 JSON 与总结交接 | 重复决策并增加格式失败入口 |
| 执行契约 | 只采用首个调用、工具异常自动重试、空回复补为用户消息、新输入打断执行 | 丢调用、重放副作用或混淆消息来源 |

这些问题不能全部归因于模型弱或计划不够细。

于是改造的重点从“增加更详细的外层计划”转向“减少重复决策边界”。保留一份工作记忆和一个循环，计划变成同一模型维护的记录工具；调用解析、动作授权、等待与结束仍由程序负责。模型可以在下一次反馈后重排动作，程序不按清单调度阶段。

单循环减少了一套规划与交接，但不自动理解业务目标。计划语义是否正确、成果是否满足要求仍需要证据；后续长任务问题也证明，去掉外层 Planner 并未消除遗漏和重复检查。

## 为什么保留技术栈而不先迁移框架

比较与复审支持沿 Python、PostgreSQL、Playwright/CDP 和现有 Web 分层渐进改造。更换语言或框架不能直接解决调用配对、结果未知、上下文容量和成果交付问题；追加日志格式也不能自动提供执行恢复。Git worktree 可以隔离目录，但不自动隔离记忆、权限和网络。

早期评测设想曾要求固定数量的重复运行，复审后撤回：先建立可解释的同任务基线，再按具体改动验证关键行为。需要实际模型对照的地方保留条件匹配；结构契约用脚本化模型确定性检查。没有对 Codex 做运行测试，因此外部源码比较只作为方案启发。

## 工作记忆与历史事实开始分开

旧消息列表同时承担持久历史和模型工作记忆。按浏览器工具名裁剪正文、删除推理字段，可以减少局部负担，却没有统一处理长结果和累计历史。某条正文提前丢失后，再好的摘要也无法恢复它。

后来的方案分成三条链：原始事件保存发生过什么，模型记忆组织下一次判断需要什么，页面投影展示用户需要看什么。调试请求可以由运行快照和上下文事件重建，不必让模型永远携带全部历史。

| 问题 | 采用的处理 | 为什么单独处理 |
|---|---|---|
| 单条工具结果过大 | 完整结果落盘，返回首尾预览、长度和读取路径 | 信息仍可按需读回，避免裁剪等于永久丢失 |
| 多轮历史累计过大 | 每次请求前估算容量，摘要较早完整轮次 | 单条结果都很短也可能累计超限 |
| 压缩后忘记原要求 | 在保留区重新注入用户原文，恢复最新结构化任务状态 | 摘要是模型解释，不能替代要求与成果事实 |
| 模型切换后估算失真 | 新模型首轮重新估算，后续利用自己的 usage | 前一模型的 token 数不一定适用于新模型 |
| 容量仍不足 | 明确失败并说明边界 | 静默删除约束会让后续行为不可解释 |

压缩边界必须在完整调用及结果之后，不能留下一半协议。较早内容可摘要，最近轮次保留原样。预算提醒等内部消息需要保留其来源，不能被摘要改写成用户要求。用户原文和结构化状态也有容量成本，固定输入或保留区本身超限时仍可能失败。

## 效率问题为什么后来转向工具契约

历史任务提供了效率线索，但没有形成统一性能基准：

| 当时条件与观察 | 可以说明什么 | 限制 |
|---|---|---|
| 本机 Compose，glm-5.2 文件任务：约 36.4 秒、13 次请求、累计输入 64,763 tokens | 存在检查冗余交互的必要 | 无旧版重复对照；累计输入含重复发送，不是单次窗口或费用 |
| 同一原记录首次输出约 14/34 秒的文字与括注冲突 | 延迟记录口径不可靠 | 不作为有效首字延迟基准 |
| E5 校验码任务：四次请求、12.6 秒墙钟，模型 3.319 秒、工具 0.606 秒 | 约 8.7 秒尚未分项归因 | 不能全算作截图成本 |
| E1 纯回答无工具仍有准备开销 | 问题不限于浏览器 | 不能只删截图就断言开销解决 |

源码审查还指向准备环境、重复正文、动作后补观察和展示补读等候选原因，不能仅靠墙钟差额完成归因。

因此保留原循环和容量治理，在资源准备、能力发现、结果反馈与有限独立读取上做优化：独立对话首次需要才准备沙箱，外部能力按需发现，展示使用已有结果，白名单独立读取可以有界并发。项目运行必须先完成文件保护，不能为了提速照搬独立对话的准备顺序。浏览器问题在 [工具观察背景](tools-and-interface.md)展开。

## 请求上限与成果收敛的关系

一份 HTML 小样用尽 100 次请求。第 40 轮已有首版，后面仍在素材和视觉细节上反复调整，没有交付；长命令等待后还要再读输出，制造额外往返。提高上限可能推迟失败，却不能保证必要成果优先完成。

第一轮优化保留上限并提前提醒，末段限制动作；同时让 Shell 等待直接返回已有输出。后续真实长任务又暴露出限制所有写入会阻止必要文本成果，于是补充预登记成果、受限收尾写入和分项缺口。预算方案需要与成果契约一起理解，具体分析见 [长任务计划与交付](plans-and-delivery.md)。

历史效率数字属于当时的模型、窗口、缓存、镜像与冷暖条件。受控三读取并发可以证明那个契约减少等待，不能推出所有任务按同样比例加速。

当前机制另见 [Harness 工程](../harness.md)，这里保留选择的形成过程，不复述全部现行字段。
