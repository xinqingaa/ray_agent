# 运行记录与控制的设计取舍

页面请求、执行协程、模型轮次和本机工具进程各有寿命。将它们合成一个运行标记，会使刷新、停止和重启后的状态无法解释。详细机制见[控制平面](../architecture.md#结束路径与控制平面)。

## 为什么保存运行身份与终态

取消协程不会自动终止操作系统进程，进程结束也不撤销文件。会话用于组织连续历史，运行用于关联一次执行及终态，轮次和尝试用于关联模型与工具活动。

停止需要传播到具体资源，控制结果另行记录。工作区文件夹还要求确认旧写入者静止（见[文件夹工作区与写入保护](workspace-folders.md)），文件与浏览器资料可以留存，但不代表旧进程仍可被认领。外壳退出也不能证明其后台子树已结束，终止与释放占用必须以整棵树为准。

## 为什么事件回放不等于执行恢复

只保存界面内容不足以解释模型输入，只保存进程内对象又无法跨重启读取。运行快照与上下文事件提供可重建的记录，数据库提交后再通知，订阅方按序号补查。

这些记录提供审计与有限续接，数据库事务却不包含外部提交、文件写入和上传。响应丢失可能留下未知副作用；通用恢复还需要检查点、资源认领与副作用对账，不能由事件完整推导出来。

## 为什么等待退出协程

提问和审批的等待时间无法预知。将其仅保留在调用栈中，会使重启丢失待处理调用，因此等待先持久化，再由回复触发运行器重建。

提问回复补齐原调用结果，审批只放行具体调用；同批未执行动作不能盲目重放。预算与配置也随身份恢复，内部反馈不能冒充用户新输入获得额外预算。

## 为什么流式文本与完整响应分别处理

即时文字反馈与可执行的工具调用有不同条件。文本增量可以临时展示，工具参数必须完整组装并检查结束原因；否则断流会把半截参数变成动作。

增量不承担历史保存，完整消息和用量沿持久事件回放。首段到达时间、模型耗时、工具耗时与任务墙钟也分别计算，避免将局部时长当作整个任务的成本。

## 为什么受理与资源准备分开

同步等待环境与外部发现会延迟首次响应，客户端超时后重发可能造成重复任务。短事务先受理输入，再后台准备，使客户端能够按请求身份读回结果。

前端禁用按钮无法代替服务端准入；迟到结果也必须检查资源仍属于哪个运行。结构化计划确认沿同一事务绑定具体版本，普通文字则不按关键词自动转换为计划批准。

## 为什么健康检查之外还需要构建身份

服务可访问只说明能响应请求，不能证明使用预期代码、提示或配置。API 与 UI 分别记录构建输入指纹，运行快照保存实际提示，才能区分部署产物和执行条件。

Git 提交不能独自区分工作树修改，源码指纹也不覆盖凭据、可变环境或外部模型。两端身份、运行快照与服务健康需要分别核对，详见[构建身份](../architecture.md#构建身份与运行快照)。

## 为什么工具解释器以归档分发

冻结核心和执行用户脚本需要不同的 Python。把正常解释器目录直接交给冻结工具，会让其 Mach-O 依赖重写规则作用于工具解释器，可能把工具自己的动态库引用改向核心库；文件虽然都在包里，实际版本却已改变。正常 Python 还会生成或刷新字节码缓存，若资源位于签名包中，执行脚本就会破坏包的资源封印。

解释器归档作为只读资源分发，运行时在数据根校验并原子展开，保留上游动态库布局。这样解释器与核心的依赖所有权分开，实际启动核对版本，脚本的可写缓存也留在应用资源之外。此处解释分发取舍，发布与检查方法见[执行环境与限制](../architecture.md#执行环境与限制)和[桌面开发指南](../../ray_agent/desktop/README.md#构建内部包apple-silicon)。

## 为什么安装目标不能代替当前发布版本

若可用性检查要求收据版本等于最新目标，仅更新目标清单就会撤掉尚可工作的旧组件；新版本下载失败、取消或重启都不能恢复服务。已发布版本与安装目标因此分别保存，能否继续使用旧版由运行适配契约决定。新目录完成校验后才切换发布指针，正在使用旧目录的进程也不因切换被破坏；适配契约不兼容时说明原因，由新的完整安装替代。
