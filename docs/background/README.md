# 演进背景

本文解释 RayAgent 为什么从双循环教学工程演进到当前 Harness，保留影响理解方案的关键转折与历史证据修正。当前机制见[架构说明](../architecture.md)，现阶段结论及关键验收见[维护入口](../plan/README.md)；详细工作包设计保存在[二次开发历史参考](phase-4/README.md)，不随日常修改续写。

## 旧方案解决了什么

旧实现由外层 Plan + ReAct 创建计划、选择步骤、更新计划与总结，内层执行器请求模型、执行工具并回填结果，两者各有记忆。文件、Shell 和浏览器在沙箱执行，MCP/A2A 接入工具层，业务过程通过 Web 观察。旧实现基线为 2c323cc；tag baseline-v1 指向 961005d，两者之间只有文档变更。

这一结构明确展示了步骤与工具反馈两种边界、模型陈述与真实动作的区别，以及协程、持久记录和外部副作用的不同寿命。原 16 章以此完成验收，仍有教学价值；课程里的旧实现说明需要按基线阅读。

## 为什么升级

| 旧选择及收益 | 暴露的代价 | 已落地的演进 |
|---|---|---|
| 独立 Planner 与步骤调度，方便展示进度 | 两份上下文、额外规划调用和步骤 JSON；开放任务常在一步完成后续步骤 | 单循环推进，计划作为记录工具，控制边界由程序维护 |
| 消息列表支撑多轮对话 | 持久事实与工作上下文混合，局部裁剪无法处理长轮次 | 原始事件、模型记忆与页面投影分开，请求前检查容量 |
| 模型整包返回，解析直接 | 生成期间没有可见内容 | 流式组装完整响应后执行工具，另推临时文本增量 |
| 会话状态兼任运行结果 | 停止与完成混合，重启后难解释发生了什么 | 独立运行与调用身份，区分完成、取消、中断和等待 |
| 取消协程与通用重试，实现简单 | OS 进程可能继续，丢失写操作响应后重试可能重复写入 | 登记资源并传播停止，工具执行一次，保留未知结果边界 |
| 总结与假完成守卫 | 工具调用和计划勾选不能证明成果正确 | 显式文件交付、有限结束反馈和独立产物核验案例 |

这些取舍支持渐进改造，不要求先换语言、框架或数据库。PostgreSQL 适合当前 Web 服务；追加日志格式不能自动解决上下文与执行恢复，Git worktree 也不能自动隔离记忆、权限和网络。结构性选择的代价见[设计取舍记录](../decisions.md)。

### 工作区调研的本地观察

2026-09-09 在 macOS 临时目录调用实际 ShellService 执行 sleep 6，约 6.02 秒后返回 completed，未按预期约 5 秒返回 running。观察指向输出读取器被直接等待；未经过 Docker/HTTP，不能推广为所有平台的现行结论。后续 W7.1 修订由专项设计和运行证据说明。

### 能力评估的真实任务记录

2026-09-14 本机 Compose、glm-5.2 的单次文件任务耗时约 36.4 秒，13 次模型调用、累计输入 64,763 tokens。它提供冗余交互的线索，不代表全部双循环任务；累计输入包含重复发送，不能当作唯一上下文大小或费用。

该次观察的几项修正需要保留：一次写入出现四条同路径记录和一个附件，属于当时契约问题，不能继续排作未修缺陷；任务结束容器仍运行符合会话复用，不能仅据此断言泄漏；权限观察必须区分产品调用路径与宿主 docker exec。原报告“约 14 秒首次输出”的括注时刻相差约 34 秒，记录自相矛盾，不作为有效延迟基准。

原记录未覆盖断连、数据库提交故障、API 崩溃、多 worker、真实 TTL 到期等范围，也没有重新取得完整日志。这里保留的是历史分析条件与修正，不是本轮重新运行。
