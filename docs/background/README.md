## 旧方案解决了什么

RayAgent 原方案是 Web UI、API、沙箱、PostgreSQL、Redis 和文件存储组成的任务执行系统。外层 Plan + ReAct Flow 创建计划、选择步骤、更新剩余计划、总结；内层 Agent 请求模型、执行工具、回填结果。Planner 与执行器各自保存消息记忆。

文件、Shell 和浏览器在沙箱中执行；MCP 与 A2A 接入工具层；业务事件经 SSE 展示并保存；产物同步为可下载附件。会话可多轮，沙箱按会话复用。它已经展示了一个 Harness 的核心职责和跨模块交接，不是因为“不像 Codex”就失去价值。

旧方案的教学价值在于：能明确观察步骤与工具反馈两种边界、模型输出与真实动作的区别、协程/持久记录/外部副作用的不同寿命，以及协议适配如何接入自研循环。原 16 章已完成系统学习任务，阶段 3 的验收仍然有效。

## 为什么升级

| 旧选择及原收益 | 暴露的代价 | 新方案的演进方向 |
|---|---|---|
| 独立 Planner 和步骤调度，方便展示进度 | 强制交接、两份上下文、步骤 JSON 和重复规划；开放任务可能一步做完多步 | 单循环推进，计划作为工具状态；程序保留控制边界 |
| 保存消息列表，易于多轮交互 | 工作上下文与持久事实混合，定点删正文不能处理长轮次 | 原始记录、摘要和请求 Context 分开，主动预算 |
| 模型整包返回，解析简单 | 生成期间无增量内容 | 保留 SSE，增加模型内容与工具参数的流式契约 |
| 会话状态同时表示运行结果 | 停止和完成混合，重启后难解释执行情况 | 独立 Run/调用身份与中断、取消、等待语义 |
| 协程取消与通用重试，实现直接 | OS 进程可能继续，写操作响应丢失后可能重复 | 资源所有权、取消确认、副作用分类与未知结果对账 |
| 总结与假完成守卫 | 有调用不等于产物正确、上传成功 | 具体产物校验，执行结束与成果验证分开 |

数据库本身不是问题：Web 服务继续使用 PostgreSQL 合理。JSONL 更适合某些本地追加日志场景，不能自动解决上下文、恢复和并发。worktree 分离文件修改，不自动隔离记忆、权限或网络。

### 工作区调研的本地观察

2026-09-09 在 macOS 临时目录调用实际 ShellService 执行 `sleep 6`，约 6.02 秒后返回 completed，而非预期约 5 秒返回 running。观察指向输出读取器被直接等待的问题。未经过 Docker/HTTP，不能把这个结果当所有平台的现行结论。W7.1 已改为最多等 5 秒返回 running，终止打到进程组，见[本阶段的演进结果](#本阶段的演进结果)。

### 能力评估的真实任务记录

2026-09-14 本机 Compose，经 `localhost:8088`，模型 `glm-5.2`：创建文件写入 `harness-eval`，读回并交付附件。会话 `3cb937b6-6b95-46c5-94af-16a14e16cfc0`，旧报告记录终态 completed。

| 原观察 | 保留与解释 |
|---|---|
| 约 36.4 秒、13 次模型调用（规划 3、执行 10） | 单次旧基线任务，不是总体性能或新方案预期 |
| 累计 prompt tokens 64,763，completion tokens 1,295 | 输入重复发送的累计用量，不是唯一上下文大小，更不是费用 |

### 2026-09-19 核对时仍在的结构

当时的静态核对：文件替换使用旧文件 ID；未知工具分支使用 raise；A2A 取消时已有远端取消尝试。不得把旧报告的问题原样搬成重构待办。同日仍可见的结构包括取消写 completed、单步预算、消息局部裁剪、非流式模型、只取首个工具调用、进程内运行注册表。这些项在 W0–W7 中的处理见[本阶段的演进结果](#本阶段的演进结果)，不以本段当作现行缺陷清单。

Codex 的真实源码证据及固定提交链接记录在原统一计划第 2.2 节（提交 `082e825`）；教学拆解仅作理解线索。未运行 Codex，因此不宣称其所有恢复、权限和外部副作用路径都得到验证。

## 本阶段的演进结果

数字取自[总计划第 6 节](../plan/README.md#6-证据记录)已记录的评测，每条任务多为 1 次，不外推成功率。与基线的综合对照见[对比报告](../plan/evidence/w8-comparison-2026-09-29.md)：W8 在空库部署上把 E1–E7 与 E6-deny 各跑 2 次，16 次全部通过且没有重试，E4 两次都是 cancelled，E7 两次各压缩 2 次后交付正确。当前模块怎么协作不在这里展开。

- **W0**（`961005d`，tag `baseline-v1`）：加上可复跑的 E1–E6 与脚本化模型，未改产品代码。E1、E2、E3、E5、E6 通过，E4 未通过：停止后会话仍是 completed，标记 5 秒内增长 5 行。
- **W1**（`9faa304`）：单循环替换 Planner + ReAct，去掉 `message_notify_user` 和 Step JSON。同一批 E1–E6 的模型调用合计 55 次降到 20 次，prompt tokens 从 285218 降到 92653；E4 仍未通过。
- **W2**（`c0822dc`）：请求前按容量压缩，超长工具结果整形落盘。E1–E7 全部通过。E7 在 `context_window` 24576、`max_tokens` 4096 下压缩 2 次，估算 14593→5777、15347→6030，12 个校验码保留。
- **W3**（`8511bdf`）：运行与事件改为独立表，SSE 按序号续传，停止写 cancelled。E1–E6 全部通过。E4 终态 cancelled（user_stop），停止后 10 秒内标记增长 0 行。六条合计模型调用 19 次，prompt tokens 86923。
- **W4**：前端改为按序号订阅并投影成视图。浏览器里的刷新与断网补齐随 W5、W6 补记；运行中断网 8 秒后事件序号由 9 补到 23，1–23 连续。
- **W5**：会话页、工作台、开发者视图和设置页按真实事件重做。走查截图在 `docs/plan/evidence/w5-2026-09-28-*.png` 与 `w5-2-2026-09-29-*.png`。
- **W6**（后端 `33964e0`）：模型默认流式组装，文本增量不落库。E1 耗时 10.1 秒，`ttft_ms` 为 871 与 629；E2 耗时 12.5 秒，各轮 `ttft_ms` 为 652、783、751、579。
- **W7**：沙箱服务以 ubuntu 运行，动态容器默认 2048 MiB、2 CPU、512 进程；停止时向进程组发 SIGTERM。E4 停止后标记停在 8 行，返回码 -15。工具策略为 allow / ask / deny。E1–E6 通过；E6 先等审批再得到 6912，正式轮耗时 174.3 秒（当时积压了约 21 个动态沙箱）。清理后 E6-deny 复跑 14.9 秒通过，该次报告写在临时目录，未入库。
