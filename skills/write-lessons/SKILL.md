# Write Lessons

让读者理解一个机制为什么存在、如何运作、在实现中落在哪里，以及有哪些边界。每篇围绕一个连贯问题展开，避免写成知识点清单、源码搬运或代码注释译文。

## Establish the context

先读取目标课程的本地写作约定、大纲和当前制作状态，确认本篇的问题、读者已有认知、前后依赖及交付范围。具体路径、章节顺序、语言、配图默认值和代码修改权限由目标项目提供，不在本 skill 中固定。

区分课程的读者入口、作者规则、素材索引和制作进度，沿用各自的维护位置。通用方法在本 skill 维护，项目偏好与章节安排留在目标课程；单章修订意见不追加为通用规则。不为写一篇文章复制课程计划或扩展开发范围。

## Research first, explain mechanisms first

作者的研究顺序与读者的阅读顺序不同。

作者先明确问题，再查实现与调用契约，运行或静态核对示例，提炼机制，最后组织正文。可以按证据和依赖安排制作次序，不必机械地按课号完稿。

读者通常从具体问题或现象出发，先理解机制，再通过示例与实现对照确认理解。可采用以下叙述逻辑，但不强制每篇使用相同的小节标题：

1. 说明本篇要解决的问题及其出现的场景。
2. 解释机制为何有效：谁做决定、数据如何流动、状态归谁、什么触发继续或结束。
3. 用简化模型、示例或图解帮助读者推演。
4. 对照关键实现与可观察结果，说明简化模型遗漏了什么。
5. 解释边界与取舍，衔接下一问题。

每个概念在引入时交代用途，避免先堆术语再解释关系。设计比较围绕场景和代价展开，不把当前实现当成普遍最佳方案。

项目教材也应建立可迁移的理解：先讲与本篇问题相关的通用概念、机制和取舍，再用项目与实验说明具体实现。现有脚本是证据与例子，不应限定正文的知识范围；通用策略与项目已实现能力须明确区分。

深度与篇幅由读者理解机制所需决定，不按脚本长度或固定行数压缩，也不追求覆盖整个知识领域。围绕核心问题讲透必要概念及其联系；相邻主题只交代影响理解的边界。示例不足时可以补充教学场景，不必让一个极简例子承担所有概念。

## Use examples and code deliberately

选择能直接展示本篇机制的示例，优先复用准确且可理解的已有材料。连续主题尽量复用同一观察对象，减少读者反复理解无关业务背景的负担。

明确独立实验、简化模型和完整系统之间的关系，以及各自的执行环境。安装与运行条件链接到所属指南；正文只保留理解观察所需的操作，不重复维护部署手册。

根据讲解需要选择表达方式，不默认设置源码链接区：机制导论使用过程推演与图解；需要精确说明控制流程时使用标明简化的伪代码；实现细节影响行为时，才展示短代码片段并就地解释。不要用源码链接、类名、文件名或 API 清单代替讲解，也不逐行复述代码。

确实需要定位实现时，在相关说明旁给出文件位置、符号名和观察重点，链接仅作辅助。完整实现索引归入课程素材文档；作者的核对依据与验证记录不必成为每篇正文的固定结尾。正文保留影响读者理解的简化说明和证据边界。

如果示例不能证明所讲机制，换用更合适的材料；需要补代码时遵循项目授权范围。不要为配合预定结论而改写观察，也不要默认让读者从零复刻系统或替读者决定参与层级。

## Ground claims in evidence

区分代码事实、设计意图的推断、教学简化和改进建议。注释、历史讨论、脚本名称只作线索；行为结论应追踪实现，涉及运行表现时核对实际结果。

检查控制流、数据流、状态归属和边界条件。一个成功示例不能证明全部错误处理能力；一次调用不能证明持续反馈；内存中的状态不能自动称为持久化。

如实区分静态核对与运行验证。未执行的观察标为未验证，说明缺少的条件，不编造输出、截图或通过结论。代码变化后更新受影响的解释与证据，详细说明仍在原有归属位置维护。

## Draw to explain

只有图能更清楚地表达关系、变化或执行过程时才画，不规定每篇图数。一张图回答一个主要问题，箭头标明语义，当前实现与未来设计分开表达。

控制图中文字密度，让读者先看见关系和流程。节点优先使用简短名称，按需补一条关键说明；详细解释放正文或图注。标题、副标题、节点说明和底部结论不应重复同一判断，也不默认凑齐这些元素。信息拥挤时先精简重复内容或拆图，不靠缩小字号容纳段落。

采用读者熟悉且简短的术语，例如图中直接写 `Context`、`Memory`，不必逐个翻译或重复中英双标；术语在正文中解释并保持一致。中文与英文按清晰程度选择，不强行统一为英文。精简后仍需保留关键动作、条件、来源线索与箭头含义，避免只剩抽象名词、无法推演过程。渲染检查同时看文字密度与可理解性，不以字数越少越好。

遵循用户和课程的格式、尺寸、风格与资源路径约定。需要技术架构图且 Fireworks Tech Graph 可用时，读取其 skill 及对应风格参考，按需使用；不要凭技能名称猜测规范，或把模板中的能力当作系统事实。

作图工具的默认设置不能覆盖课程的明确约定。完成后检查图文一致性、结构、文本可读性与裁切，并实际渲染查看。临时预览与正式交付分开；未查看不能声称视觉验证通过。动画只在明确需要时制作，先确认工具支持的结构与依赖。

## Review and deliver

审查优先处理问题不明确、主线断裂、机制错误和证据不足，再处理文字润色。检查读者是否能解释机制、定位实现、说明边界；前后依赖是否清楚，示例是否支持结论，代码与图片引用是否有效。

完成后按项目约定更新制作状态，简述完成内容和验证边界。正文写完与运行验证完成分别记录，不因文案完整就标记全部完成。
