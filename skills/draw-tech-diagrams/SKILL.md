# Draw Tech Diagrams

只有图能比文字更清楚地表达关系、变化或执行过程时才画，不规定每份文档的配图数量。一张图只回答一个主要问题；当前实现、教学简化与未来设计分开表达。

## 确定问题与图类

先写出读者看完图后应能回答的一个问题，再选择图类：

- 能力地图：系统能做什么，各能力如何分组。
- 分层架构图：组件职责、边界、依赖方向与数据归属。
- 数据流图：什么数据从哪里来、经过何种变换、流向哪里。
- 流程图：按什么顺序执行，在哪些条件处分支或结束。
- 状态机或生命周期图：对象有哪些状态，什么事件触发迁移。
- 时序图：多个参与者按时间顺序如何交互。
- 循环或反馈图：一次执行如何根据观察、结果或错误继续推进。
- 知识路线图：概念、阶段与前后依赖如何组织。
- 对比图：方案在相同维度上的差异与取舍。

不要因现有模板而改变问题类型。一个画面需要回答多个独立问题时拆图；只有同一问题必须同时展示结构与过程时才组合图类，并明确主次。

## 组织信息

- 先确定节点、分组、层级、状态和连接关系，再设计布局。
- 箭头必须表示调用、数据、控制、反馈、保存或其他可说明的语义；方向和标签应支持读者推演，不使用装饰性箭头。
- 节点优先使用短名称，按需补一条关键说明；原因、取舍和证据留在正文或图注。
- 标题、副标题、节点说明与底部结论不要重复同一判断，也不要求每张图凑齐这些元素。
- 采用读者熟悉且简短的术语，例如直接使用 `Context`、`Memory`；不机械地中英双标。术语在图与正文中保持一致。
- 精简后仍须保留关键动作、条件、来源线索和箭头含义，避免只剩无法推演的抽象名词。
- 信息拥挤时先删除重复内容、扩大画布或拆图，不靠缩小字号容纳段落。

## 通用视觉默认值

用户或目标项目没有另行规定时，采用以下默认值：

- 画布为 1600×900、浅色背景，使用 Fireworks Style 1（Flat Icon）。
- 主节点使用白色或浅色填充、4–12 px 圆角和 3–6 px 边框；分组容器的视觉权重低于主流程。
- 连接线使用 3–6 px 线宽，箭头接在节点边缘并避开节点、标题和标签；不同线型或颜色必须对应稳定语义。
- 少量强调色用于关键节点、主路径或异常路径；同一语义在整张图中使用同一颜色。
- 字号和间距按最终阅读尺寸选择，不直接照搬工具模板；正文阅读宽度下仍须清楚可辨。

这些是可用的基线，不是所有图必须一致的硬编码。内容比例、图类和目标媒介需要其他设置时可以调整，但应保持同一文档集内的视觉语义一致。

## 选择交付格式

- **SVG**：技术示意图的默认源文件与正式交付格式；适合版本控制、无损缩放和结构检查。
- **PNG**：用于渲染预览、真实界面截图，或目标平台不支持 SVG 的兼容副本；不要把 PNG 当作仍需编辑的技术图唯一源文件。
- **GIF**：仅在用户明确需要动画，且运动能表达顺序、状态变化或数据流时制作；静态图足够时不要使用。
- **HTML**：仅在筛选、展开、缩放或交互探索本身有价值时交付；普通文档配图不使用。

临时预览与正式交付分开。若项目只允许部分格式，以项目要求为准。

## 使用 Fireworks Tech Graph

Fireworks Tech Graph 是默认的技术图实现工具。使用前读取其 skill，并按所选风格读取对应参考；不要凭工具名称猜测能力，也不要把模板内容当成系统事实。

按以下顺序工作：

1. 提炼图要回答的问题和有证据支持的内容。
2. 选择图类，列出节点、分组、关系和箭头语义。
3. 确定画布、格式和风格；项目规则与用户要求优先于本 skill 默认值。
4. 按 Fireworks Tech Graph 的流程生成 SVG，执行其结构、标记、几何与构图检查。
5. 导出预览并实际查看；必要时修正文字、连线、留白与裁切。
6. 交付项目要求的源文件与衍生格式，并如实报告未完成的检查。

## 交付检查

- 图中结论与正文、代码或其他证据一致。
- 每张图只有一个主要问题，图类与问题匹配。
- 节点没有重叠，文字没有溢出，箭头不穿过节点或标题。
- 连线方向、线型、颜色和标签具有明确且一致的语义。
- 中文字体、最小字号、留白和裁切在实际阅读尺寸下可接受。
- SVG 通过结构和几何检查，衍生格式由最终 SVG 生成。
- 已实际渲染并目视检查；未查看时不得声称视觉验证通过。

## 规则优先级

发生冲突时依次遵循：用户明确要求 → 目标目录的局部规则 → 项目级规则 → 本 skill 默认值 → Fireworks Tech Graph 工具默认值。覆盖视觉参数不免除结构、可读性和图文一致性检查。
