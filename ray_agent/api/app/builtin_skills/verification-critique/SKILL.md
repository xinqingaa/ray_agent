# 独立核验与质量批判

跳出“刚写完就觉得没问题”的惯性盲区，站在挑剔读者的立场做**交付前把关**。真正完整的核验包含两层：**内容本身到底值不值、对不对**，以及**交付的文件与交互是不是真的能打开、算得准、没破损**。（若发现缺一手外部事实或原文档依据，回到 `research-grounding` 补证，不在核验环节靠猜硬圆。）

## 一、内容与逻辑自审（所有任务交付前必做）

交出去之前，快速审视一遍最终成果（在生成前想清楚，不必写入后反复整篇重读）：
1. **需求与硬约束全覆盖**：用户原话里的每一个问题、格式、文件名、页数/篇幅上限、剔除项或“不联网”要求，是否都正面兑现了？有没有漏掉关键小问？
2. **信息密度与真实价值**：这份答复有没有因为图省事而流于空泛、敷衍或堆砌套话？该给出明确判断或可用初版的地方，是不是真的帮用户把事往前推了一步？
3. **事实与假设严守边界**：未取得一手来源的推定、补全或占位项，是否已经在主视图紧邻位置明标「待确认」或「占位」，而不是藏在文末备注？

## 二、文件与交互产物的确定性核验（按 `<runtime_environment>` 可用能力执行）

只要交付 `.xlsx`、`.pptx`、`.docx`、`.pdf`、`.html` 或可执行小工具，**不能只靠“生成命令退出码 0”或“看着像成功”判断完成**：

1. **随包结构核验脚本（仅当本机命令 `LOCAL_COMMAND` 可用时执行）**：
   - 先调用 `prepare_skill_resources(name="verification-critique")` 获取本包稳定快照根路径；
   - 使用随包 Python 运行 `<root_path>/scripts/verify_office.py <交付文件路径>`，检查返回的 JSON 报告（必要时挂入工具 `verification` 字段；只有 `passed: true` 才算结构检查通过）。
   - **当本机命令不可用时**：不要调用 `prepare_skill_resources` 空转，直接对照下方第 2 条的可用检查并在结尾诚实说明环境未开启本机脚本核验。
2. **分产物专项深检（针对最高风险点）**：
   - **PDF 文档**：**必须**额外调用 `read_document` 抽读全文或首末关键页，核实中文文本可完整提取、无乱码方块或缺字——绝不单凭截图或导出成功判通过。
   - **Excel 工作簿（`.xlsx`）**：若脚本提示存在未缓存公式值，**必须**用 Python 代码独立核算所有核心合计数、分组小计与占比（校验各分项之和等于总计），在最终答复中附上「代码核算汇总表」并如实说明应用内表格预览不重算公式。
   - **HTML 演示稿与互动网页**：
     - 当自动化浏览器可用时，用 `browser_set_viewport` 实测桌面（`1280px`）与窄屏（`390px`）无横向溢出，实际触发关键交互确认 DOM 按预期更新且无报错；
     - **当本机命令与浏览器均不可用时**：对于你**刚刚在本轮通过 `write_file` 完整写出的文本/HTML 文件**，**不要**再用 `read_file` 分段重读全文凑“自查”，也**严禁**对 HTML 调用 `read_document`；写入时一次把好编码、标签闭合和事件绑定关即可收尾。
3. **单批登记与交付入口**：
   - 参数都确定时，把 `register_preview`、`deliver_files` 与收尾 `update_plan` 合并在同一批调用，不无谓拆成多轮串行；
   - 严禁把未执行、模拟数据冒充或失败的检查写成“已通过”。

## 三、诚实报告缺口

- 实测脚本或专项复查报出的任何 `issues` 必须先修复再交付；
- 确因环境能力未开启（例如未启用本机命令或自动化浏览器）、权限或原始素材缺失而无法执行的核验，在最终答复中直白交代清楚——诚实标出边界远比粉饰“全部完成”更赢得信任。
