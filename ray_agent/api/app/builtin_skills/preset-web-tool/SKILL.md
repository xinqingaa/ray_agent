# 互动网页小工具工作流

按最小复杂度阶梯快速把想法做成**在应用内就能直接打开用**的互动网页工具，交互真实可用、视觉克制耐看。

## 阶段流

1. **对齐核心功能与存储方式**：
   - 若需求明确，直接按最小可用闭环出初版；若关键交互或数据去向不明，最多问 1–2 个短选择题；
   - 按**最小复杂度阶梯**选型：
     1. 纯前端交互即可满足 → **单个自包含 HTML 文件**（首选）；
     2. 需多模块或较大静态资源且无需读写本机任意文件 → **纯静态多文件目录 + `localStorage`**；
     3. 必须跨运行持久化本机文件或运行本机数据处理逻辑 → **极简单进程 Python 标准库服务**（绑定 `127.0.0.1`，读取 `HOST` 与 `PORT` 环境变量，绝不写死端口）。
2. **设计与编码**：
   - 遵循预加载的 `presentation-design` 视觉规范，必要时读取其 `references/visual-checklist.md`；
   - 注意应用内静态预览沙箱限制：单/静态 HTML 中需要刷新保留的数据在独立文件下载后才持久，静态预览下尽量让当前会话操作流畅且提供导出 JSON/CSV/HTML 的按钮（若用到导出，确保原生 `<a download>` 或 Blob 下载可用）。
3. **核验、登记预览与交付（必做）**：
   - 运行 `verification-critique` 的 `scripts/verify_office.py <index.html>` 校验 UTF-8、非空正文、本地引用与无占位符；
   - 若自动化浏览器可用，打开预览并测试桌面与窄屏视口、关键交互点击后 DOM 是否按预期更新、无横向溢出；
   - 调用 `register_preview` 登记应用内预览（同时调用 `deliver_files` 交付入口文件）。

## 反模式红线

- **禁止用 `shell_execute` 临时后台服务地址当作长期入口**：本地服务小工具必须经 `register_preview(kind="service")` 托管。
- **禁止留“装饰性假按钮”**：界面上出现的每一个筛选、添加、删除、导入导出按钮必须真实生效。
- **禁止过度设计框架与依赖**：能用原生 HTML/CSS/JS 单文件干净解决的，不要在用户目录初始化整套 Node 脚手架。
- **禁止编造测试数据充当真实用户数据**：若自带示例数据，必须标明「示例数据」并提供一键清空入口。
