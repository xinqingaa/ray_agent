# 认识 Agent Harness：从一句请求到任务完成

RayAgent 是一个能够规划任务、调用工具并在沙箱中执行操作的 AI Agent 应用。用户通过 Web 界面提出目标，系统推进任务，把计划、工具记录和结果返回页面。对学习者而言，这个应用也提供了一个可以运行和观察的对象：模型怎样参与决策，程序又怎样把决策变成真实行动？

先看一条很小的请求：

> 在沙箱工作目录创建 hello.txt，写入 hello，再读取文件，告诉我里面是什么。

用户期待的不只是一句回答，还包括一个实际存在、内容正确的文件。任务推进时，页面会展示计划与执行记录；任务结束后，用户可以查看总结和相关文件。这样，一句话就连接了模型、工具、执行环境和用户界面。

本章无需启动服务。我们沿这条任务理解项目在做什么、为什么需要这些运行机制。下面的执行过程是教学示意，实际计划和工具调用顺序取决于模型响应与执行结果。

## 模型提出行动，程序让行动发生

如果模型只返回“文件已创建，内容是 hello”，我们得到的是一段文本。无论这段话多么肯定，它本身都没有在磁盘上创建文件。

要完成请求，模型可以提出一份工具调用：使用写入工具，目标是 hello.txt，内容是 hello。程序接到这份请求后，找到相应实现，把操作交给执行环境，再取得成功或失败的结果。模型参与了行动选择，真正访问文件的是工具背后的程序。

可以先把这件事分成三种职责：

| 职责 | 在文件任务中做什么 | 提供什么 |
|---|---|---|
| 模型决策 | 根据目标与已有信息，提出写入或读取操作 | 工具调用请求，或给用户的回答 |
| 程序执行 | 接收调用，找到工具，把操作交给执行环境 | 实际的执行结果 |
| 流程控制 | 组织后续调用，决定何时继续、等待或结束 | 有边界的任务推进过程 |

这也解释了为什么“换一个更强的模型”不能自动补齐整个系统。模型可能更善于选择操作，但程序仍然需要提供工具、传递信息、管理执行位置，并处理运行中的变化。

## 工具结果为什么还要交回模型

假设写入工具返回成功，接下来该做什么？用户还要求读取确认。程序需要把刚才的结果交给模型，让它依据已经发生的操作决定下一步。模型于是可能提出读取 hello.txt，读取结果再成为最终回答的依据。

这里有一个关键变化：模型后续使用的信息来自真实执行。如果读取返回 hello，它有了确认内容的依据；如果返回“文件不存在”，原先的完成判断就站不住了。系统需要让这个错误进入后续决策，模型才有机会检查路径、提出其他操作，或向用户说明未完成的原因。

这种让行动产生反馈、再让反馈影响后续行动的过程，就是 Agent Loop 的基本直觉。它使任务能够根据新情况继续推进，而不必由用户在每一步之后重新发出指令。具体是否继续、如何处理错误，仍由程序的控制规则约束。

因此，文件任务不必总是固定的“写一次、读一次、答一句”。我们关注的是这些动作之间的联系：后面的决定是否获得了前面的实际结果。理解了这一点，就能看出一次模型回答与持续执行任务之间的差别。

## 围绕模型，Harness 还要承担什么

即使模型已经能够提出合适的操作，用户的任务仍有许多具体问题：目标和工具说明由谁准备？文件写在哪里？页面怎样知道进度？用户怎样拿到文件？这些工作需要周围的程序共同承担。

本课程把围绕模型、组织信息与行动、支持任务持续执行的运行机制称为 **Agent Harness**。这里用它描述一组工程职责，不限定某个框架。Agent Loop 是其中的核心控制机制，Context、工具环境、状态、事件和产物管理则让它能够服务于完整任务。

![Harness 组织 Context、模型调用、执行控制与工具反馈，状态、事件和产物贯穿任务](assets/01-system-overview.svg)

读图时，可以从用户目标进入 Context 开始，沿模型响应走向执行控制与工具，再沿绿色箭头看工具结果怎样回到后续输入。下方的状态、事件和产物支撑整个过程。图按职责分组，不是部署拓扑；每个方框也不一定对应一个独立服务。

### 准备模型需要的信息

模型需要知道用户目标、可用工具和此前发生了什么。程序把这些内容组织为本次调用的输入，也就是 Context。例如，读取之前需要知道目标文件；生成总结之前需要知道实际读出的内容。

文件已经写入，但结果没有进入模型输入，模型就不能仅凭这件事发生过而自动知道它。反过来，程序保存的所有信息也未必都应交给模型。任务记录、界面展示和模型输入有不同用途，Harness 需要把合适的信息送到使用它的地方。

### 承接并推进任务

用户在页面发送消息，服务端需要接住请求，准备运行资源，再启动执行。此后谁调用模型、谁执行工具、结果回来后交给谁，都需要程序安排。否则，即使每个工具单独可用，它们也不会自行组成一条任务。

任务还需要有运行边界。如果操作始终没有结束，程序不能只靠等待模型“自己想明白”。执行上限、取消或等待输入等控制机制各自解决不同问题；认识 Harness 时，先明确这些决定也属于运行系统的职责，具体能力要对照实现判断。

### 给工具明确的执行位置

同一个“写文件”动作，可以发生在本机，也可以发生在远程环境。RayAgent 的文件工具把操作交给沙箱，因此本例中的 hello.txt 属于沙箱执行环境。用户通过本机浏览器发出请求，不意味着文件写到了本机项目目录。

执行位置会影响工具能访问什么，也影响后续操作能否找到已有文件。写入和读取必须指向同一个目标，后续调用还需要能够访问它。理解工具时，除了问“做什么”，也要问“在哪里做”。

### 让用户看见进展，让系统留下记录

任务可能包含多次模型调用和工具操作。如果页面只在最后返回一句话，用户很难知道当前执行到哪里、是否遇到了问题。RayAgent 把计划、步骤、工具和消息等变化作为事件返回界面，让执行过程能够被观察。

这些记录也帮助我们区分模型的说明与实际动作：“我准备读取文件”是一段说明，工具调用及其返回结果才表明程序走到了执行环节。页面记录能提供哪些证据、还遗漏什么，需要结合事件内容判断。

状态与历史还让任务有了可追踪的进度。不过，重新打开页面能看到“写入完成”，只能说明记录还在；它不自动证明系统能够从这里继续读取。保存记录与恢复执行相关，但承担不同的工作。

### 把执行产物交给用户

沙箱里出现 hello.txt，距离用户可以访问它，还需要文件保存、关联和交付。RayAgent 会将相关文件纳入存储与附件管理，让执行结果可以作为产物呈现在任务中。

对用户而言，总结解释做了什么，文件则是可以继续使用的结果。若只返回“文件已创建”，却没有明确文件去向，任务的交付仍不完整。Harness 因此既要组织行动，也要连接行动产生的资源与用户实际取得的结果。

## RayAgent 怎样组合这些职责

RayAgent 采用自研 Plan + ReAct 组织任务。Planner 负责安排和更新步骤，执行器围绕当前步骤选择工具、取得反馈并继续决策。这让系统既能维护任务安排，也能处理某一步中的具体操作。

对文件任务，计划可能分成“创建文件”和“读取确认”。执行器接到一个步骤后，再决定调用哪些工具。一个步骤可能需要多次调用，负责规划与执行的角色也可以使用同一个模型服务：程序为它们准备不同的任务说明，并安排调用时机。

这是一种有取舍的设计。显式计划便于组织和展示任务进度，也增加了维护计划的工作与模型调用。简单任务可以采用更直接的反馈循环；任务是否受益于独立规划，要看实际需求。认识这个项目，既要知道它采用了什么，也要知道这是一项可以研究和比较的选择。

工具能力同样可以扩展。RayAgent 内置文件、Shell 和浏览器工具，通过 MCP 接入外部工具，通过 A2A 调用远程 Agent。无论能力来自哪里，程序都需要把调用和结果接回任务过程。协议提供接入方式，任务如何推进仍由现有执行流程组织。

从用户侧看，这些机制表现为一个可以发起任务、查看进展和取得结果的 Web 应用；从工程侧看，它们组成了我们要学习的 Harness。界面使过程更容易观察，课程则进一步解释背后的职责与设计。

## 怎样理解一次“完成”

回到最初的请求：文件是否实际写入？随后读取到了什么？内容是否符合用户要求？这些问题让“完成”有了具体依据。

假设读取返回“文件不存在”，工具调用已经返回了结果，但用户目标没有实现。假设模型直接回复“已经完成”，却没有相应执行依据，我们也不能只凭这句话判断成功。停止执行与达成目标，需要分别看待。

判断结果是否成立是一项工程责任，可以由工具反馈、产物检查和人工核对提供依据；这不意味着 RayAgent 已经具备独立的目标验收模块。本章先用文件任务理解这种责任，之后再研究怎样选择检查方式、评价不同任务的表现。

通过这条小任务，我们已经可以说明 RayAgent 在做什么：模型参与规划与行动选择，程序准备信息、执行工具和推进流程，状态与事件留下过程，文件管理把产物交给用户。下一章从其中第一个具体接口开始：**程序怎样把信息交给模型，又怎样理解模型返回的内容？**
