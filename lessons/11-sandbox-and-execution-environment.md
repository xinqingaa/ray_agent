# 沙箱与执行环境

第九章的任务写下文件，等待回复，再在同一个沙箱中读回；第十章通过事件确认这些动作发生过。现在换一个问题：为什么换到另一个会话，相同路径可能找不到文件？把工作目录指定为 `/home/ubuntu`，工具是否就只能访问那里？任务显示结束以后，文件和进程又由谁清理？

这些问题都需要找到工具实际执行的位置。本章承接第三章的工具契约、第八章的执行控制和第九章的状态归属，解释执行环境的权限、资源与生命周期。可以先阅读机制，再按[沙箱指南](../ray_agent/sandbox/README.md#执行环境观察)运行受控观察；完整容器观察的条件见 [API 指南](../ray_agent/api/README.md#沙箱环境观察)。本章不需要模型调用。

## 工具说明之外，还需要一个执行位置

模型给出“读取 `/home/ubuntu/hello.txt`”，只是提出了动作和参数。这个路径不是跨机器通用的文件标识：API 进程、沙箱容器和宿主机即使都有这个名字，也可能指向不同内容。真正执行读取的进程，使用的是它能看到的文件系统和它的操作系统权限。

**执行环境是动作发生时可使用的文件、进程、网络、软件与权限条件。** 工具契约说明如何提出请求；执行环境决定请求落地时能做什么。一个合法路径字符串不能证明访问已获授权，一句“只在工作目录操作”也不能自动改变操作系统权限。

例如，限制文件工具只读取一个目录，却允许 Shell 执行任意 `cat`，限制仍可能从另一条行动路径绕过。有效边界需要覆盖能够产生同类副作用的入口。通用设计可以使用路径访问策略、低权限身份、受限挂载、网络策略及资源配额；它们解决不同问题，需要分别落实和验证。第八章的审批解决是否允许这次动作，环境约束解决动作执行时实际能触及哪些资源。

## 从 API 到沙箱里的进程

RayAgent 的 Shell 与文件工具通过沙箱适配发起 HTTP 请求，沙箱 FastAPI 调用实际服务；文件服务使用 Python 文件操作，Shell 服务使用 `/bin/bash` 启动子进程。浏览器另走 Playwright/CDP 连接，VNC 提供画面访问，它们并不经过文件服务执行。

![API 通过不同端点连接沙箱中的执行资源](assets/11-execution-boundaries.svg)

图中的容器边界表示资源位于哪里，不代表所有访问已经被授权检查。API 在当前 Compose 中还挂载了 Docker Socket，用于动态创建容器；这是控制执行环境的管理权限，与沙箱内的一次文件读写不是同一级能力。动态容器的创建参数没有把该 Socket 挂进去。

完整镜像由 Supervisor 启动 FastAPI、Chromium、虚拟显示、CDP 代理与 VNC 相关进程。`ensure_sandbox` 检查 Supervisor 返回的服务是否全部处于 `RUNNING`；仅能连接某一个端口，并不足以证明整个环境准备好。创建任务时还会准备浏览器适配，因此文件任务也依赖完整沙箱的准备路径。

在宿主机只启动沙箱 Python API，则文件和 Shell 会在宿主机当前身份下执行，同时不会自动出现 Chromium、VNC 或容器隔离。调试 Python 服务与启动完整沙箱，是两种不同的实验条件。

## 工作目录不是文件访问围栏

工作目录主要决定相对路径如何解释。Shell 的 `cwd` 指定命令从哪里开始；绝对路径仍从该进程可见的文件系统根目录解析，`..` 可以访问父目录，符号链接可以指向别的位置。只有另行实施路径策略、文件系统挂载或权限限制，工作目录才可能成为受保护范围的一部分。

当前文件请求的 `filepath` 是字符串，说明文字要求绝对路径，但没有据此建立目录白名单。普通读写路径直接进入 `open` 等文件操作；Shell 的 `_create_process` 只设置 `cwd`，没有把它变成根目录或访问检查。

本章观察在一个临时目录里建立 `work/` 和它旁边的 `outside.txt`，再在 `work/` 内建立指向后者的符号链接。实际 FileService 可以通过 `work/../outside.txt` 和链接读到相同标记。全部文件都由实验创建，所谓“外部”仅指教学指定的 `work/` 之外；它证明该目录不是服务强制的边界，不是容器逃逸实验。

文件内容能否访问还与身份有关。当前 Supervisor 将 FastAPI 配置为 `user=root`，Shell 子进程没有切换身份；本章容器实测 `id -u` 为 `0`。环境变量 `HOME=/home/ubuntu` 只是主目录取值，并不会把 root 变成 ubuntu；文件参数 `sudo=false` 也不等于低权限执行，因为普通 `open` 已经继承了服务身份。

root 在容器内并不自动等同于能访问宿主机所有文件。挂载、容器能力与运行时设置仍影响可见范围。反过来，容器内 root、镜像赋予 ubuntu 的免密码 sudo，以及 Chromium 的 `--no-sandbox` 等选项，都使我们不能把“运行在沙箱容器”解释为已具备最小权限或浏览器自身沙箱保护。浏览器行为在第十三章展开。

## 同一个会话，指的是哪一种会话

理解环境复用，先把三个标识分开：

| 对象 | 保存或管理什么 | 不能据此推断什么 |
|---|---|---|
| 产品会话 | 消息、计划、Memory、事件，以及当前 `sandbox_id` | 数据库记录在，不代表容器仍在 |
| 一次任务执行 | API 中的执行协程与输入输出流 | 等待续接可以换任务，不必换沙箱 |
| Shell 会话 | 沙箱进程内的命令、输出与子进程句柄 | 同一标识不代表一个持续运行的登录终端 |

`AgentService._create_task` 先按会话的 `sandbox_id` 查找沙箱；找到运行中的容器就复用，找不到才创建并保存新 ID。下面是省略网络与保存错误的简化 Python：

```python
sandbox = await find_running_sandbox(session.sandbox_id)
if sandbox is None:
    sandbox = await create_sandbox()
    session.sandbox_id = sandbox.id
    await save_session(session)
runner = make_runner(session, sandbox)
```

重新建立适配对象，不等于重新建立环境；新建环境，也不等于恢复旧环境。第九章同会话等待续接时，任务 ID 变了，沙箱 ID 不变，文件仍在。本章绕过模型和数据库，直接创建两个真实动态容器：向第一个的 `/tmp/` 写入标记，按 ID 重新连接后读到 `hello-ch11`，第二个相同路径不存在。它证明这次容器复用与文件分离，不代替应用的多用户隔离验收。

如果旧容器已经不存在，创建新容器只能提供新的执行位置，不能凭原来的 Memory、路径或事件恢复旧可写层。输入附件可以按运行器逻辑重新上传，但这与完整环境快照恢复不同；产物保存由第十二章解释。

### Shell 标识保留了记录，没有保留全部终端状态

当前 `ShellService.active_shells` 是服务实例内存中的字典。每次 `exec_command` 都创建新子进程；同一 Shell ID 的旧进程若还在运行，会先尝试终止它，再创建新进程。记录可以续接，进程状态却不是持续的。

受控观察先在一次命令中执行 `export LESSON_11_MARKER=first` 和 `cd ..`，下一次用同一 Shell ID、显式传入原工作目录，得到变量 `unset` 和原目录。环境变量与 `cd` 没有自动跨调用延续。文件能保留，是因为两个子进程访问同一文件系统；需要传递状态时，应明确重设参数或使用持久化文件，不能根据 UI 的终端外观猜测。

第八章已经区分等待超时、调用协程取消和进程退出。本章还要注意 `exec_command` 先等待输出读取器结束，随后才进入注释所说的五秒等待逻辑；不能把它理解为所有长命令都在五秒后返回。取消命令请求、终止单个进程、结束进程树和删除容器，仍是不同动作。

## 文件分开，不代表网络彼此不可达

两个容器有各自的可写层，仍可以接入同一个 Docker 网络。`localhost` 指当前网络命名空间中的回环地址，不能直接指代 API 或另一容器；连接其他服务需要从发起方环境可达的地址和端口。

当前动态沙箱接入配置的 `SANDBOX_NETWORK`，产品使用同一个 bridge 网络。创建参数传入 HTTP/HTTPS 代理变量，但代理配置并非目标地址白名单，也不能说明所有工具流量都会使用代理。Compose 没有发布沙箱端口到宿主机，说明没有这条端口映射，不能据此断言同网络的其他容器无法访问。

本章让第一个临时沙箱通过 Shell 请求第二个临时沙箱的 `8080/api/supervisor/status`，得到 HTTP 200，没有携带认证信息。沙箱路由也没有为这些接口定义调用者身份检查。这个证据表明本次部署中容器间可达，不能将“每个会话不同容器”直接解释为租户间完整隔离。

另一个本地实验仅访问自己启动的回环 HTTP 服务，用于说明子进程能够发起网络请求。两种观察都没有发送真实资料或连接公网；公网出口、DNS 策略和受限网络部署仍未验证。若要限制外发，需明确哪些地址、端口和数据可以访问，并在实际执行路径落实控制，不能只靠工具说明。

CPU、内存和进程数也有类似区别。Docker 可以提供配额，但当前动态创建参数没有设置这些上限，本次检查得到 `Memory=0`、`NanoCpus=0`、`PidsLimit=null`。这表示没有显式设置相应容器级配额，不代表宿主机或 Docker 虚拟机资源无限。我们没有通过耗尽资源来测试限制。

## 谁创建，谁复用，谁负责回收

一种通用的资源管理方法是把“连接外部环境”与“拥有可删除环境”分开：连接可以关闭，外部资源是否删除需要另行确定所有者。动态沙箱通常由创建它的系统负责回收；共享的已有环境则要遵守外部生命周期。

![资源继续存在的条件，与任务结束和显式回收之间的关系](assets/11-environment-lifecycle.svg)

当前动态 `create` 保存生成的容器名，`destroy` 先关闭 HTTP 客户端，再按容器名强制删除；本章实际创建的两个容器都通过这条显式路径删除，并再次查询确认不存在。这里验证的是主动销毁，不是到期回收。

已有沙箱模式存在需要明确的实现差异：`create` 仅保存 IP，不设置容器名，直接 `destroy` 不会删除容器；但 `get(id)` 把传入 ID 写入 `container_name`，其后的 `destroy` 就会尝试按该 ID 调用 Docker 删除。因此“已有沙箱永远不会被删除”不是当前代码能保证的结论。该分支只做静态核对，本章没有对任何已有外部容器执行销毁。

### 任务结束，不等于运行器销毁

正常运行结束后，运行器的 `finally` 清理 MCP/A2A 连接，任务完成回调移除进程内注册；它们没有调用沙箱 `destroy`。保留环境能够支持后续输入，但也意味着界面上的 `done` 不能证明文件、浏览器或容器已经回收。

运行器另有 `destroy` 方法，应用关闭的任务清理路径会尝试调用它；然而全局注册表只包含尚未移除的任务，且当前 `RedisStreamTask.destroy` 在遍历字典时调用会删除字典条目的 `cancel`，存在清理中断的风险。不能把“有销毁方法”写成“应用退出一定清理所有沙箱”。本章未模拟应用关闭故障，第十六章承接故障验证。

### TTL 要核对变量、计时与触发点

TTL 表达资源存活时间的意图，生效还需要读取配置、启动计时、触发关闭并验证资源退出。当前有三处细节影响这条链路：

- API 创建容器时写入 `SERVICE_TIMEOUT_MINUTES`，沙箱设置字段却是 `server_timeout_minutes`，默认读取的环境名为 `SERVER_TIMEOUT_MINUTES`。没有别名映射，因此不能假定修改 `SANDBOX_TTL_MINUTES` 就改变了沙箱计时；默认值碰巧一致也不能证明传参有效。
- SupervisorService 经缓存依赖首次构造时建立计时。符合条件的 `/api/` 请求会在现有剩余时间基础上取整后再增加三分钟，超时管理接口被排除；这不是固定任务总时长，也不是每次简单重置为三分钟。
- 到期逻辑调用 Supervisor shutdown，动态容器设置了 `AutoRemove`；要证明自动回收仍需观察计时触发、主进程退出与 Docker 删除。持续调用接口还会影响观察条件。

上述是代码核对，不是到期运行结果。本章只验证显式删除，自动 TTL、API 崩溃后清理和长进程树回收仍标为 `unverified`。

## 用观察结果判断边界

一个环境检查应先写明操作对象、预期限制和可观察结果。例如，把临时目录的 `work/` 当作候选边界，通过服务读取旁边的受控标记；若成功，应得出“工作目录未限制这条访问”，而不是笼统地说“沙箱失效”。容器级文件分离、网络分离和宿主机边界是不同问题。

本章新增本地脚本检查路径、Shell 状态、回环网络、身份继承与资源清理；Docker 脚本检查两个专用容器的重新连接、文件分离、同网络访问、运行配额和显式删除。第八章的单进程脚本另行复跑，保留其取消后仍继续写入、显式终止后停止的证据。命令和前提统一维护在服务指南，代码入口集中在[素材索引](map.md#第-11-章素材)。

这些实验没有调用模型，也没有重新做页面提交、真实用户鉴权、容器逃逸、公网外发或故障恢复测试。已有实现的缺口不妨碍学习通用方法，但设计建议不能成为产品能力声明。

读完后，可以用三个情境检查理解：同会话文件找不到时，先查路径、沙箱 ID 还是 Memory？Shell 中设置了变量，下一次命令为什么看不到？两个容器文件分开，为什么仍要检查网络和执行身份？解释时应指出实际执行者、资源归属、实施限制的位置和证据范围。

环境里的文件存在，只完成了交付的一部分。容器被回收后，用户还能否下载，需要另一套保存与访问机制；下一章继续追踪文件怎样成为任务产物。
