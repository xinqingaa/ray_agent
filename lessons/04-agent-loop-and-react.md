# Agent Loop 与 ReAct

上一章里，程序已经能执行一次 `tool_calls`，并把结果以 `role: tool` 送回。现在把文件任务写完整，问题就变成：结果回来之后，还能不能再做下一步？

本章仍用 labs 中的独立脚本观察 **OpenAI 兼容的 Chat Completions**，不必启动 RayAgent。配置继续读 `LLM_*`。读结构即可跟上；要运行脚本，条件和命令见[基础实验运行指南](../labs/foundations/README.md#工具反馈循环)。未配置真实模型密钥时，外部调用为 `unverified`，正文与图中的调用都是示意。

> 请把 hello 写入 hello.txt，再读取文件，告诉我里面是什么。

这句话里有两件必须发生的事：先写入，再根据写入结果读取。主观察脚本把文件放在进程内存里，只用来看循环，不经过沙箱，也不是产品里的 Planner。

## 写完就停，确认就做不成

上一章的实验在执行工具后，下一次请求加了 `tool_choice="none"`。程序能打印一段 `content`，模型却不能再提出 `read_file`。

对上面这条请求，这就够致命。写入返回成功，只说明写这一步有了结果。要确认文件里是 `hello`，还必须再读一次。工具被锁住以后，模型最多只能口头说“已经写好”，没有新的执行事实。

有的脚本名字里带 ReAct，控制流却是同一回事：做完一次就强制收口。终端里一句一句输入，也只是用户换了一句、程序再走一遍，不是同一次查询里自己写完再读。

判断是不是工具反馈循环，要看执行结果是否真的参与了下一轮决策。

## 同一条请求，怎样连续做完

下面用三轮示意走完这条请求。字段和返回值都是机制说明，不是本次真实模型输出。

**第一轮。** 模型提出写入。程序执行后，把结果追加进消息：

```text
user: 请把 hello 写入 hello.txt，再读取文件，告诉我里面是什么。
assistant: tool_calls → write_file(filepath=hello.txt, content=hello)
tool: {"ok": true, "filepath": "hello.txt"}
```

到这里，程序只完成了上一章会做的事。若下一步禁止再调工具，循环在此结束。

**第二轮。** 再次请求时，上面三条都还在。模型看见写入成功，提出读取；程序读到内容后再追加一条：

```text
assistant: tool_calls → read_file(filepath=hello.txt)
tool: {"filepath": "hello.txt", "content": "hello"}
```

这一轮能发生，是因为第二次请求仍然允许 `tool_calls`。模型不是在回忆“我应该写过”，而是在看刚才那条 `role: tool`。

**第三轮。** 模型看见文件内容，不再请求工具，只返回 `content`。程序把它当作本轮回答，停下来。

如果第二轮读到的是“文件不存在”，第三轮的依据就变了：可能再写一次，也可能说明失败。循环不保证固定的「写、读、答」顺序，保证的是**下一次决策看得到上一轮结果**。

用户在终端里继续输入下一句，是另一层循环。上面三轮发生在同一次查询内部。

## 结果回来之后走哪条路

把刚才的过程收成判断：每次模型返回后，先看有没有 `tool_calls`。

有，就执行、回传、再请求。没有，就使用 `content`，结束本轮。次数用完仍在调工具，按上限停，不把空转当成完成。

```text
把用户请求追加到 messages
重复最多 N 次
  请求模型
  把这条 assistant message 追加到 messages
  如果没有 tool_calls：
    使用 content，结束本轮
  否则：
    执行工具
    追加 role: tool
如果 N 次之后仍在调用工具：
  按上限停止
```

和上一章伪代码的差别，不在“会不会执行工具”，而在执行之后：下一次请求还许不允许再调工具。

![同一条请求如何连续写入、读取并结束](assets/04-feedback-loop.svg)

图的左侧是每次响应后的分叉，右侧是文件任务可能的三轮。顺序是示意，不是实测。

ReAct 常用 Thought / Action / Observation 称呼这几步。提示词可以要求模型写出思考，那只是给模型看的格式。**循环是否成立，取决于结果回来之后会不会再次请求，以及会不会允许再调工具。** 没有 Thought 标签，只要继续条件还在，仍然是反馈循环。

系统还可能因为错误或等待用户而停下。本章最小脚本只实现了“没有 tool_calls”和“达到迭代上限”。提示词里写“可以向用户提问”，不等于程序进入了等待状态。

## 在实验里看谁真正在转

主观察脚本是 `labs/foundations/4_1_工具反馈循环.py`。它在内存里提供 `write_file` 和 `read_file`，用带上限的 `for` 循环重复「请求 → 执行 → 再请求」。运行条件见开头链接的基础实验指南。

决定它是不是循环的，是再次请求时没有锁住工具：

```python
response = self.client.chat.completions.create(
    model=self.model,
    messages=self.messages,
    tools=self.tools,
)
```

这里没有 `tool_choice="none"`。模型仍可提出 `read_file`，也可以直接给 `content`。本地夹具可以核对：写入后再读取会发出三次模型请求，后两次都不带 `tool_choice`；只有 `content` 时不再执行工具；工具一直不结束时按上限报错。夹具不能证明真实模型一定会先写后读。

上一章那种收口，以及名字里带 ReAct、控制流却相同的脚本，都可以拿来对照：它们在第二次调用上加了 `tool_choice="none"`。另有一份多步报销脚本，用递归再次进入 `process_query()`，继续条件相同，但没有迭代上限；注释写成“生成最终回复”，代码却会继续决策，以代码为准。报销规则是那份实验的业务，不是 RayAgent 的产品行为，也不是第 07 章的 Planner。

| 做法 | 结果回来之后 | 怎样停止 |
|---|---|---|
| 一次执行后锁死工具 | 第二次调用 `tool_choice="none"` | 强制生成文本 |
| 带上限的反馈循环 | 再请求，仍允许 `tool_calls` | 无工具调用，或达到上限 |
| 递归再请求 | 同样允许继续调用 | 无工具调用；没有上限 |

## 循环必须有边界

达到上限仍收到 `tool_calls` 时，最小脚本结束本轮并报错，而不是假定任务已经完成。没有上限的递归不会自己停。产品内层也按“无 tool_calls 则停”推进，另外还有迭代上限；外层如何安排步骤，留给第 07 章。有反馈，不等于会可靠地一直做完。

内存里的 `hello.txt` 只活在这次进程中。它证明写完之后可以再读，不能证明文件进了沙箱或被保存下来。
